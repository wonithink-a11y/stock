# 조용히 버려지는 소스 필드 감사

질문: **우리가 받고 있는데 저장하지 않는 데이터가 더 있는가.**
방법: 수집기 소스 코드의 저장 스키마 ↔ 프로브 산출물에 기록된 실제 응답 필드 대조.
읽기 전용 — 수집 실행 0건, 스키마 변경 0건.

**근거 등급을 섞지 않는다.** 실측(프로브 JSON에 응답 필드가 남아 있음)과
문서·관례(API 문서상 그 필드가 온다고 알려짐)를 갈라 적는다. 후자는 프로브
1콜이면 확정된다.

### A-1. 분봉 `acml_tr_pbmn` (누적 거래대금) ★ 시한 있음

## 소급 재수집 판단 — 실측으로 STOP (2026-09-09)

`acml_tr_pbmn` 을 소급으로 받을 값이 있는지 재봤다. 근사(`close×volume`)가 실제
거래대금과 얼마나 다른지를 **기존 로컬 데이터만으로** 쟀다 — 분봉
`Σ(close×volume)` vs A4 일별 실제 거래대금(`buyAmount['전체']`).

1차 대조는 오차 꼬리가 커 보였다(|오차|>1% 가 15~20%, 최악 -86%). 그런데 그것이
**근사 탓인지 범위 탓인지**를 갈랐더니:

```
2026-08-21 · 2,110종목
  상관(금액격차, 거래량격차) = 0.997          ← 거의 전부 같이 움직인다
  |금액격차|>5% 인 43종목 중 |거래량격차|>5% 도 함께인 비율 = 100%

★ 거래량이 0.1% 이내로 일치한 1,151종목만 (= 같은 범위를 본 종목):
     금액 격차 중앙  +0.0000%     |오차|>1%  0.70%     최대  +1.51%
```

꼬리는 **시간외·종가단일가 등 세션 범위 차이**지 가중 오차가 아니다.
**같은 범위를 볼 때 `close×volume` 근사는 사실상 정확하다.**

★ **이 측정이 말하지 않는 것**: 일 단위 집계로 쟀으므로 **분당 단위 오차는 모른다.**
누적·집계는 오차가 평균화되지만 한 개 bar 안의 가중 오차는 이걸로 안 잡힌다.
그리고 그것을 재려면 `acml_tr_pbmn` 이 있어야 한다 — 순환이다.

| 용도 | 근사로 충분한가 |
|---|---|
| 유동성 필터 · 유니버스 선정(거래대금 상위 N) | **충분**(오차 ~0%) |
| 거래대금 급증 · volume shock | **충분** |
| capacity · 체결가능금액 | **충분** |
| 분당·세션 초반 정확 VWAP | **남는다**(크기는 미측정) |

### 결정: 소급하지 않는다. 신규 수집분으로 간다 (사용자 확정)

- 소급이 메워줄 오차가 **집계 용도에서 0%** 다. 남는 건 세션 초반 VWAP 정밀도
  하나인데 그 실험은 이미 근사 기준 5배 격차로 REJECT 다.
- 신규 수집분은 비용 0 으로 매일 쌓인다. **1년 뒤엔 소급 없이 1년치가 생기고,
  그때는 전부 신규 수집이라 수정주가 축도 일관되다.**

**재개 조건**: 분당 정확 VWAP 이 실제로 필요한 연구가 생겼을 때. 그때의 방법은
전체 재수집이 아니라 **사이드카**다 — 별도 트리(`ticker·ts·tradingValue`)에
쓰고 조인한다. 기존 MN-1.0 파티션을 안 건드리므로 덮어쓰기·중복 위험이 없고,
거래대금은 금액이라 분할 조정에 사실상 불변이라 축 혼재도 안전하다. 단
**호출량은 줄지 않는다**(KIS 는 필드 단위 요청이 없다 — 200종목 1년 약 25만 콜·
7.5시간 / 전량 약 307만 콜·92시간). 착수 전 **1일 스모크로 조인 매칭률**을 먼저
잰다 — `(ticker, ts)` 가 1:1 로 안 맞으면 조용히 행이 빠진다.
