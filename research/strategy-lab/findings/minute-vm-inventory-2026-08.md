## 1. 데이터 존재 여부·파일 구조

존재한다. 구조:

```
~/minute-raw/
  date=YYYY-MM-DD/
    part-000.parquet ~ part-012.parquet   (13개 고정, 최초·최근 날짜 동일)
  _manifest/  {date}.json                  (VM 자체 일별 manifest, git repo와 별개)
  _state/     state-{date}.json            (일별 수집 상태)
  _t1/        plan.json, t1-{timestamp}.json (재현성 정찰(T1) 아티팩트)
```

parquet, ticker 단위 파일이 아니라 **샤드(part) 단위** — 13-way 분할.

## 6. 1분봉 여부·KST 여부

**확인됨.** 같은 종목의 연속 행이 `09:00 → 09:01 → 09:02` 1분 간격이고,
`ts`가 `+09:00` 오프셋(KST)을 명시적으로 갖고 있다. 관측 범위는
`09:00~15:30`(KRX 정규장 시간과 일치).

## 결론

1. **2,578종목 전체가 수집되지는 않는다.** 표본일 기준 2,448종목(94.94%)만
   실제 데이터가 있다.
2. **실제 수집 대상은 하루 약 2,448종목**(표본 1일 기준, 다른 날짜는 미확인).
   CLAUDE.md에 기록된 "약 2,455/2,578"과 근사해 이게 상시적인 수준으로 보인다.
3. **연구용 승격이 가능한 상태인가 — 조건부로 그렇다.** 스키마가 깨끗하고
   (ticker/ts/OHLCV, KST 1분봉 확인), 표본에서 중복도 없어 데이터 자체 품질은
   나쁘지 않다. 다만:
   - 이번 조사가 252일 중 1일 전량 + 구조 확인 수준이라, "전체 기간에 결측·
     중복이 없다"고 단정할 근거는 아직 없다.
   - 승격 파이프라인(VM → Object Storage → Actions 대조 → commit)이 여전히
     미구현이므로, 데이터가 "쓸 만해 보인다"와 "저장소로 승격할 준비가 됐다"는
     별개다 — 후자는 파이프라인 구현이 선행돼야 한다(이번 조사 범위 밖).
   - 실제 승격을 검토한다면 전체 252일에 대한 날짜별 종목수·중복·row수 전수
     검사가 다음 단계로 필요하다(이번엔 토큰 최소화를 위해 표본만 봤다).
