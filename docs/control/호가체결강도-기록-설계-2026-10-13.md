# 호가·체결강도 장중 기록 — 설계안 (2026-10-13, GO 대기)

> 상태: **10-13 사용자 GO → 수집기·유닛 작성(12b601d2), VM 프로브 통과, 타이머 설치는 사용자(sudo).**
> 프로브 결과: 6종 모두 rt_cd 0 · 순위 30행 · 패널 1행 94칸. 등락률 정렬 코드는 문서의 `0000` 이 아니라 `0`(OPSQ2002).
> 순위는 거래량 하한 10만 주·정리매매/거래정지/ETF/ETN/스팩 제외를 걸었다 — 없으면 체결강도 1위가 206주짜리(999.99) 종목이다.
> 실제 구현: 1분 순위 6콜 + 3분 패널(400콜, 초당 4 → 약 100초), 패널 도중에도 분이 바뀌면 순위를 끼운다. 08:51 부터 장 전 예상체결도 담는다. 휴장일은 09:03 삼성전자 최근 체결 시각으로 알아채고 지운다.
> 조회 전용 — 주문 경로 없음. 점수·매매에 쓰지 않는다(절대 규칙 1).

## 1. 왜 기록부터 하나

급등주 연구(야간연구-보고-2026-10-13)에서 가격·거래량·일별 수급·뉴스 조건은 전부 "맞히지만 사면 진다"였다.
아직 못 잰 것이 **장중 호가 잔량과 체결강도**(매수 체결 ÷ 매도 체결)다. KIS 는 이 값의 **과거 이력을 주지 않는다** —
오늘부터 쌓아야 몇 달 뒤 잴 수 있다. 공짜로 소급할 길이 없어서, 늦게 시작한 만큼 그대로 손해다.

기대는 낮게 둔다: 크립토 1분봉 거래량 급증은 과거 구간 t 5.30 → 이후 구간 +0.01bp 로 사라졌고(findings/scalping-volsurge-results-2026-09.md),
국내 장 초반 강세 종목은 장중에 진다(장 초반 무리형·테마 대장주 REJECT). 이 기록의 실질 가치는 "호가·체결강도도 안 된다"를 싸게 확정하거나, 드물게 실마리를 찾는 것이다.

## 2. 두 층으로 나눈다

| | 1층 — 시장 전체 순위 | 2층 — 고정 종목 패널 |
|---|---|---|
| 목적 | 지금 어디에 매수세가 몰리나(사건 목록) | 신호를 결과와 무관하게 재는 표본 |
| 대상 | KOSPI·KOSDAQ 전 종목 중 순위 상위 | **전일 거래대금 상위 200**(전날 분봉으로 장 전에 고정) |
| 무엇 | 체결강도 상위 · 호가잔량(순매수잔량) 순위 · 거래량 급증 · 등락률 상위 | 10단계 호가 잔량·총잔량·예상체결 + 최근 체결(체결강도) |
| 주기 | 1분 | 3분 |
| 호출 | 약 8콜/분 → 하루 약 3천 | 200 × 2콜 / 3분 ≈ 초당 2.2 → 하루 약 5만 |
| 한계 | **순위에 든 종목만** 보인다 → 결과로 고른 표본이 되기 쉽다(급등한 뒤 상위에 뜸). 사건 시각 기록용 | 거래대금 상위라 소형 급등주는 적다 |

**왜 1층만으로 안 되나**: 체결강도 상위에 뜬 종목은 이미 오르는 중인 종목이다. "뜬 뒤 샀다면"은 잴 수 있지만
"체결강도가 높아진 종목이 그렇지 않은 종목보다 나은가"는 순위 밖 종목 값이 없으면 못 잰다(교훈75 — 없는 행은 이유를 말하지 않는다). 그래서 2층이 판정용 정본이다.

**왜 2층은 200개·3분인가**: 실전 키 한도는 초당 20콜이고, 같은 키를 분봉 수집·A2b·ETF 일일 수집·autotrader 스냅샷이 쓴다.
장중엔 분봉 수집이 안 돌아 여유가 있지만, 초당 2~3콜로 묶어 다른 작업의 `EGW00201`(초과) 위험을 남기지 않는다. 1분 주기로 올리려면 첫 주 실측(§5) 뒤에.

**왜 웹소켓(실시간 체결 H0STCNT0)이 아닌가**: 체결 메시지 하나에 체결강도·총호가잔량이 다 들어 있어 가장 정밀하지만 **접속 하나에 41종목** 상한이다.
모의 키는 이미 `kis-live-relay`(관심종목 실시간 중계)가 쓰고 있고, 실전 키 토큰을 상시 잡으면 배치 작업이 깨진 전례가 있다(relay 머리말). 시장 전체 표본이 목적이라 REST 스냅샷이 맞다.

## 3. 저장

```
VM ~/orderflow-raw/date=YYYY-MM-DD/rank.parquet     1층 (시각·순위 종류·시장·순위·종목·값 칸)
VM ~/orderflow-raw/date=YYYY-MM-DD/panel.parquet    2층 (시각·종목·매도/매수 호가 1~10·잔량 1~10·총잔량·예상체결가·체결강도·최근 체결 요약)
VM ~/orderflow-raw/date=YYYY-MM-DD/universe.json    그날 2층 200종목과 고른 근거(전날 거래대금)
```
- 하루 2층 약 4만 행, 수 MB. 1년 1GB 미만 — VM 디스크 문제없음.
- **저장소에 올리지 않는다**(분봉처럼 manifest 승격까지 만들 이유가 아직 없다). 월간 점검 때 `--sync` 로 로컬 `.cache/orderflow_raw/` 에 복사(분봉 `--sync` 와 같은 방식).
- 응답이 요청 종목·시각을 담는지 검사한다(교훈81). 실패·빈 응답은 버리지 말고 `status` 칸에 이유를 남긴다 — 빈 칸이 정상인지 손실인지 나중엔 모른다.
- 시각은 수집기가 받은 시각(KST, 초 단위)과 응답 안 시각을 둘 다 둔다.

## 4. 결과(수익률)는 따로 받지 않는다

수익률은 이미 매일 쌓이는 분봉(`~/minute-raw`)으로 계산한다. 이 기록은 **신호 쪽만** 쌓는다 — 수집기는 단순하게, 연구는 나중에.

## 5. 단계

| 단계 | 내용 | 확인 |
|---|---|---|
| 0. 프로브 | 순위 4종·호가·체결 TR 을 각 1회 호출해 칸 이름·행 수·모의 키 지원 여부 확인. 순위 TR ID 는 KIS 공식 예제에서 확인 후 확정(이 문서엔 아직 안 적는다) | 1회, 수십 콜 |
| 1. 수집기 | `scripts/collect-orderflow-kis.py` — 2층 종목 선정(전날 분봉 거래대금) · 1분 루프 · 3분 패널 · 초당 상한 · fail-soft · `--selftest` | 회귀 |
| 2. 유닛 | `deploy/orderflow-collect.{service,timer}` 평일 08:58 시작 · 15:31 종료(한 번 띄워 장 끝까지 도는 서비스) · OnFailure 장애 그룹 알림 | **사용자 설치(sudo)** |
| 3. 첫 주 실측 | 하루 호출 수·`EGW00201` 횟수·누락 비율·다른 작업 영향(분봉 수집·autotrader 스냅샷 로그) | 1주 뒤 보고 |
| 4. 사전등록 | **6개월 쌓인 뒤**(≈2027-04) 질문을 결과 전에 고정 — 예: 2층에서 체결강도 상위 20% ∧ 순매수잔량 양(+) → 30분·종가 초과(같은 시각 같은 직전 수익 종목 대조), 비용 33.5bp | 그때 GO |

판정 질문을 지금 정하지 않는 이유: 칸 구성·누락 패턴을 보기 전에 정하면 잴 수 없는 계약이 된다(교훈50). 대신 **데이터를 보기 전에** 정한다 — 6개월 동안 값을 열어 보지 않는다(건수·누락만 본다).

## 6. 비용·위험

- 돈: 0원(KIS 무료). VM 추가 부하 미미(지금 load 0.16).
- 위험: 실전 키 초당 한도 공유 → 초당 상한을 코드에 고정하고 첫 주 실측. 토큰은 기존 파일 캐시(`KIS_TOKEN_CACHE`)를 같이 써서 새로 발급하지 않는다(토큰 발급 알림 사고 전례 — 메모리 feedback-kis-token-per-actions-run).
- 되돌리기: 타이머 끄면 끝. 데이터는 VM 디렉터리 하나.
