## 1. 결함 A — 이월 조각 재검증이 hive 파티션 컬럼에 걸렸다 (커밋 `3130ade`, 🟡)

```
09-04 16:10  FAIL  위반 1건 openOutOfRange   697s   ← 최초 실패
09-04 17:42  FAIL  위반 20건 schemaMismatch    8s   ← 원인이 바뀐다
   … 이후 모든 재시도가 8초 만에 같은 죽음
```

`revalidate_carried` 가 쓰던 `pq.read_table(f)` 가 상위 `date=YYYY-MM-DD/`
디렉터리를 hive 파티션으로 읽어 **파일에 없는 `date` 컬럼을 되붙인다.**
그러면 `validate_rows` 의 `list(r.keys()) != SCHEMA` 가 전 행을
`schemaMismatch` 로 세운다. resume 은 설계상 재수집을 안 하므로
(회귀 22b 가 그걸 핀으로 박아 뒀다) **그 하루는 영원히 FAIL 에 갇힌다.**

### ★ 왜 회귀가 이걸 못 잡았나 — 같은 코드가 버전에 따라 갈렸다

```
로컬 pyarrow 25.0.0   되붙이지 않는다   → 22b 초록
VM   pyarrow 17.0.0   되붙인다         → 실운영 FAIL
```

VM 은 Python 3.8 이라 pyarrow 가 구버전으로 고정된다(CLAUDE.md VM 운영 기준).
**CLAUDE.md 는 이미 이 위험을 적어 뒀다** — *"결정적 쓰기 같은 성질은 pyarrow
버전의 함수이므로 VM에서 다시 잰다"*. 그 경고가 쓰기에는 적용됐고 읽기에는
적용되지 않았다.

고침: `pq.ParquetFile(str(f)).read()` — 파일 자체 스키마만 읽어 버전과 무관하다.
겸사 MN-1.0 조각(`tradingValue` 없음)을 알려진 옛 스키마로 받아 `None` 으로
채운다(교훈57 — 없는 것은 0이 아니다). 그 밖의 어긋남은 그대로 위반이다.

회귀 22c 신설(5건). **스키마 검사가 아니라 '실제 위반이 나오는가'를 잰다** —
버전이 갈려도 같은 것을 보려면 그래야 한다. VM(pyarrow 17)에서 직접 돌려
확인했다.

## 2. 결함 B — `openOutOfRange` 실측 (커밋 `2eeafd8`, 🔴 승인)

**MN-1.1 면제의 근거가 깨졌다** — 정책 주석의 *"09:01 이후로는 한 건도 없다"*
(3거래일 표본, 2026-08-10)가 263거래일에서 **28건**이었다.

### 메커니즘 전수 분해 (69건, 설명 불가 0)

```
52건 (75%)  그 종목의 그날 첫 봉          open = 시가단일가 체결가
17건 (25%)  open == 직전 체결 봉의 close  이월값 (7건은 거래 공백 뒤)
```

**소스가 `open` 을 "이 분의 첫 체결가"로 주지 않는다.** 09:00 이 특별한 게
아니라 대부분의 종목이 그때 처음 체결될 뿐이다. 11:00 건은 그때까지 거래가
없던 종목이고, 옛 카운터 이름 `openOutOfRangeAtSessionOpen` 의
"AtSessionOpen" 이라는 단언을 반증한다.

## 4. 실측 중 나온 함정 셋 (다음 세션이 같은 데 안 빠지게)

1. **행 단위 파이썬으로 1.5억 봉을 훑지 않는다.** 첫 시도가 10분 타임아웃을
   넘겼다. `pyarrow.compute` 로 벡터화하니 **27초**다. 두 번 같은 실수를 했다 —
   두 번째(carry 가설 검정)는 위반이 있는 날만 스캔해 5초가 됐다.
2. **백그라운드로 밀린 작업이 나중에 출력 파일을 덮는다.** 타임아웃으로
   백그라운드에 간 첫 스캔이 완주하면서 `local.json` 을 다시 썼고, 그 사이
   같은 경로에 쓴 빠른 판본을 깨뜨렸다("Extra data: line 2"). 재생성으로 풀었다.
3. **`--days` 기본값 3 때문에 실패한 날짜가 3일 지나면 백로그에서 사라진다.**
   정기 타이머는 "할 일 없다"고 답했고 `--date` 로 직접 지목해야 했다.
   결함 A·B 와 같은 무리(조용한 영구 손실)지만 별건이고 **미수정**이다.
