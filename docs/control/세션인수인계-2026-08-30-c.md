## 1. 매크로 리서치 파이프라인 — calendar.json 동결 문제 완전 해소

- **근본 원인 발견**: `research/strategy-lab`의 매크로 4개 스크립트(`build_vix_backfill.py`
  등)가 전부 `data/backfill/calendar.json`(A0.5, 프로덕션 백필 체인 전용, 수동 갱신)의
  `tradingDays`를 읽어 KR 거래일 asOf-join을 했다 — calendar.json이 8/14에 멈춰 있어서
  원본 FRED/ECOS가 최신이어도 결과가 항상 8/14에서 잘렸다.
- **해결**: `macro_common.py`의 `load_kr_calendar()`를 `scripts/build-calendar.py`와 같은
  방식(pykrx 라이브 조회)으로 교체 — calendar.json을 아예 안 읽게 분리(커밋 `ff37237`).
  GH Actions 실측으로 `seriesAsOf`가 8/14→8/28로 늘어난 것 확인.
- **미국 국채금리 소스 교체**: FRED DGS2/DGS10이 실측상 최소 1영업일 지연(주말 낀 경우
  더 늦음)됨을 확인 — 미 재무부 Daily Treasury Par Yield Curve Rates(무인증, 무료,
  FRED보다 빠름)로 전환 + DGS30(30년물) 신규 추가(커밋 `f2c1e84`). 재무부 사이트가
  연속 요청 시 요청당 18~25초로 느려지는 현상 실측 확인(로컬·GH Actions 둘 다 재현) —
  치명적이진 않음(전체 워크플로 632초, public repo라 Actions 분당 비용 무료)이라
  최적화 안 함.
- **매크로 UI/Calendar 워크플로 스케줄 활성화**: `macro-regime-ui.yml`(`ddd21e7`),
  `calendar.yml`(`3d1f317`) 둘 다 schedule 켬. **원래 "calendar.yml 수동 전용" 설계
  근거("스케줄 걸면 A1~A8 재실행 파급")를 코드로 재검토해 틀렸음을 확인** — A1a~A8은
  calendar.json 변경을 감지해 자동으로 도는 데몬이 아니라 각각 별도로 트리거해야
  하는 배치 스크립트라 자동 파급 경로 자체가 없다. `calendar.yml` 활성화 중
  **CAL_FROM 빈값 처리 버그**를 발견·수정(CAL_TO만 방어돼 있었음 — schedule 트리거는
  `github.event.inputs` 자체가 없어 크래시 위험이 있었음).
- **실제 calendar.json 갱신 실행**: 8/14→8/28로 갱신(`e8da06a`). A2a 최소표본(1종목)
  스모크로 하류가 새 범위를 정상 반영하는지 실측 확인 — `구간 20140513~20260828`
  정상 확인, 부작용 없음.
- **자동 갱신 메커니즘 명확화**(사용자 질문에 답변) — calendar.json은 앞으로 평일

## 6. OCI Object Storage IAM — 진행 중, 미해결

목적: 분봉 manifest 승격 파이프라인(`VM → Object Storage → Actions → commit`)의 첫 단계,
`stock`/`stock-new` VM이 Instance Principal로 `Stock-minute-manifest` 버킷에 쓸 수 있는지
검증.

- Dynamic Group `stock-minute-object-writer`(`ANY{instance.id=stock, instance.id=stock-new}`)
  + Policy `stock-minute-object-writer-policy`(`manage objects in tenancy where all
  {target.bucket.name='Stock-minute-manifest', any {request.permission='OBJECT_CREATE',
  request.permission='OBJECT_INSPECT'}}`) — 사용자가 콘솔에서 생성, 문법·OCID 둘 다
  캡처로 확인.
- `stock-new`에 OCI CLI 설치(격리 venv `~/oci-cli-venv`, collector-venv와 안 섞음, v3.91.0).
- **Instance Principal 인증 자체는 확실히 성공** — `oci os ns get`도 되고, 인스턴스
  identity 인증서(`http://169.254.169.254/opc/v2/identity/cert.pem`)를 직접 디코딩해
  Dynamic Group에 넣은 OCID와 바이트 단위 일치 확인.
- **그런데 `put_object`(OBJECT_CREATE)·`head_object`(OBJECT_INSPECT)가 전부
  실패** — `BucketNotFound` 계열 404, 메시지 자체가 "does not exist **or you are
  not authorized**"라 권한 문제임을 OCI가 스스로 암시.
- **정정 사항**: 초반에 `get_bucket`/`list_buckets` 실패를 권한 문제의 증거로
  해석했는데, 이건 틀렸다 — 이 Policy는 애초에 `buckets` 리소스 타입엔 권한을
  안 줬으니(`objects`만 줌) 그 둘이 실패하는 건 설계대로 정상. 판단 근거가
  됐어야 할 건 `put_object`/`head_object`뿐이고, 이 둘은 여전히 실패 중.
- **현재 작업가설**: Dynamic Group membership 변경의 OCI 전파 지연(공식 문서상
  최대 ~1시간). 변경 후 30분 시점 재검증도 여전히 실패(동일 에러) — **다음 검증은
  22:30 KST 예약됨(ScheduleWakeup, 이 세션 안에서)**. 그때도 실패하면 전파 지연
  가설은 소진된 것으로 보고 다른 원인(Dynamic Group 중복 생성·Policy 실제 attach
  컴파트먼트 등, 전부 콘솔에서만 확인 가능해 다음 세션에서 사용자 확인 필요)을
  찾아야 한다.
- 코드/설정/IAM 전혀 변경 안 함(사용자 명시 지시) — 전부 읽기 전용 진단 + 테스트
  object 1개 시도(전부 실패해서 실제로 생성된 적 없음).
