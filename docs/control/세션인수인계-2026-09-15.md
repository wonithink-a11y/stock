## 0. 다음 세션이 먼저 볼 것

### ① 업비트 CORS 요청 전용 요청 한도 — 재론 금지, 완화 안 됨

업비트는 브라우저에서 오는(Origin 헤더 있는) 요청에 서버 대 서버 호출
(분당 수백 회)과는 별개로 **훨씬 빡빡한 한도(IP당 분당 6회 수준)**를
건다(2026-09-15 실측, `curl -H "Origin: ..."` vs 헤더 없는 호출을 나란히
비교해 확인 — 후자는 `group=ticker; min=600`, 전자는 `group=origin;
min=6`). 막히면 CORS 헤더 없는 429를 돌려줘 브라우저가 상태코드를 읽기도
전에 `TypeError: Failed to fetch`로 뭉뚱그린다. **이건 이 세션의 버그가
아니라 업비트 쪽 구조적 한도다** — 코드로 없앨 수 없고, 지수 백오프
재시도(최대 2회, 1.5s→3s)와 "다시 시도" 버튼으로 완화만 했다. 다음
세션이 또 "업비트만 안 된다"는 보고를 받으면 새로 원인을 찾지 말고 이
항목부터 확인한다 — 몇 초~1분 기다리면 대개 풀린다. 빗썸은 이 한도가
없다(실측: burst capacity 150, 훨씬 여유 있음).

### ② GH Pages 배포는 push 직후 자동으로 도는데, 캐시 때문에 확인이 늦을 수 있다

`ui/tabs/*.js`는 GH Pages에서 `Cache-Control: max-age=600`(10분)로
캐싱된다. 이번 세션에서 배포 직후 브라우저가 구버전 스크립트를 계속
써서(캐시 히트) "코드를 고쳤는데 반영이 안 됐다"는 혼란이 있었다 —
`location.reload(true)`는 이 캐시를 안 뚫는다(Chrome이 그 인자를 무시).
확인할 땐 Ctrl+Shift+R(강제 새로고침)을 쓰거나, 스크립트 URL에
`?cb=<timestamp>`를 붙여 직접 fetch해서 내용을 대조한다.

### ③ 남은 기능 후보 — 착수 안 함, 사용자가 명시적으로 요청하면 그때 검토

- **진짜 매수/매도 체결량 분리** — 지금 "거래량" 막대는 캔들 방향(상승/
  하락)으로 색칠한 것뿐이지 진짜 매수자/매도자 체결량 구분이 아니다.
  진짜로 하려면 체결(tick) 데이터를 낱개로 받아 buyer/seller를 직접
  판별해야 해서 API 호출량이 훨씬 커진다 — 업비트 CORS 한도(위 ①)를
  감안하면 지금 구조로는 무리다. 재개하려면 서버 사이드 집계(VM에서
  주기적으로 tick을 모아 JSON으로 미리 계산해두는 방식)를 먼저 검토해야
  한다.
- **다른 브로커(업비트·빗썸)의 성과 이력** — 여전히 "현재 스냅샷"만
  있다(`세션인수인계-2026-09-14-b.md` §5에서 이미 지적됨, 안 바뀜).

  RSI/MACD처럼 캔들과 같은 시간축을 따라 계속 이어지는 막대였다 — API로
  낼 수 없는 모양이라 대신 **거래량**(캔들에 이미 있는 값, 방향별 색칠)
