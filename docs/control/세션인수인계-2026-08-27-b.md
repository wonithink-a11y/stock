## 3. 🔴 안전 — 반드시 먼저 읽을 것

### 3-1. 키 노출 사고 (미해결 가능성 있음)

이번 세션 중 사용자가 여러 서비스 키를 모아둔 파일(`C:\Users\User\
Downloads\KEY\KEY.txt`)을 자동으로 읽게 해달라고 요청했다. `scripts/
setup-all-keys.py --from-file ... --diagnose`(진단 모드, 값을 안 보여주는
게 설계 의도였음)를 돌리는 과정에서 **버그로 실제 원문 값 두 개가 대화
로그에 그대로 출력됐다**:

1. `KIS_APP_KEY`/`KIS_APP_SECRET`(실전) 중 **`KIS_APP_SECRET`이 확실히
   노출**됐다(라벨과 함께 출력돼 어떤 키인지 명확함).
2. 라벨 없이 값 하나가 더 노출됐다 - **어느 서비스의 어느 키인지 세션 내
   에서 특정하지 못했다.** 사용자가 원본 파일(`KEY.txt`)에서 `KIS_APP_
   Secret` 줄 바로 다음/근처에 있던 값이 무엇인지 직접 확인해야 한다.

**사용자가 "그건 내가 알아서 할게"라고 답해 이 세션은 재발급(rotate)
여부를 확인할 방법이 없다.** 새 세션이 반드시 사용자에게 재확인할 것:
- KIS 실전 앱시크릿을 KIS Developers에서 재발급했는가?
- 두 번째 노출값의 정체를 확인했고, 그것도 재발급했는가?
- **지금 `.env`에 들어있는 `KIS_APP_SECRET`이 재발급된 새 값인지, 노출됐던
  옛 값을 그대로 다시 넣은 것인지는 이 세션도 다음 세션도 확인할 방법이
  없다**(값을 직접 안 보는 게 설계 원칙이라 - 이게 맞는 설계이지만, 그
  대가로 "재발급이 실제로 됐는지"는 코드로 확인이 안 되고 사용자 확인에
  의존한다).

근본 원인(재발생 방지용 기록): `setup-all-keys.py`의 라벨 파싱이 줄에서
첫 번째 `=` 또는 `:`를 라벨/값 구분자로 가정했는데, 파일의 실제 형식이
`라벨 값`(공백 구분, 구분자 없음)이었다. 값 자체가 base64라 끝에 "="
패딩이 있어, 그 패딩 문자를 진짜 구분자로 착각해 줄 전체(라벨+값)를
"라벨"로, 패딩 뒤 남은 조각을 "값"으로 잘못 나눴다.

**`scripts/setup-all-keys.py`는 이제 쓰지 않는다.** 파일을 자동으로
통째로 파싱하는 방식 자체가 이런 종류의 사고를 구조적으로 못 막는다
(같은 취약점이 다른 파일 형식에서 또 나올 수 있음). 코드는 참고용으로
남겨뒀지만(`--diagnose` 모드는 라벨만 보여주고 값은 안 보여주도록 고쳤음
- 그래도 다시 쓰지 않는 게 안전) **새로 키를 넣을 일이 있으면 반드시
`scripts/setup-keys-interactive.py`(또는 `setup-keys.bat` 더블클릭)를
쓴다** - 서비스당 값 하나씩만 클립보드로 받아 같은 부류의 파싱 버그가
원리적으로 불가능하다(구분자 파싱 자체를 안 한다).

### 3-2. Claude는 `.env`나 사용자의 키 모음 파일을 직접 읽지 않는다

이 세션 전체에서 지켜진 원칙이고, 다음 세션도 지켜야 한다 - Read 도구로
`.env`나 키가 담긴 파일을 열지 않는다. 값 확인이 필요하면 마스킹된
출력만 하는 전용 스크립트(`probe-upbit-key-check.py` 같은)를 통해서만
간접 확인한다.
