# VM 이전 계획 — stock-Monitor(x86/1GB) → Stock(ARM/10GB)

작성 2026-08-23. 실행은 오늘 오후 5시 이후(사용자 주간사용량 한도 이후)로 보류 —
지금은 계획만 확정한다. 각 실행 단계는 그때 별도로 사전 확인한다.

## 배경

CLAUDE.md "수집 VM 운영 기준"이 미리 못박아 둔 상황: "나중에 큰 VM이 생기면
코드가 아니라 실행 환경만 옮긴다." 오늘 그 VM이 생겼다 — `Stock`
(`VM.Standard.A1.Flex`, 1 OCPU/10GB, Always Free 범위 확인됨, public IP
129.225.145.14).

## 확인된 전제

- `Stock`이 Always Free 범위 안(사용자 확인, 2026-08-23).
- **아키텍처가 바뀐다** — 기존 `stock-Monitor`(129.225.177.125)는
  `VM.Standard.E2.1.Micro` = x86(AMD), `Stock`은 `VM.Standard.A1.Flex` = **ARM**.
  단순 증설이 아니라 venv 재생성 + `scripts/check-vm-readiness.py` 재검증이
  필수다(기존 x86 실측 RSS·pyarrow 결정성 수치는 그대로 안 옮겨진다).
- `stock-Monitor`는 현재 유일한 운영 박스다(매일 16:10·17:40 수집, 18:10 감시,
  19:10 T1, Broad ~2,455/2,578종목). 끊기면 그날 분봉이 KIS 보존기간 때문에
  영구 손실 — 무중단 전환이 원칙.
- 로컬 `~/.ssh/config`에 `Host stock` → 129.225.177.125(기존)만 등록돼 있다.
  `Stock`(신규)용 엔트리는 아직 없음.

## 실행 순서 (각 단계 시작 전 사용자 확인)

1. **SSH 설정** — `~/.ssh/config`에 신규 `Host` 엔트리 추가(129.225.145.14),
   키 페어 확인(기존 키 재사용 가능한지, 신규 키가 필요한지).
2. **환경 구축(ARM)** — venv 새로 생성. requirements는 기존과 동일 버전 우선
   시도 → 실패하는 패키지(pyarrow 등 컴파일 필요한 것)만 개별 대응.
3. **재검증** — `scripts/check-vm-readiness.py`를 새 VM에서 실행, 메모리 RSS·
   pyarrow 결정적 쓰기 여부를 x86 기존 실측치와 나란히 문서화.
4. **코드 배포(수동, 크론 미등록)** — `stock-Monitor`가 쓰는 collector/deploy
   스크립트를 무변경으로 복사만 한다. 이 시점까지는 스케줄러에 아직 안 건다.
5. **병행 시험수집** — 실제 스케줄 시각대에 새 VM에서 수동 실행(1회 또는
   며칠), 산출물은 기존 경로와 분리된 디렉터리에 저장.
6. **구조적 대조** — 같은 날 기존 VM 산출물과 행수·스키마·품질게이트
   (gapReason·dayVerdict 등)를 비교. **byte-diff 완전 일치는 기대하지 않는다**
   (T1 재현성 정찰 FAIL 결론 — KIS 재조회가 항상 동일값을 주는 게 아님).
   구조적 일치(정상 커버리지·정상 게이트 통과)만 확인하면 된다.
7. **전환** (검증 통과 시) — systemd timer·cron을 새 VM으로 이관, 기존 VM은
   크론만 끄고 그대로 둔다(폴백 대기, Always Free라 유지 비용 없음).
8. **정리** — 며칠 안정 확인 후 기존 VM을 완전히 끌지, 다른 용도(분봉 승격
   파이프라인 등 여유 있는 작업)로 돌릴지 결정.

## 안전 메모

- 6단계까지는 기존 VM·기존 산출물 경로를 전혀 건드리지 않으므로 언제든 중단
  가능.
- 7단계(크론 이관) 이후 문제가 생기면 기존 VM이 그대로 살아 있으니 즉시
  되돌릴 수 있다.
- SSH 키·자격증명은 기존 원칙대로 어떤 자동화 서브에이전트(Ox Alpha 등)에도
  전달하지 않는다.
- 4·5·7·8단계(배포·실행·크론 등록/해제)는 운영 변경이라 매 단계 실행 직전
  별도로 확인받는다 — 이 문서의 존재가 사전 승인을 대신하지 않는다.

## 여유 용량 활용 후보 (전환 완료 이후, 별도 판단)

- 아직 미구현인 분봉 승격 파이프라인(VM → Object Storage → Actions → commit)
  구축 — 1GB에서는 부담스러웠던 작업.
- 청크 제출·동시성 2~4 같은 기존 보수적 설계는 메모리보다 API 예의/안정성
  목적도 있어 여유가 생겼다고 바로 완화할 필요는 없다.
