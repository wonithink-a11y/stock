# VM 이전 계획 — stock-Monitor(x86/1GB) → Stock(ARM/10GB)

작성 2026-08-23. 실행은 오늘 오후 5시 이후(사용자 주간사용량 한도 이후)로 보류 —
지금은 계획만 확정한다. 각 실행 단계는 그때 별도로 사전 확인한다.

## 배경

CLAUDE.md "수집 VM 운영 기준"이 미리 못박아 둔 상황: "나중에 큰 VM이 생기면
코드가 아니라 실행 환경만 옮긴다." 오늘 그 VM이 생겼다 — `Stock`
(`VM.Standard.A1.Flex`, 1 OCPU/10GB, Always Free 범위 확인됨, public IP
129.225.145.14).

## 확인된 전제

- `Stock`이 Always Free 범위 안(사용자 확인, 2026-08-23).
- **아키텍처가 바뀐다** — 기존 `stock-Monitor`(129.225.177.125)는
  `VM.Standard.E2.1.Micro` = x86(AMD), `Stock`은 `VM.Standard.A1.Flex` = **ARM**.
  단순 증설이 아니라 venv 재생성 + `scripts/check-vm-readiness.py` 재검증이
  필수다(기존 x86 실측 RSS·pyarrow 결정성 수치는 그대로 안 옮겨진다).
- `stock-Monitor`는 현재 유일한 운영 박스다(매일 16:10·17:40 수집, 18:10 감시,
  19:10 T1, Broad ~2,455/2,578종목). 끊기면 그날 분봉이 KIS 보존기간 때문에
  영구 손실 — 무중단 전환이 원칙.
- 로컬 `~/.ssh/config`에 `Host stock` → 129.225.177.125(기존)만 등록돼 있다.
  `Stock`(신규)용 엔트리는 아직 없음.

## 실행 순서 (각 단계 시작 전 사용자 확인)

1. **SSH 설정** — `~/.ssh/config`에 신규 `Host` 엔트리 추가(129.225.145.14),
   키 페어 확인(기존 키 재사용 가능한지, 신규 키가 필요한지).
2. **환경 구축(ARM)** — venv 새로 생성. requirements는 기존과 동일 버전 우선
   시도 → 실패하는 패키지(pyarrow 등 컴파일 필요한 것)만 개별 대응.
3. **재검증** — `scripts/check-vm-readiness.py`를 새 VM에서 실행, 메모리 RSS·
   pyarrow 결정적 쓰기 여부를 x86 기존 실측치와 나란히 문서화.
4. **코드 배포(수동, 크론 미등록)** — `stock-Monitor`가 쓰는 collector/deploy
   스크립트를 무변경으로 복사만 한다. 이 시점까지는 스케줄러에 아직 안 건다.
5. **병행 시험수집** — 실제 스케줄 시각대에 새 VM에서 수동 실행(1회 또는
   며칠), 산출물은 기존 경로와 분리된 디렉터리에 저장.
6. **구조적 대조** — 같은 날 기존 VM 산출물과 행수·스키마·품질게이트
   (gapReason·dayVerdict 등)를 비교. **byte-diff 완전 일치는 기대하지 않는다**
   (T1 재현성 정찰 FAIL 결론 — KIS 재조회가 항상 동일값을 주는 게 아님).
   구조적 일치(정상 커버리지·정상 게이트 통과)만 확인하면 된다.
7. **전환** (검증 통과 시) — systemd timer·cron을 새 VM으로 이관, 기존 VM은
   크론만 끄고 그대로 둔다(폴백 대기, Always Free라 유지 비용 없음).
8. **정리** — 며칠 안정 확인 후 기존 VM을 완전히 끌지, 다른 용도(분봉 승격
   파이프라인 등 여유 있는 작업)로 돌릴지 결정.

## 안전 메모

- 6단계까지는 기존 VM·기존 산출물 경로를 전혀 건드리지 않으므로 언제든 중단
  가능.
- 7단계(크론 이관) 이후 문제가 생기면 기존 VM이 그대로 살아 있으니 즉시
  되돌릴 수 있다.
- SSH 키·자격증명은 기존 원칙대로 어떤 자동화 서브에이전트(Ox Alpha 등)에도
  전달하지 않는다.
- 4·5·7·8단계(배포·실행·크론 등록/해제)는 운영 변경이라 매 단계 실행 직전
  별도로 확인받는다 — 이 문서의 존재가 사전 승인을 대신하지 않는다.

## 진행 기록

- **1단계 완료** — `~/.ssh/config`에 `Host stock-new`(129.225.145.14) 추가.
  연결 확인: `ubuntu@` 접속 정상, `aarch64` · Ubuntu 24.04.4 LTS.
- **2단계 완료** — `~/collector-venv`(Python 3.12.3) 생성. 기존 pinned
  버전(x86/py3.8 `pip freeze`) 그대로 설치 시도 → 대부분 정확히 일치,
  cp312 wheel이 없던 2개만 개별 대응:
  - `numpy` 1.24.4 → **1.26.4** (1.24.4는 py3.12 소스빌드 자체가 불가)
  - `pandas` 2.0.3 → **2.3.3** (동일 사유)
  - `setuptools<81`로 고정(부수 조치) — pykrx가 쓰는 `pkg_resources`가
    setuptools 84+에서 빠져 import 실패, 다운그레이드로 해결
  - `pyarrow==17.0.0`은 정확히 동일 버전 그대로 설치됨
- **3단계 완료** — `scripts/check-vm-readiness.py` 새 VM에서 실행, 기존
  x86 실측(`docs/operations/minute-실측기록.md` "VM 준비 완료 2026-08-10")과
  대조:

  | 항목 | 기존(x86·1GB·py3.8) | 신규(ARM·10GB·py3.12) |
  |---|---|---|
  | MemTotal | 952MB | 9,916MB |
  | MemAvailable | 539MB | 9,392MB |
  | 조각 피크 RSS | 167MB | **168.9MB** (거의 동일) |
  | pyarrow | 구버전 고정 | 17.0.0(동일 버전) |
  | 결정적 쓰기 | PASS | **PASS** |
  | parquet 왕복·zstd | PASS | PASS |

  FAIL 1건(KIS 앱키 미설정)은 예상된 것 — 4단계(코드·자격증명 배포) 전이라
  당연히 없다. 진짜 실패 아님.
- **4단계 완료** — `~/collector`에 기존 VM과 **동일 커밋**(`29f2640`)으로
  git clone(무변경 원칙 준수, main 최신이 아니라 기존 VM이 실제로 돌리는
  버전에 맞춤). 자격증명(`.env`·`collector.env`)은 `scp -3`으로 두 VM
  사이에서 직접 전송(로컬에 내용을 띄우지 않음), 파일 크기 245B/400B
  정확히 일치 확인. systemd 유닛·crontab은 아직 등록 안 함(계획대로).
  `run-minute-daily.py --selftest`(16 PASS)·`alive-monitor.py
  --selftest`(27 PASS) 전부 통과 — numpy 1.26.4·pandas 2.3.3로 버전이
  바뀐 환경에서도 회귀 무영향 확인.
- **5단계 완료(1일치만)** — 사용자 선택으로 08-21 하루만 시험수집(3일
  전체가 아님). 새 VM에서 `run-minute-daily.py --date 2026-08-21` 실행,
  1,364.3초(22분 44초) 소요 — 기존 x86 VM 실측(~22분)과 거의 일치.
  결과: `TRADING_OBSERVED` · rows=591,605 · 종목 2448/2579 · unresolved
  0 · acceptancePassed=true. 별도 경로(`~/minute-raw`, 새 VM 로컬)에
  저장, 기존 VM 산출물 무영향.
- **6단계 완료** — 같은 날짜(2026-08-21) 기존 VM manifest와 대조:

  | 항목 | 기존(x86) | 신규(ARM) | 일치 |
  |---|---|---|---|
  | rows | 591,603 | 591,605 | 거의 일치(차이 2행, 0.0003%) |
  | symbols | 2,579 | 2,579 | ✅ |
  | symbolsWithRows | 2,448 | 2,448 | ✅ 완전 일치 |
  | symbolsNotQueried | 0 | 0 | ✅ |
  | gapReasons.EMPTY | 44 | 44 | ✅ 완전 일치 |
  | gapReasons.HALT | 87 | 87 | ✅ 완전 일치 |
  | unresolved | {} | {} | ✅ |
  | acceptancePassed | true(4/4 게이트) | true(4/4 게이트) | ✅ |
  | dayVerdict | TRADING_OBSERVED | TRADING_OBSERVED | ✅ |

  행수 2행 차이만 있고 나머지 전부 완전 일치 — byte-diff는 기대하지
  않는다는 계획의 전제(T1 재현성 FAIL 결론)대로 구조적 일치로 충분히
  판정. **아키텍처 전환(x86→ARM)이 산출물 품질에 영향을 주지 않음을
  확인.** 7단계(크론 이관)는 별도 승인 대기.
- **7단계 완료(2026-08-30, 사용자 확인 후)** — 재확인 결과 `stock-new`는
  6단계 이후 일주일간 완전히 idle(crontab·systemd 둘 다 미등록, 08-21
  하루치 산출물뿐)이었다 — "중복 수집"은 실제로 없었다. 실행 직전 새로
  발견한 블로커: **`stock-new`의 시간대가 `Etc/UTC`**(Ubuntu 24.04 기본값,
  `stock`은 `Asia/Seoul`) — 그대로 옮기면 크론·타이머가 9시간 밀린다.
  `sudo timedatectl set-timezone Asia/Seoul`로 먼저 맞춘 뒤 진행.
  `minute-collect.timer`·`minute-collect.service` 유닛 파일을 `stock`에서
  그대로 복사(무변경) → `stock-new`에서 `daemon-reload`+`enable --now` →
  NEXT가 `Mon 2026-08-31 16:11:38 KST`로 정상 확인. crontab(alive-monitor
  18:10 라인)도 그대로 복사 적용. 이후 `stock`의 타이머는
  `disable --now`(파일은 그대로, `systimers.target.wants`에서만 제거돼
  `enable --now`로 즉시 복원 가능) · crontab은 라인 삭제 대신
  `# MIGRATED-TO-stock-new-2026-08-30` 접두사로 주석 처리(삭제 아님,
  접두사만 지우면 즉시 복원). **오늘(일요일)은 양쪽 다 원래 거래일이
  아니라 컷오버 공백의 실질적 위험이 없었다** — 월요일(08-31) 16:10
  실주행이 이 전환의 첫 실제 검증이다. 범위 밖 확인: 같은 VM에 사는
  `stock.service`(`~/stock`, 메인 스코어링/T1 앱)는 이번 계획 대상이
  아니라 손대지 않았다 — 별도 판단 필요.

## 여유 용량 활용 후보 (전환 완료 이후, 별도 판단)

- 아직 미구현인 분봉 승격 파이프라인(VM → Object Storage → Actions → commit)
  구축 — 1GB에서는 부담스러웠던 작업.
- 청크 제출·동시성 2~4 같은 기존 보수적 설계는 메모리보다 API 예의/안정성
  목적도 있어 여유가 생겼다고 바로 완화할 필요는 없다.
