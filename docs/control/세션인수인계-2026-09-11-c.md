## 1. ★ 주문 만료 정산 — 부분체결이 상태에 갇히던 구멍 (`cc84b04`)

앞 문서 §0③ 이 "실측한 뒤에 고친다"로 남긴 항목. **표본은 이미 사라졌다** —
VM 실측에서 5전략 167포지션이 전부 OPEN 이었다(09-09 의 ENTRY_SUBMITTED 5건은
그 뒤 체결됐다). 그래서 취소된 행의 모양(`rmn_qty`·`rjct_qty`)은 여전히 모른다.

**모르는 채로 고칠 수 있는 방법으로 고쳤다.** 구멍의 원인은 취소행의 모양이
아니라 **경계가 없다는 것**이었다.

```python
# kisVtsClient.py:410
fully_filled = remaining_qty == 0 and filled_qty >= requested_qty and rejected_qty == 0
```

KRX 주문은 당일물이고 장 마감에 잔여가 취소된다. 부분체결로 끝나면 이 조건은
**영영 참이 안 된다.** 그런데 두 분기가 그것만 기다렸다.

```
ENTRY_SUBMITTED   fullyFilled 만 기다림 → 갇히면 그 종목을 영영 못 산다
EXIT_SUBMITTED    같음            → 갇히면 그 포지션을 **영영 못 판다**  ← 더 나쁘다
```

고친 규칙 하나를 양쪽에 같이 넣었다 — `order_date != 오늘이면 그 주문은 끝났다`.

```
매수  체결분 누적 → 목표 채웠으면 OPEN, 아니면 PENDING_ENTRY(남은 수량 재주문)
매도  체결분만 손익 반영 → 남은 수량만 OPEN 복귀(청산 사유는 다음 poll 이 다시 판정)
```

추측하지 않는 자리 둘:
- 취소된 행의 모양을 안 본다. **거래일 경계와 `filledQty` 만** 쓴다(교훈50).
- 체결이 0 이면 `first_fill_date` 를 아예 안 만든다(교훈57). 만료분이 체결됐으면
  그 날짜는 오늘이 아니라 **주문일**이다 — 앞 문서가 남긴 `entry_date` 어긋남의
  일부가 여기서 같이 닫힌다(정상 경로의 어긋남은 그대로 남는다, §4).

★ 당일에는 아무 것도 안 바뀐다 — `order_date == 오늘`이면 옛 경로 그대로다.
만료 판정은 다음 거래일 첫 poll 에서만 난다.

회귀 3건 신설(만료+부분 · 만료+미체결 · 매도 만료). **고치기 전 코드로 되돌리면
셋 다 붉어진다**(교훈61·72 — 통과가 정보를 주는지 먼저 물었다).

★ 부수로 하나 잡았다: `tests/test_paper_engine_poll.py` 의 pending 테스트가
**3주 전 주문일을 seed 한 채 "아직 대기중"을 주장**하고 있었다. 주문일 당일로
`now` 를 넘겨 테스트가 말하는 바를 실제로 재게 했다.

★★ **`ok()` 가 예외를 안 낸다.** strategy-lab 테스트들은 실패를 세기만 하고
`main()` 에서 `exit(1)` 한다 — 그래서 **pytest 로 돌리면 체크가 깨져도 초록이다**
(실제로 이번에 한 번 속았다). 이 파일들은 `python tests/test_*.py` 로 돌린다.

VM(`stock-new`)은 `git pull` 로 반영했다. 되돌리려면 `git revert cc84b04` 후
VM 에서 다시 pull.

## 3. ★ A3c 주식수 staleness — 켜졌고, 고장이 아니다 (`3f0c9eb`)

앞 문서가 "켜진 뒤에 적을 자리를 정한다"로 미뤄둔 항목. **켜졌다** — 19그룹 중
5개(`maxSharesStaleDays` 182~183), 나머지 11개도 174~178이라 곧 따라 켜진다.

원인을 쟀다. `maxSharesStaleDays` 의 최대값은 **항상 A3C 폴백이 만든다** —
KRX 스냅샷 행은 전부 7~8일이다.

```
config/policies/fundamentals.v1.json
  fiscalYearTo      2025
  fiscalYearToRule  현재월 >= 4월이면 (현재연도 - 1)   ← 2026-09 기준 2025. 어긋난 데 없다
```

그래서 A3c 가 볼 수 있는 가장 새 서류는 FY2025 사업보고서(2026-03 접수)다.
FY2026 분기보고서는 `bsns_year=2026` 이라 범위 밖이다.

```
종목별 최신 A3C 레코드 접수월
  2026-03    2,378 / 3,197  (74%)   ← 여기 멈춰 있다. 오늘 177일
  2026-04~08   297
공시 간격 실측 (88,225표본)  p50 92일 · p95 182일 · p99 273일   ← 분기 주기
```

**임계 180 이 처음부터 틀린 값은 아니었다.** 틀어진 것은 수집 범위가 연 1회
리셋된다는 점이다. 그래서 **임계를 안 올렸다** — 올려도 400일 근처에서 같은
자리에 다시 온다. 근거 전문: `docs/operations/a3c-shares-staleness-2026-09.md`.

**닫았다(`f193873`, 사용자 GO)**: `sharesStale` 을 **KRX 출처에만** 건다.
KRX 스냅샷은 매일 갱신되므로(실측 2~8일) 거기서 180일이 나오면 진짜 고장이고,
경고는 그때 처음으로 정보를 준다. A3C 의 나이는 `maxSharesStaleDays` 로 계속
보이고 새 필드 `maxKrxSharesStaleDays` 가 경고가 실제로 재는 값이다.

```
좁히기 전  sharesStale 5/19 (곧 전부 켜질 예정)
좁힌 뒤    sharesStale 0/19 · maxKrx 2~8일 · maxSharesStaleDays 7~183일(그대로)
```

임계 180 은 안 건드렸다. selftest tripwire — 같은 나이를 KRX 로 주면 켜지고
A3C 로 주면 안 켜지되 `maxSharesStaleDays` 는 180을 넘는다(70 → 76건).
로컬 진단 실행 후 `docs/data/` 는 되돌렸다(그 경로 writer 는 Actions 다).

평균수익 net, %p       거래량 없음    거래량 있음    거래량의 기여
  LWTI 없음            A -0.184%     B -0.232%     -0.048%p

## 6.7 ★ 확인하려다 찾은 것 — `shares-snapshot` 이 절반은 타임아웃이다

§3 변경(`sharesStale` 좁히기)이 production 에서도 도는지 보려고
`shares-snapshot` 을 `commit=false` 로 띄웠는데 **30분 타임아웃에 걸렸다.**
내 dispatch 만의 문제가 아니다 — 최근 전량 실행 4회 중 2회가 같은 자리다.

```
09-08  schedule           success     5.2분
09-09  schedule           cancelled  30.3분   ← 타임아웃
09-10  schedule           success    16.1분
09-11  workflow_dispatch  cancelled  30.4분   ← 이번 것
```

로그가 원인을 그대로 말한다.

```
패스 1: 시도 353 · 성공 233 · 실패 120        ← 실패율 34%
2차 패스 대기 600초 (실패 120종목 재시도)
(대기 종료 06:31:22) ... 06:47:23 ##[error]The operation was canceled.
```

즉 **2차 패스가 16분 넘게 돌다 잘렸다.** `build-shares-snapshot.py` 의 주석이
예산을 이렇게 잡아 뒀다:

```python
MAX_PASSES = 2           # 1차 + 재시도 1회
RETRY_PAUSE_SECONDS = 600
# ★ 워크플로 timeout-minutes 가 30 이다. 2패스 = 대기 10분 + 수집 약 5분이라 들어간다.
# 실패분만 돈다 - 80종목이면 한 패스가 16초다
```

**전제가 데이터에 달려 있다.** 80종목·16초를 가정했는데 오늘은 120종목이고
KRX 가 계속 던지니 종목마다 백오프가 붙어 16분을 넘겼다. 예산이 고정이 아니라
**KRX 의 기분에 비례**한다 — 30분 타임아웃이 유일한 정지선이다.

터졌을 때 무슨 일이 나는가:

```
Build snapshot           cancelled
Consumer check (sector-strength)   skipped   ← 그날 sector-strength 가 안 돈다
Commit snapshot          skipped   ← docs/data/shares-snapshot.json 그대로
```

★ 그리고 **아무도 모른다.** conclusion 이 `failure` 가 아니라 `cancelled` 라
'성공→실패' 전이가 아니고, 애초에 `notify-failure` 감시 5개에 이 워크플로가
없다. 분봉 때와 같은 모양이다 — *워크플로 색과 데이터 존재는 다르다.*

완화 요인 하나: `daily-analysis`(07:40 UTC)도 `build-sector-strength.py` 를
`continue-on-error: true` 로 돌린다. 그래서 `sector-strength.json` 은 전날
스냅샷 위에서라도 갱신된다. 타임아웃의 실제 손실은 **그날의 상장주식수**다.

**타임아웃을 올리지 않았다.** 30 → 45 로 밀면 실패율이 더 오른 날 같은 자리에
다시 온다 — 임계를 옮기는 것은 경고를 끄는 일이지 고치는 일이 아니다(§3 에서
`sharesStale` 에 대해 내린 것과 같은 판단). 먼저 물어야 할 것은 **왜 실패율이
23%(09-08 추정) → 34% 로 오르고 있는가**다.

## 7. ★ 타임존 감사 — cron 은 KST 로 못 바꾼다 (`cd7e006`, 사용자 질문)

"워크플로가 UTC 로 된 게 많은데 KST 로 다 맞춰야 하지 않나"는 질문에서 나왔다.

**답의 절반은 "못 바꾼다"다.** GitHub Actions 의 `schedule` 은 UTC 만 받고
타임존 지정 문법이 없다. 지금처럼 UTC 로 쓰고 KST 를 주석으로 병기하는 것이
유일한 방법이다. 절대 규칙 3 이 가리키는 곳은 cron 문법이 아니라 **데이터·
로직의 시각**이다 — 그쪽을 봤다.

```
cron 24줄   KST 주석이 달린 것 전수 검증 — 산수가 전부 맞다
            실제로 빠져 있던 건 3개 파일뿐(intraday-alert 2줄 ·
            supply-demand-a4 · weekly-backtest). 채웠다
```

★ 러너에 `TZ` 설정이 없어 **UTC** 다. 그래서 **UTC 15시 이후**에 도는
워크플로만 날짜가 밀린다 — 대상이 셋뿐이라 전수로 봤다.

| 워크플로 | UTC | 상태 |
|---|---|---|
| `state-expire` | 21 | `expire-states.js` 가 `kstNow()` 로 +9h — 처리됨 |
| `intraday-alert` | 13~21 | `intraday-check.js` 가 UTC 시로 장 개장 판별 — **의도적** |
| `fundamentals-us` | 22 | `dt.date.today()` — **하루 전으로 찍힌다** |

22:00 UTC 는 KST 로 **다음 날 07:00** 이다. `_asOf`·`updatedAt`·`usUpdatedAt`
세 곳을 `today_kst()` 로 바꿨다.

★ **2026-09-02 실행은 우연히 맞았다.** 23:48 UTC 에 시작해 00:14 UTC 에
기록해서 UTC 날짜가 마침 넘어가 있었다. 제때(22:00) 돌면 틀린다 — **달마다
맞았다 틀렸다 하는 라벨**이라 아무도 못 알아챈다.

★★ **전역 `TZ: Asia/Seoul` 은 걸지 않았다.** 한 줄이면 전부 KST 가 되지만
`intraday-check.js` 는 UTC 시로 장 개장을 판별하도록 **명시적으로** 짜여 있어
전역으로 바꾸면 그게 조용히 깨진다. 틀린 한 곳만 고친다.

(`date -u` 사용처 2곳은 커밋 메시지뿐이고, 그 시각엔 UTC 날짜 = KST 날짜다.)


### 7.1 ★★ 그런데 더 큰 게 나왔다 — 예정 시각이 실제 시각이 아니다

shares-snapshot              06:40      +304 +307 +301

CLAUDE.md 가 macro-regime-ui 의 cron 을 "이중 안전망"이라 부른 것이 옳았다.

### 7.2 ★★★ `intraday-alert` 는 사실상 안 돌고 있다

고빈도 cron 은 밀리는 정도가 아니라 **거의 전부 드롭된다.**

```
cron '*/10 0-6 * * 1-5'   한국장 창에서 하루 42회 기대
실측 (2026-09-02 ~ 09-11, 8거래일)   하루 1회        ← 매일 정확히 1회
                                    전체도 하루 5~6회(한국장+미국장 합쳐 96회 기대)
```

8거래일 전부 한국장 창 **1회**다. 실제로 도는 시각은 13:04·13:06·13:09 KST
언저리 — 장중이긴 하다. 즉 **10분마다 감시하는 시스템이 아니라 하루 한 번
찍어보는 시스템**이다. `intraday-check.js` 가 스스로 장 시간을 판별하므로
잘못된 알림이 나가지는 않는다 — 나가야 할 알림이 안 나갈 뿐이다.

GitHub 이 공개 저장소의 고빈도 schedule 을 흘리는 알려진 동작이고, **우리가
cron 으로 고칠 수 있는 문제가 아니다.** 고치려면 트리거를 바꿔야 한다 —
분봉 VM 에 이미 systemd 타이머가 있으므로 거기서 호출하는 것이 자연스럽지만,
**새 VM 유닛은 확인 대상**이다(CLAUDE.md 실행 기준). 미결로 남긴다.
