## 2. GATE-EP-1 재정의 검토 — 보류로 확정

Tier A+B 완료 후 A1b 1,223종목 중 UNKNOWN 975건(79.7%)이 GATE-EP-1(5%)을
크게 초과. exitAtConfirmed가 없는 715종목의 구성을 A2b `_diagnostics.json`
으로 실측: **591종목(48.3%)은 수집 구간(2014~2026) 전체에서 가격이
단 한 행도 없음** — 앵커 자체가 없어 Tier C를 아무리 설계해도 원리적으로
분류 불가능. 122종목은 raw 가격은 수집됐으나 품질 게이트(UNADJUSTED_
CORPORATE_ACTION 107·TRANSIENT_PRICE_SPIKE 15)로 통째 제외(raw 행 자체가
로컬에 없어 재수집 없이는 복구 불가). 2종목은 단순 네트워크 예외.

분모를 "가격 흔적이 있는 A1b"(630=508+122)로 재정의하면 UNKNOWN이
79.7%→60.6%로 낮아지지만 **그래도 12배 초과**(31건까지 낮춰야 통과,
남은 382건의 91.9%를 새로 분류해야 함).

**재정의 자체를 보류로 확정**(사용자 판단, 로컬 데이터만으로) — 가격
흔적 없는 591종목의 **80.2%가 dartModifyDate=2017 배치값 하나에 몰려
있음**(가격 흔적 있는 630종목은 2017~2026에 16.2%로 고르게 분산). Group A
508종목의 실제 exitAtConfirmed가 2014~2026에 고르게 퍼져 있어(2014~2015도
9.4%) 가격 수집이 오래된 폐지도 정상적으로 잡는다는 게 확인됐으므로, 이
몰림은 수집 결함이 아니라 **591종목이 수집 캘린더(2014-01) 이전에 이미
사라진, 훨씬 더 오래된 폐지 종목이라는 뜻**이다. "가격 흔적 있는
630종목만 분모로" 재정의하면 최근 폐지는 남고 오래된 폐지는 조직적으로
빠져 **survivorship bias를 재도입할 위험이 실측 확인됨** — 채택 안 함.

업종 축은 A1b에 필드 자체가 없고 `lib/sectorResolver.js`의 이름패턴
대체(8개 좁은 카테고리)로는 양쪽 다 87~93% 미분류라 결론 근거가 못
됐다 — 연도 신호가 이미 결정적이라 업종 확인용 추가 DART `company.json`
호출(최대 1,223콜)은 하지 않기로 함(사용자 판단).

**부수 발견 — 분류가 다 같은 무게를 갖지 않는다**: `exit.v1.json`의
mode를 보면 MERGED·SPINOFF·UNKNOWN은 전부 exclude(A6 계산 기여 0),
BANKRUPTCY류 4종+VOLUNTARY만 실손실을 반영한다 — Tier A의 MERGED 179건은
GATE 수치는 낮추지만 실질적 편향 보정 기여는 0, 실제로 편향 보정을
작동시키는 건 Tier B가 분류한 69건(5.6%)뿐이다. GATE를 어떻게 재정의
하든 이 사실은 안 바뀐다.

정책 파일(`config/policies/exit.v1.json`·`docs/BF-1.1-백필계약.md`
§5/§6)은 무변경. 세부:
`docs/verification/BF-1.1-GATE-EP-1-재정의-비교.md`.

## 3. A5 파일럿 + exit overlay 설계 — 리스트까지 확정, 구현은 미착수

### 3.1 왜 A5가 GATE-EP-1과 무관한가

`docs/BF-1.1-백필계약.md` §5: "**A5는 EP를 읽지 않는다.**" GATE-EP-1/2는
A6의 Primary 결론만 막는다 — A5(사실 저장)는 exitReason 복원 진행
상태와 무관하게 지금 착수 가능하다는 게 이번 세션의 핵심 재발견. 이전
세션("exitReason 먼저, A5는 나중")의 순서 판단은 A6에만 해당했다.

### 3.2 exit overlay 설계

A5 레코드는 그 시점 A1b의 `exitReason`을 baked-in 사실로 저장(계약
무변경). Tier B/C/D로 분류가 늘어나도 **A5 재계산 없이** 반영할 수
있도록 별도 overlay 파일을 둔다 — 오늘 만든 `build-exit-reason-
overlay*.py`와 같은 패턴을 정식화한 것. 키는 `corp`, 버전은 파일 전체
교체(v1→v2→…, 증분 patch 아님). **A6이 overlay를 어떻게 읽을지는 별도
🔴 결정 — 이번 세션은 안 다뤘다.**

### 3.3 파이프라인 — 재사용 가능한 조각이 대부분

```
(ticker, corp, asOf) 1점 계산   scripts/probe-v7-vertical-slice.js 그대로
                                 (resolve()+score() 이미 검증, 2026-08-21)
가격 조회                       lib/a5/priceSource.js 그대로(오늘 세션 전
                                 신설, findPrice·findCandles 검증됨)
샤드/재개/finalize 골격          scripts/build-fundamentals-a3d.py 패턴

```

**새로 설계해야 하는 건 fwd/fwdStatus 계산 하나뿐**(§5.1·§5.3):
horizon(d20/d60/d120)은 `calendar.tradingDays` 인덱스 오프셋(달력일

`volume>0`(체결일) 조건 하에서만 계산.

### 3.5 Claude/OpenCode 위임 경계 — 두 차례 조정 끝에 확정

```
Claude    scripts/build-a5-pilot.js 먼저 작성·실행(위 전체)
OpenCode  Claude 완료 후 착수, research/strategy-lab/a5-pilot-independent/ 안에서만
```

**독립 재구현(코드를 다시 짬)은 fwd/fwdStatus 하나로 좁혔다** —
`resolve()`·`score()`·`priceSource.js`는 둘 다 읽기 전용 재사용(이미
검증됨, 재구현 낭비). fwd/fwdStatus만 새 로직·우선순위가 있고 조용히
틀리면 210만 레코드 전체를 오염시키는 유일한 부분이라 검증강도가 맞다.

**shard/resume·exitReason bake-in은 독립 재구현 대상에서 뺐다**(사용자
지적으로 축소) — A3/A3b/A3c/A3d에서 이미 검증된 패턴 재사용이라 새로
짜봐야 잡을 버그가 거의 없다. 대신 Claude 스크립트를 OpenCode가 그대로
재실행+강제중단→재개 시나리오 관찰로 충분.

**overlay join(A6 몫)은 A5 pilot 범위 밖** — OpenCode 지시서에 이 경계를
명시해야 한다(안 그러면 "exitReason 처리 비교"라는 말만 보고 스코프가
슬금슬금 늘어날 위험).

차이가 나오면 자동으로 어느 쪽이 맞다고 안 고른다(`AGENTS.md` §4 그대로,
새 규칙 아님) — Claude와 사용자가 원인 판정.

세부: `docs/A5-파일럿-exit-overlay-설계안.md`(§1~§5.3 전부, 이 문서가

  으로만 3커밋 앞서 있고 파일 겹침 없음(실측 확인) — push 시 안전하게
  rebase 가능하나, 그래도 push 자체는 매번 사전 확인 대상이다(등급과
  무관, 프로젝트 규칙).

  썼다 — 로컬에 키가 있다는 사실은 전전 세션(-b)이 이미 확인해 뒀다.
- 새로 만든 스크립트(`scripts/build-exit-reason-overlay-tierb.py`)는
