## 1. resume이 이월 조각을 재검증하지 않던 버그 (🔴 승인 후 수정)

**발견 경위**: `세션인수인계-2026-08-30-d.md`가 남긴 "월요일(08-31) 16:10 KST
`stock-new` 첫 실주행 확인"을 SSH로 직접 확인하다가 발견했다. 16:10 실행이
432980 09:02 `openOutOfRange` 위반 1건으로 FAIL했는데, 같은 날 17:40 재실행
(resume)이 그 위반을 재검증 없이 그대로 PASS로 승격시켰다.

**원인**: `scripts/collect-minute-kis.py`의 `run_day()`에서 이미 완료(`OK`)로
기록된 티커는 resume 시 재조회되지 않는다 — 그 티커가 남긴 이월(carried)
스테이징 조각은 `parts`·`row_count`에는 더해지지만 `validate_rows()`는 새로
받은 배치(`flush()`)에만 걸려 있었다.

**수정**(커밋 `2088e47`): `revalidate_carried()` 신설 — 이월 조각을 parquet에서
다시 읽어 재검증한다. 네트워크 재호출은 없다(`todo` 선택 로직 무변경). 회귀
22b가 432980 사례를 그대로 fixture화 — resume이 재호출 0건이면서도 이월 위반을
재검증해 FAIL을 유지하는지 확인한다. 전체 118개 회귀 통과.

**위반 자체(432980 09:02)**는 별개 관측으로 `docs/operations/minute-실측기록.md`
에 남겼다(커밋 `4fc4d27`) — 초저유동성 종목에서 KIS의 `open`이 그 1분의 실제
체결가가 아니라 직전 체결가를 캐리오버한 것으로 보이는 단발성 사례. 지금은 면제
규칙을 넓히지 않고, 향후 누적 시 종목·유동성·시간대·HALT여부·발생패턴으로
집계해 근거를 만들기로 했다. 부수로 스테일 테스트 2건(정책버전 MN-1.1→1.2 반영
누락 — 실은 08-18에 사용자가 이미 승인한 정식 정책 승격이었다)도 같이 정정.

## 2. 분봉 manifest OCI 승격 파이프라인 (신규 구현 + 실전 검증 완료)

### 설계

```
VM(Instance Principal 인증)
  → OCI Object Storage(stock-minute-manifest, ap-osaka-1, ns ax4zjhxnmgyz)
  → GitHub Actions(API Key 인증, sha256·행수 대조만 — 인수 조건 재계산 안 함)
  → GitHub main 커밋(data/backfill/minute/manifest/{date}.json만, raw는 안 올림)
```

Actions가 인수 조건을 다시 계산하지 않는 이유: 원본 KIS 응답을 본 적이 없어 잴
수단이 없다(교훈50). 대신 "OCI에 올라온 바이트가 manifest가 말하는 그대로인가"
(조각별·결합 sha256, 행 수)만 본다 — 어긋나면 그 날짜는 승격하지 않는다(교훈43).

### 신규 파일

```
scripts/oci-object-storage.py        VM·Actions 공용 OCI transport (실제+Fake)
scripts/upload-minute-oci.py         VM → OCI. 조각 먼저·manifest 마지막 순서
scripts/test-upload-minute-oci.py    13케이스, 네트워크 없음
scripts/promote-minute-manifest.py   OCI → 검증 → 저장소 커밋
scripts/test-promote-minute-manifest.py   10케이스, 네트워크 없음
.github/workflows/promote-minute-manifest.yml   평일 19:30 KST + workflow_dispatch
deploy/minute-oci-upload.service/.timer         VM systemd 유닛
deploy/install-oci-upload.sh         install-vm.sh와 분리한 별도 설치 스크립트
```

IAM은 OVERWRITE·DELETE를 의도적으로 안 준다(2026-08-30 확정 유지) — 그래서
업로드는 "재시도 가능"이지 "덮어쓰기 가능"이 아니다. 이미 있는 조각은 건너뛴다.

### 실전 검증 (전부 완료)

1. **OCI 콘솔 IAM**(사용자가 직접 생성): Group `github-actions-readers` ·
   User `github-actions-minute-reader` · Policy `github-actions-minute-reader-
   policy`(`Allow group ... to read objects ... where target.bucket.name=
   'stock-minute-manifest'`) · API Key. GitHub secrets 5개 등록
   (`OCI_MINUTE_READ_USER_OCID`·`FINGERPRINT`·`PRIVATE_KEY`, `OCI_TENANCY_OCID`,
   `OCI_REGION`). `OCI_NAMESPACE`는 민감정보가 아니라 워크플로에 리터럴로
   고정(커밋 `6c7325a`) — 처음에 secret으로 설계했다가 사용자가 실제 등록
   과정에서 누락된 걸 계기로 정정했다.
2. **인증 테스트**(run `33407746398`) — 버킷이 비어 있을 때 실행, "승격할 것
   없다"로 정상 종료. OCI API Key 인증·Policy 스코프 정상 확인.
3. **실제 업로드 + round-trip**(run `33408137682`) — `stock-new`에서
   2026-08-31 하루를 실제로 OCI에 업로드(`upload-minute-oci.py`, 13조각+
   manifest), Actions가 재검증해 커밋 `94b9e55`.
4. **밀린 날짜 일괄**(run `33408401163`) — 08-21·27·28도 업로드+승격,
   커밋 `c42a35d`. 08-29·08-30은 주말이라 애초에 로컬 manifest가 없다(정상).
5. **systemd timer 설치**(커밋 `f0abedd`) — `stock-new`에
   `minute-oci-upload.timer` 활성화, 매일 18:00 KST(17:40 수집 뒤) 자동
   실행. `systemctl start`로 수동 1회 트리거해 유닛 배선(EnvironmentFile·
   MemoryMax·권한) 자체도 검증 완료(`status=0/SUCCESS`).

`data/backfill/minute/manifest/`가 이 프로젝트 역사상 처음 실제 파일(2026-08-21·
27·28·31 4개)을 갖게 됐다.
