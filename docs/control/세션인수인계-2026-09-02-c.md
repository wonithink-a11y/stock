## 1. A5 10년 백필 — supplyDemand 축 연결 실제 완료 (버그 2건 발견·수정)

### 배경
앞선 세션이 "코드는 다 짰고 로컬 10종목 검증도 통과했으나, 전체 3,801종목
GH Actions 재백필은 아직 트리거 안 했다"고 남긴 상태를 이어받아 실행했다.

### 트리거 1차 — 8샤드 전량 실패
`ERR_STRING_TOO_LONG`. `scripts/build-a5-backfill.js`의 `readJsonl()`가
연도별 jsonl.gz를 gunzip한 뒤 `.toString('utf8')`로 통째로 하나의 JS
문자열을 만드는데, A4(전 시장 일별 수급, 540만행)의 한 해 분량이 Node의
최대 문자열 길이(0x1fffffe8 ≈ 512MB)를 넘는 해가 있었다. A3/A3b/A3c/A3d는
법인 수(3,801)만큼만 있어 이 한계를 넘은 적이 없었는데, A4는 전 종목×전
거래일이라 규모가 다르다.

**수정**: Buffer 상태에서 줄 단위로만 `toString()`하도록 `readJsonl()`을
고치고, 결과를 relPath로 캐시(A3 계열은 파일이 작아 무해하고, corp마다
반복 재압축해제하던 비효율도 없앤다). 커밋 `39fa6ef`.

### 트리거 2차 — 로컬 재현 시 OOM
수정한 `readJsonl()`을 캐시 그대로 A4에 적용하니, 이번엔 로컬 재현
(`--universeLimit 10`)에서도 "JavaScript heap out of memory"가 났다.
캐시가 A4 전체(2,578종목분, 540만행)를 통째로 붙잡고 있었기 때문 — 샤드
하나는 담당 종목(약 475개)만 있으면 되는데 나머지 종목의 레코드까지
메모리에 다 올라간 것.

**수정**: `findByCorpAcrossYears`와 달리 A4 전용으로 `buildA4Index()`를
새로 만들어, 샤드 시작 시 담당 ticker 집합으로 한 번만 필터링해 인덱싱
— 안 쓰는 종목의 레코드는 파싱 직후 버려 메모리에 안 쌓인다. 로컬
재현(10종목) 통과 확인 + `supplyDemand` 필드에 실제 값(예: 17.2) 채워짐
확인 + 회귀 78건 전체 통과. (39fa6ef에 같이 포함)

### 트리거 3차 — 8샤드 전량 성공, finalize만 실패
manifest 작성 단계가 `Error: A5의 필수 상류가 upstream에 없다: A4`로
실패. `lib/backfillManifest.js`의 `REQUIRED_UPSTREAM['A5']`는 이미 A4를
요구하도록 (앞선 세션이) 고쳐뒀는데, `scores-a5.yml`의 `write-manifest.js`
호출부 `--upstream` 목록은 옛 것(A4 없음) 그대로였다 — manifest 계약이
설계대로 정확히 거부한 것(계산 자체는 8샤드 전부 성공, 1,254,759행 정상
산출). 커밋 `703b67e`로 `--upstream`에 A4 추가.

### 트리거 4차 — 전 구간 성공
run [33598390715](https://github.com/wonithink-a11y/stock/actions/runs/33598390715).
실측: 레코드 1,254,759행 · corpsDone 3,801/3,801 · corpsIncomplete 0 ·
assembleFailed 0 · validateViolations 0 · exitReasonUnknown 95,745
(기존 2026-08-24 완료 기록과 정확히 일치 — supplyDemand만 새로 채워짐을

## 2. ETF별 분배금(배당) 현황 — 신규 기능

### 배경
사용자가 "ETF 별 배당금 상황도 알수 있을까?"라고 질문. 조사부터 시작했다.

### 조사 경과
- **pykrx**: `dir(stock)`에 분배금 관련 함수 없음 — 기존 research 조사
  (`research/strategy-lab/findings/etp-data-axis-build-feasibility-2026-08.md`)
  가 이미 "NOT AVAILABLE"로 확인해 둔 것을 재확인만 함.
- **KRX Open API**(data-dbg.krx.co.kr, 이 프로젝트가 이미 쓰는 AUTH_KEY
  방식): 공식 서비스 목록 페이지(openapi.krx.co.kr)를 직접 열어 전체
  카탈로그를 확인 — 지수·주식·증권상품(ETF/ETN/ELW 일별매매정보만)·채권·
  파생상품·일반상품·ESG, **분배금 엔드포인트 자체가 없다**(공식 1차
  출처로 확정).
- **KRX 정보데이터시스템 구버전 통계**(data.krx.co.kr bldAttendant,
  `fetch_short_credit.py`가 이미 쓰는 방식): 새 "KRX Data Marketplace"
  UI로 개편되면서 메뉴 딥링크가 전부 로그인 페이지로 리다이렉트됨(실측) —
  이 경로는 이제 로그인 없이 못 연다.
- **FunETF**(funetf.co.kr, 삼성자산운용이 운영하는 공개 ETF 비교 포털 —
  전체 운용사 ETF를 다룬다는 점에서 삼성 자체 상품 페이지와 다름): 페이지
  HTML에서 `/api/public/product/etf/distributionCheck/list` 엔드포인트를
  발견. 실측 결과 **로그인 불요** — 페이지를 한 번 GET하면 세션 쿠키와
  CSRF 토큰(`<meta name="_csrf">`)이 자동 발급되고, 그걸로 바로 API를
  호출할 수 있다(표준 스프링 시큐리티 CSRF — 인증이 아니라 자기 사이트
  폼 위조 방지 목적). `robots.txt`도 이 경로를 막지 않음(`Disallow`는
  개인정보·포트폴리오 관련 경로만). 종목코드는 API의 `sotCd` 필드가 이
  프로젝트의 6자리 ticker와 이미 같은 값이라 별도 매핑이 필요 없다(실측
  확인, 예: `sotCd: "069500"` = KODEX 200).

### 실측 데이터
`size=1000` 한 번의 GET으로 전체 955개 ETF(전체 유니버스 1,167개의 약
82%)의 최근 분배 이력을 받았다 — Spring Data Page 표준 페이지네이션이라
페이징도 그대로 동작 확인. 필드: `divRt`(최근회 분배율%) · `divCnt`(연간
분배횟수) · `divRateYear`(연환산 분배율%, 단리) · `divRateYearMult`(연환산,
복리) · `divAmtYear`(연간 분배금 합계, 원) · `divMonthYn`(월분배 여부) ·
`annYmd`/`payYmd`/`realPayYmd`(공시일/기준일/지급일).

### 구현
- `scripts/build-etf-distributions.py` 신설 — 세션+CSRF 발급 → API 호출 →
  ticker 키 정규화된 `docs/data/etf-distributions.json` 생성. `--selftest`
  포함(필드 매핑·결측 None 처리 검증). 순수 stdlib(`urllib.request`·
  `http.cookiejar`), 신규 의존성 없음.
- `.github/workflows/build-etf-price-history.yml`에 단계 추가
  (`continue-on-error: true` — FunETF 사이트 구조가 바뀌어 이 단계가
  깨져도 ETF 가격/수익률 갱신(핵심 파이프라인)은 막히면 안 됨).
- `docs/index.html` ETF 탭에 "연분배율"·"분배횟수" 정렬 가능 컬럼 추가.
  분배 이력 없는 ETF(주로 국내주식 액티브·성장형)는 결측이 아니라 무배당
  관측 사실이므로 `-`로 정직하게 표시(절대 규칙 1, A3b의 배당 세 갈래와
  동형 원칙).

### 검증
로컬 `python scripts/build-etf-distributions.py --selftest` 통과 → 실제
네트워크 호출로 955건 확인(파일 바이트 직접 확인으로 한글 인코딩 정상,
터미널에 찍힌 깨진 글자는 이 환경 콘솔의 cp949 표시 문제일 뿐 — 기존에도
반복 관측된 것). `stock-dashboard`(`.claude/launch.json`, 포트 8733)로
브라우저 실측 — 연분배율 내림차순 정렬 시 커버드콜 ETF들이 연 +20~28%대로
상단에 몰리는 것 확인(방향성 타당), "12회(월)" 같은 라벨도 정상 표시.

  문자열 길이·OOM·manifest upstream 누락)는 원인이 명확해 오퍼스 위임
  기준(조용히 틀리고 되돌릴 수 없는 판단)에 해당하지 않는다고 판단

  운영 주체가 다르다. 사이트 구조가 바뀌면 `build-etf-distributions.py`가
  조용히 빈 응답을 낼 수 있어 `continue-on-error`로 막아뒀지만, 실패가
  누적되면 그때 재조사 필요(원인은 로그에 남는다 — `Fetch ETF
  distributions (FunETF)` 스텝의 실패 여부로 바로 보임)
- **A5 10년 백필(`data/backfill/scores/`)은 이제 5개 축(재무·기술·수급·
  주주환원·밸류에이션) 전부 연결된 상태다** — supplyDemand가 마지막
  퍼즐이었다. 이 데이터로 하는 추가 분석(예: 수급 축 자체의 IC 분해)은
  다음 세션이 판단할 사안
- **저장소 루트 잡동사니**: 지난 세션에서 디버그 스크래치 파일 15개는

  `HANDOVER_2026-08-17.md` 더미는 여전히 미정리 상태 — 지울 것/남길 것
  구분은 여전히 다음 세션(또는 사용자 판단) 대상
