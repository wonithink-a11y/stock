# 멀티에이전트 파이프라인 — 현황 조사 (Fable 설계 세션 입력)

작성 2026-11-14 (Sonnet, 코드 읽기 전용 조사 — 코드·정책 변경 없음). 대상: `Fable 5.2 프로젝트별 작업 지시서 (11/15~11/17)` 의 stock 절.
목적: Fable 세션이 코드를 다시 읽는 데 한도를 쓰지 않도록, **5개 구성 요소가 지금 저장소의 어디에 대응하는지·지시서의 전제가 맞는지·무엇이 비었는지**를 사실로 모아 둔다.
표시: ✔ 이 세션에서 파일을 읽어 확인 · △ 일부만 확인 · ? 확인 필요(읽지 않았거나 외부 사실).

## 0. 한 장 요약

1. **처음부터 짓는 일이 아니다.** 5개 중 2번(스코어링)·4번(위험·실행)·5번(사후 평가)은 상당 부분 이미 있고, 비어 있는 것은 **3번(논리·반증 에이전트)** 과 **팀 사이를 잇는 계약(스키마·이벤트 로그)** 이다.
2. **지시서의 "기존 event-sourced 상태 모델"은 공시 위험 상태 전용이다.** `reduce` 는 종목별 `riskStates`/`activeMeta`(TTL)만 다룬다. 에이전트 신호·주문 계획·승인을 `reduce` 에 그대로 넣을 수 없다 → 별도 이벤트 로그 또는 두 번째 reducer 가 필요하다 (§3).
3. **지시서의 인프라 전제는 낡았다.** "GitHub Actions + Oracle Cloud(서울)" 중 Oracle 은 2026-11-13 영구 종료. 지금은 GitHub Actions + 이 PC + Cloudflare Workers(§5).
4. **비용·규칙 충돌 4곳**: 런타임 LLM(유료 API) = 절대 규칙 9 · 3번 출력을 점수에 반영 = 절대 규칙 1 · 승인 단계 = 현재 자동매매에 없음 · 실주문 = Claude 가 켜지 않음 (§5).
5. 이 저장소의 연구 결과는 **대부분 REJECT, 통과분도 얇다**(§6). 파이프라인의 가치는 수익 약속이 아니라 "어느 근거가 맞았는지 알 수 있게 하는 기록"(5번)에 있다.

## 3. 상태 모델의 정확한 범위 (설계 입력)

`reduce(prevState, event, stateMapPolicy)` (✔ 86줄):
- 입력 이벤트 필수: `type`·`occurredAt`·`sortKey`. 상태 필수: `riskStates`(배열)·`activeMeta`(배열). 정책 필수: `events`.
- 상태 모양(`ST-1.0`): `ticker`·`listingStatus`·`tradingState`·`riskStates`·`activeMeta[{code, activatedAt, ttlDays}]`·`lastSortKey`·`lastEventId`·`updatedAt`.
- 멱등: `event.sortKey <= prevState.lastSortKey` 이면 무시(REDUCE-006, 역순 방어 + 재실행 안전). 미매핑 타입은 상태 불변·커서만 전진. 같은 위험이 이미 활성이면 `activatedAt` 보존(REDUCE-007, TTL 재설정 금지). 시간 경과(TTL 만료)는 `stateExpirer.js` 만 한다(`state-expire.yml`).
- 저장: `lib/stateStore.js` → `data/state/{ticker}.json`(현재 상태) + `data/state-history/{연도}/{ticker}.jsonl`(append-only).
- 배선: `fetch-disclosures-kr.js` 가 `buildEvents → reduce → putState/appendHistory`.
**의미**: 이 모델은 "종목이 지금 어떤 공시 위험 상태에 있는가"이지 "어떤 신호가 났고 승인됐고 체결됐는가"가 아니다.

**확장 선택지(Fable 이 정할 것)**
- A. **별도 이벤트 로그** — 신호·논리·반증·승인·주문계획·결과를 `agent-events/{연도}/{종목}.jsonl` 로 append-only 하고, 기존 `reduce`(위험 상태)는 손대지 않는다. 장점: 기존 회귀·골든셋 무영향. 단점: 두 상태 모델.
- B. **두 번째 reducer** — 같은 `sortKey`·멱등 규약을 따르는 `signalReducer`(신호 수명주기 상태). 기존 `reduce` 와 계약 모양을 맞추되 코드는 분리.
- C. 기존 `reduce` 의 `stateMapPolicy` 규칙 형태를 일반화 — **비권장**(검증된 DC-1.3·골든셋·회귀를 건드리고, 🔴 정책 변경 경계).
- 어느 쪽이든 `sortKey` 규약이 필요하다: DART 는 `{접수일}:{rcept_no}:{seq}`. 에이전트 이벤트는 같은 날 여러 팀이 쓰므로 `{발생시각}:{팀}:{순번}` 같은 비교 가능한 키를 정해야 한다(? 설계 항목).

## 4. 팀 사이를 잇는 현재 흐름 (있는 연결 / 없는 연결)

```
[공시·뉴스·수급 수집] ──✔──> docs/data/*.json , data/state(위험 상태)
        │
        ├──✔──> [스코어링] latest-v2 / rank-h5 (후보) ──✔──> [종목 카드 stockcard: 규칙 계산 진입·손절·목표]
        │                                                          │
        │                                              사용자가 웹에서 계획 카드 입력 (= 현재의 "승인")
        │                                                          ▼
        │                                            [autotrader: 위험 관문 → 주문(dry-run 기본)] ──> ledger.jsonl
        │                                                          │
        └──(없음)──> [논리·반증 LLM] ─────────(연결 없음)──────────┘
                                     [평가] 추천 기록·R 배수·forward 그림자  ← 신호 근거별 귀속은 없음
```
- 없는 연결: ① 후보 → 논리·반증 → 신뢰도 ② 신호·근거를 공통 스키마로 쓰는 이벤트 로그 ③ 승인 요청/응답 이벤트 ④ 논리 훼손 → 매도 점검 ⑤ 평가 → 각 팀 개선 환류.
- 승인(4): 지금 승인은 "사용자가 웹에서 계획을 만든다"이다. 지시서의 "주문 계획이 나오고 사람이 승인"은 **신호가 계획 초안을 만들고 사용자가 확정**하는 흐름으로 바뀌어야 하며, 그 확정 이벤트가 곧 승인 로그가 된다 — `plans.py` 의 파일 소유 규칙(웹만 plans.json 에 씀)을 지켜야 한다.

## 6. 검증 기준 재료 (VALIDATION.md 입력)

- **이미 있는 규율**: 사전등록(결과 전 판정 기준 고정) · 코드 동결 · TRAIN/VALID/TEST · 시기 세 칸 · 비용은 시장별로 사전 고정(KR 연속 ≈33.5bp, 단일가 23.54bp, ETF ≈5bp 등) · 같은 표본 재판정 금지 · 통과해도 forward 확인 전 운용 근거 아님. 목록은 `research/strategy-lab/findings/INDEX.md`(자동 생성).
- **결과의 분포(2026-11-14 기준)**: 레지스트리 775건 중 REJECT 186 · INFORMATION 20 · ECONOMIC 5 · ROBUST 6 · KEEP 14 등. 통과분의 대표: 바이낸스 신규 상장 7일 약세(꼬리 위험·forward 미확인), 한국 정적 VI 숏(차입 미확인), 결합 순위 모델(비용 뒤 이익 얇음, h1 TEST 33.5bp 에서 약 +4bp). **모의 슬리브 REJECT 라도 존치** 같은 선례가 있다.
- **LLM 단계에 쓸 수 있는 선례**: 공시 해독은 "인용 검증을 코드가 한다"로 환각을 막는다. 월간 예측은 사전등록 + 등록일 = 오늘 + 중간 성과 비열람. 반증 에이전트의 가치를 재려면 같은 후보에 대해 **반증 있음/없음 두 갈래를 사전등록하고 forward 로 비교**해야 한다(? 설계 항목).
- **한도**: 계획 카드는 종료 30건 전에는 기대값을 판정에 안 쓴다. 월간 예측 판정은 2029-10-20 이후. 즉 **검증 가능한 표본이 쌓이는 데 수 개월~수 년**이 걸린다는 점을 ROADMAP 에 반영해야 한다.
