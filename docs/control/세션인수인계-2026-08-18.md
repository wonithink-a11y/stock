## 2. pykrx 조사 핵심 결론 (문서화 안 된 부분 요약)

- pykrx는 KRX 공식 Open API(`openapi.krx.co.kr`, 발급키+쿼터)를 쓰지 않는다.
  `data.krx.co.kr`(정보데이터시스템 웹사이트)의 내부 AJAX 엔드포인트
  (`POST .../getJsonData.cmd`, `bld` 파라미터로 리포트 구분)를 그대로
  호출하는 스크레이핑 라이브러리다.
- 2026년 초부터 이 웹사이트가 로그인을 요구하도록 바뀌었고(pykrx PR #282
  배경 설명), pykrx는 `KRX_ID`/`KRX_PW`(일반 회원 로그인)로 세션 쿠키를
  받아 우회한다 — **공식 API 신청·발급키·쿼터와 무관**하다. 문서화된
  호출 한도도 없다(pykrx 자체의 `time.sleep(1)`이 유일한 자율 제한).
- 무자격 실측(`pykrx==1.2.8`): 개별종목 OHLCV(단일종목×기간)만 3/3 성공,
  나머지(시가총액·수급·공매도·외국인보유·PER/PBR·지수·업종분류)는
  전부 실패/빈 결과.
- 이 프로젝트는 이미 A4·`market-flows.yml`용 실계정을 GitHub Secrets에
  갖고 있고, 그 계정으로 수급 경로는 검증됐다(§4~§5). 다른 리포트(공매도·
  외국인보유·지수·업종분류)는 로그인 계정으로 재확인한 적이 없다 —
  "된다"고 단정하지 않는다.
- 상장폐지 종목 목록(`상폐종목검색`)은 로그인 없이도 되지만 **날짜가 없는
  스냅샷**이라 A1b(exitAt 확정치, KIS 소스)보다 열등 — 대체할 이유 없음.
- 결론: production PRIMARY 소스로 승격하지 않는다(비공식 스크레이핑,
  정책이 계속 바뀜, SLA 없음). 연구/백필 원자료 수집 경로로는 이미
  A4처럼 검증된 채로 쓰인다.

코드 문제가 아니라 그날의 반복 시도 누적으로 보인다 — "한 번에 하려다
문제"라는 사용자의 직관은 절반만 맞았다(OOM은 맞음, 마지막 실패는 아님).

## 4. 워크플로 수정 — `sourceRunId` (커밋 `af4cd25`→push 후 `1ca9832`)

`.github/workflows/supply-demand-a4.yml`에 선택 입력 `sourceRunId` 추가.
비우면 기존대로(`collect`→`finalize`). 값을 주면:

- `collect` 잡 전체를 스킵(`if: inputs.sourceRunId == ''`)
- `finalize`는 `collect`가 스킵돼도 진행(`if: always() && (needs.collect.result
  == 'success' || needs.collect.result == 'skipped')`)
- `actions/download-artifact@v4`가 `run-id: sourceRunId`로 **다른 run의
  아티팩트**를 받는다 — 이때 API 조회가 필요해 `permissions.actions: read`도
  추가(빠뜨리면 403으로 조용히 실패했을 부분, 실행 전에 발견해 고침)

15:47 run(`32043379133`)의 샤드 아티팩트 16개는 그대로 살아있었다(retention
1일, 만료 2026-08-18 17:34~17:52 UTC였음 — 이번 실행으로 이미 소비됐으니
재확인 불필요). `f8a893d`(OOM 수정)는 `run_finalize`의 검증 로직만 스트리밍
방식으로 바꿨고 샤드 파일 포맷(`shard-N.jsonl`)은 안 바꿔서 옛 샤드와
호환됐다.
