# LAB-7 — 발행주식수 소스 정찰 결과 (2026-08-12)

```
★ 이것은 정찰이다. 수집·백필·코드·계약·registry·criteria·policy 어느 것도
  건드리지 않았다. DART OpenAPI 공개 문서(opendart.fss.or.kr)를 WebFetch로
  읽은 결과다 — 실제 API 호출(DART_API_KEY 필요)은 하지 않았다. 따라서
  응답 필드 실측이 아니라 "문서가 뭐라고 말하는가"다. 착수하면 실제 응답으로
  한 번 더 확인해야 한다(LAB-7 원 설계서의 한계 그대로).
```

## 배경 — 왜 이 정찰을 하는가

A5-3 부분 구현(peg) 중 A2a(수정주가) ↔ A3b(원본 EPS)의 조정 기준 불일치를
실측으로 발견했다(005930/2016-04-08, per=0.197로 비정상). 임의로 배율을
추정하지 않고, 근본 해결에 필요한 원자료가 실제로 확보 가능한지만 확인한다.

## 확보 가능한 원자료

DART OpenAPI "정기보고서 주요정보"(DS002) 카테고리에 관련 API 둘이 있다.

### ① 주식의 총수 현황 (`stockTotqySttus`, apiId=2020002)

```
기본 필드   rcept_no · corp_cls · corp_code · corp_name · stlm_dt(결산기준일)
핵심 필드   istc_totqy (발행주식의 총수) ← 그 시점 실제 유통 주식 수
           isu_stock_totqy · now_to_isu_stock_totqy · tesstk_co(자기주식수) ·
           distb_stock_co(유통주식수)
           감소 사유 상세: redc(감자)·profit_incnr(이익소각)·
           rdmstk_repy(상환주식상환)·etc(기타)
조회 단위   사업연도 + 보고서코드(분기/반기/3분기/사업보고서) — 연 4회 스냅샷
액면분할·무상증자 사유 필드   없음 — 증가 원인은 구분 안 됨. 감소 사유만 있다
```

### ② 증자(감자) 현황 (`irdsSttus`, apiId=2019004)

```
기본 필드   rcept_no · corp_cls · corp_code · corp_name · stlm_dt
핵심 필드   isu_dcrs_de(주식발행 감소일자) · isu_dcrs_stle(발행 감소 형태) ·
           isu_dcrs_stock_knd · isu_dcrs_qy(수량) ·
           isu_dcrs_mstvdv_fval_amount(주당 액면가액) ·
           isu_dcrs_mstvdv_amount(주당 가액)
형태 구분   "발행 감소 형태" 필드가 있어 증자·감자 종류는 구분되는 것으로
           보이나, ★ 순수 액면분할(자본금 불변, 액면가만 재분할)이 이
           엔티티의 "형태" 목록에 명시적으로 포함되는지는 문서에서
           확인하지 못했다 — 미확인으로 남긴다
비율/배수 필드   없음. isu_dcrs_qy(변경 수량)만 있고 "몇 대 몇"으로 직접
                주지 않는다 — ①의 istc_totqy 전후값과 대조해야 배수를 얻는다
```

## PIT 가능 여부 — 가능

두 API 모두 `rcept_no`(접수번호)와 `corp_code`를 갖고 있다. 이건 A3/A3b가 이미
쓰고 있는 바로 그 PIT 키다 — `availableFrom = rcept_no 앞 8자리`, `pit.selectAsOf()`가
그대로 적용된다. 새 PIT 로직을 만들 필요가 없다.

①(주식의 총수 현황)은 분기 단위 스냅샷이라 A3b(연 1회)보다 촘촘하다. BF-1.1
§2가 미해결로 남겼던 질문("연도 말 스냅샷으로 충분한가, 바뀐 시점을 알아야
하는가")에 대한 답이 여기서 나온다 — **분기 스냅샷 + PIT 선택으로 충분하다.**
기중에 주식 수가 바뀌어도 다음 분기 보고서의 `rcept_no` 시점부터 "알려진 사실"이
되고, 그 이전엔 이전 분기 값이 선택된다 — A3/A3b의 정정공시 처리(교훈47)와
완전히 같은 패턴이라 새로 설계할 게 없다.

## 기존 데이터 재사용 가능 여부 — 재사용 불가, 새 수집 필요

`data/backfill/fundamentals/a3/`·`a3b/` 어디에도 `istc_totqy`나 그와 유사한
발행주식수 필드가 없다(스키마 실측, 이전 세션에서 확인). A3가 쓰는
"단일회사 주요계정"(재무제표 계정) 엔드포인트에는 애초에 이 정보가 없다 —
재무제표 계정과 주식총수현황은 DART에서 별도 공시다. **A3/A3b 재사용으로는
안 되고, 새 엔드포인트 호출이 필요하다.**

## 추가 계약 변경 필요 여부 — 필요하다

새 DART 엔드포인트(①, 필요시 ②)를 호출하는 건 지금 없는 수집 단계다. BF-1.1
§2가 이미 이걸 "A3c"로 이름 붙여 예정해뒀지만(`stockTotqySttus` stage), 실제
착수는 안 됐다. 새 수집 = 새 계약(스키마·인수조건·manifest)이라 🔴 결정이다.

## A3c(①) vs LAB-7 원안(②) 비교

```
                    ① 주식의 총수 현황(A3c안)      ② 증자(감자) 현황
필요한 것            istc_totqy 시계열만            형태 분류 + 시행일 + 배수 역산
분할 종류 구분 필요    불필요 — 실제 수량만 보면 됨    필요 — "이게 액면분할인가"를
                                                  판정해야 하는데 이 API의 "형태"
                                                  목록에 순수 액면분할이 있는지
                                                  자체가 미확인

                    istc_totqy) — EPS 원본을        발견된 배수로 사후 보정
                    아예 안 쓴다

                    같이 열린다

                    kr.js 패턴 그대로 확장          형태 분류 검증 필요
```

**①이 더 안전하다고 판단한다.** 사유를 분류하지 않고 실제 수량만 추적하므로
"이게 액면분할이 맞나"를 오판할 위험이 구조적으로 없다 — 어떤 이유로든 주식
수가 바뀌면 그 사실이 그대로 분모에 반영된다. ②는 "형태" 필드가 액면분할을
어떻게 표기하는지 실제 응답을 봐야 확정되는 미확인 지점이 있어 그 자체가
추가 리스크다.

## 남은 미확인

```
- WebFetch는 API 문서를 읽은 것이지 실제 응답을 받은 게 아니다.
  실제 착수 시 DART_API_KEY로 최소 1개 법인 테스트 호출이 선행돼야 한다
  (LAB-7 원 설계서의 경고 그대로 — "확정이 아니라 사전 정보")
- ②의 "발행 감소 형태" 필드가 순수 액면분할을 어떻게 표기하는지 미확인
- ①의 분기 스냅샷이 실제로 얼마나 자주 결측(013 조회된 데이터 없음)인지 미측정
```
