# VALIDATION — 파이프라인 통과 기준 (설계, 2026-11-15)

짝 문서: `docs/ARCHITECTURE.md` · `docs/AGENT_SPEC.md` · `docs/ROADMAP.md`.
이 문서는 **기준의 설계**다. 숫자가 효력을 갖는 것은 §3 이 `preregistered-research` 스킬로 사전등록 파일이 되고 사용자 GO 를 받은 뒤다(표본 정의·판정 기준 = 🔴).
규율은 새로 만들지 않는다 — 이 저장소의 것(사전등록 → 코드 동결 → 판정 1회 → 같은 표본 재판정 금지)을 그대로 쓴다.

## 0. 기대치

- 이 저장소의 연구는 대부분 REJECT 다(레지스트리 775건 중 REJECT 186 · INFORMATION 20 · ECONOMIC 5 · ROBUST 6, 현황조사 §6). **아래 판정들의 가장 그럴듯한 결과는 INCONCLUSIVE 또는 REJECT** 다.
- 그 경우 S3(LLM 주석)를 끄고 S2·S4·S5(코드·사람·기록)만 남긴다. 그것이 실패가 아니라 설계된 출구다.
- **LLM 토론·주석의 그럴듯함은 채택 근거가 아니다.** 근거는 forward 숫자뿐이다.

## 1. 무엇을 어떤 방법으로 검증하나

| 대상 | 방법 | 왜 |
|---|---|---|
| S2 후보 규칙(점수 상위 20) | **새 판정 없음.** 점수 엔진의 예측력은 이미 백테스트·A5 로 다뤘고 여기서 다시 판정하면 같은 표본 재판정이다. 사후 수익은 기록만 한다(§2) | "안 한다" 규칙 |
| S3 논리·반증 | **forward 만.** 과거 구간 백테스트 금지 | LLM 은 학습 자료로 2016~2025 의 결과를 이미 안다. 과거 날짜의 근거 묶음을 줘도 "그 뒤 어떻게 됐는지"가 새어 들어온다 — 잴 수 없는 누수(교훈 50). 모델 지식 마감 뒤의 사건만 깨끗하다 |
| S3 운영 품질(인용 통과율 등) | 운영 관문 G0(§4) | 수익과 무관하게 먼저 걸러야 할 것 |
| S4 승인·계획 | 모의 계획의 R 배수(§4 G2) | 기존 계획 카드 규율(`MIN_SAMPLE 30` ✔) |
| S5 귀속 표 | 판정 아님 — 기록. 표에서 나온 가설은 새 사전등록으로만 | 사후 관찰을 판정에 쓰면 다중검정 |

**시기 세 칸(2016~23 / 2024 / 2025~)**: forward 는 2026-11 이후뿐이라 세 칸을 채울 수 없다. 결과 표에 **"2025~ 한 칸뿐 — 대형주·반도체 쏠림 장세 특이일 수 있다"** 를 고정 문구로 싣고, '반도체 제외' 한 줄을 진단용으로 더한다(CLAUDE.md 시기 분리 규칙).

## 2. 비용·진입 — 결과 전에 고정

| 항목 | 값 | 근거 |
|---|---|---|
| 시장 | KR 연속 시장(코스피·코스닥 보통주) | 후보가 KR 관심종목 |
| 왕복 비용 | **33.5bp** | CLAUDE.md 단기 연구 기록 규칙의 KR 연속 값. 다른 시장·비용으로 옮겨 다시 보지 않는다 |
| 진입 | 기록 `occurredAt` **다음 거래일 종가** | 후보는 20:40 에 나온다. 당일 종가는 살 수 없다 |
| 청산 | 진입 뒤 5 · 20 · 60 거래일 종가 | 주 판정은 **h20** 하나. h5·h60 은 기록 전용 |
| 기준 수익 | 같은 기간 **KR 관심종목 동일가중 평균**(`KR_WATCHLIST_EW`) | 저장소에 코스피·코스닥 지수 일별 시세가 없다(구현 때 확인). "뽑힌 20개가 안 뽑힌 나머지보다 나았나"가 선별의 값을 묻는 질문이기도 하다. 한계: 오늘의 관심종목 목록 기준이라 중간에 빠진 종목은 평균에 없다 |
| 가격 | 수정주가. 정지·폐지는 `status` 로 남기고 평균에서 뺀 건수를 같이 낸다 | 생존편향을 숨기지 않는다 |
| 겹침 | 같은 종목이 연속으로 후보가 되면 **첫 날만** 사건으로 센다(그 종목이 5거래일 연속 탈락한 뒤 다시 오르면 새 사건) | 같은 종목 20일치를 20건으로 세면 표본이 가짜로 는다 |
| 군집 | 부트스트랩은 **주(週) 단위** | 같은 주 후보들은 같은 장세를 탄다 |

모의 체결은 실제보다 유리하게 나온다(O2b·O3u 시초가 체결 −17.67bp 선례). 그래서 신호 평가(§3)는 모의 체결이 아니라 **종가 + 고정 비용**으로 한다.

## 3. 반증 에이전트의 가치 — 사전등록 설계 (현황조사 §7 #6)

### 3.1 질문 (하나)
**반증 깃발이 붙은 후보(`caution`·`thesis-weak`)를 빼면, 후보 전체보다 h20 초과수익이 나아지는가 — 그리고 그 개선이 LLM 없이 코드만으로 만든 깃발보다 큰가.**

두 번째 절이 핵심이다. LLM 깃발이 "위험 상태가 있거나 커버리지가 낮은 종목"을 다시 말하는 것뿐이라면 값이 없다.

### 3.2 갈래 (결과 전에 고정)
| 갈래 | 정의 |
|---|---|
| ALL | 그날의 후보 사건 전부 |
| LLM-KEEP | 반증 `flag == "none"` 인 후보 |
| LLM-DROP | `caution` 또는 `thesis-weak` |
| CODE-DROP(기준선) | 코드 깃발: 후보일 종가가 60일선 아래 **또는** 직전 20거래일 수익률이 후보 중 하위 30% |
| CODE-KEEP | 그 나머지 |
| 미기록 | 반증 기록이 없는 후보(한도·검증 실패) — **어느 갈래에도 넣지 않고 건수를 따로 낸다** |

기준선 깃발의 정의는 여기서 고정한다. 결과를 보고 더 약한 기준선으로 바꾸지 않는다.
무작위 배정 두 갈래(반증 있음/없음)는 쓰지 않는다 — 반증이 후보를 바꾸지 않으므로(주석일 뿐) 모든 **사건(후보 첫 날)** 에 반증을 달고 깃발의 **변별력**을 보는 편이 표본을 반으로 나누지 않는다.

### 3.3 지표와 판정
- 주 지표: `D_llm = mean(excess h20 | LLM-KEEP) − mean(excess h20 | LLM-DROP)`, 주 단위 군집 부트스트랩 90% 구간.
- 기준선: `D_code` 를 같은 식으로.
- 바닥선: 후보 안에서 깃발을 **주 안에서 섞는** 순열 500회로 `D` 의 분포를 만들고 95 백분위를 문턱으로 한다.

| 판정 | 조건 |
|---|---|
| REJECT | `D_llm` 이 바닥선 문턱 아래(신호 없음) |
| INFORMATION | `D_llm` > 문턱이나 `D_llm − D_code` 의 90% 구간이 0 을 포함(코드로 되는 일) |
| ECONOMIC | 위 + `D_llm − D_code` 구간 하한 > 0 ∧ LLM-KEEP 의 h20 순초과수익(33.5bp 뒤) 평균 > ALL 의 그것 |
| ROBUST | 위 + 전반기·후반기로 나눠 둘 다 같은 부호 ∧ '반도체 제외'에서도 같은 부호 |
| INCONCLUSIVE | 판정 시점에 표본 조건을 못 채움 |

머리말에는 "신호: 있음/없음 · 경제성: 통과/미달"을 가른다(단기 연구 기록 규칙).

### 3.4 표본·시점
- 판정은 **한 번.** 조건: 첫 기록부터 **12개월 경과 ∧ LLM-DROP 사건 100건 이상 ∧ 사건이 있는 주 40주 이상.** 셋 다 차야 한다. 코드는 그 전의 `--judge` 를 거부하고 건수만 낸다(기존 `run_*_forward.py` 본보기).
- 24개월이 지나도 못 채우면 INCONCLUSIVE 로 닫는다.
- **갈래 고정**: `promptVersion`·`model` 이 바뀌면 새 갈래다. 판정은 **등록 때 정한 한 조합**만 본다. 중간에 지시문을 고치고 싶어지면 옛 조합은 계속 돌리고 새 조합을 나란히 추가한다(한도가 허락하는 한). 둘 중 좋은 쪽을 고르는 판정은 하지 않는다.
- 중간 성과는 보지 않는다. 월간 점검(`monthly-check`)에는 건수와 운영 지표만 올린다.
- 예상 속도(추정, 미실측): 하루 후보 20 중 새 사건은 며칠에 몇 건 수준일 것이다(상위권은 잘 안 바뀐다). LLM-DROP 100건에 **1년 이상** 걸릴 수 있다. ROADMAP 은 이를 전제로 한다.

### 3.5 무효 조건의 가치 (부 질문, 같은 등록에 넣되 판정은 별도 한 줄)
`INVALIDATION_TRIGGERED` 가 난 후보의 **닿은 날 다음 거래일 종가부터 20거래일** 초과수익 vs 같은 주의 닿지 않은 후보. 닿은 사건 60건 ∧ 12개월에서 한 번. `manual` 조건은 대상이 아니다.
이것이 통과해야만 "무효 조건 닿음 → 자동 청산 제안"을 논의할 수 있다(그때도 🔴 별도 GO).

### 3.6 닫는 규칙
- REJECT·INFORMATION·INCONCLUSIVE → **반증 단계를 끈다**(Gemini 호출 중지). 논리 단계는 §4 G0 를 만족하는 한 "읽을거리"로 남길지 사용자가 정한다.
- ECONOMIC 이상이어도 점수·후보 규칙에 넣는 것은 별도 🔴(정책 버전 승격). forward 확인 전에는 운용 근거가 아니다.
- 사람이 반증을 보고 거절한 후보(`approvals.jsonl` 의 `reasonCode: rebuttal`)의 사후 수익은 **기록 전용**이다(표본이 작고 비공개 — 판정에 쓰지 않는다).

## 4. 단계 관문 (현황조사 §7 #10)

앞 관문을 못 넘으면 뒤로 가지 않는다. 각 관문의 숫자는 결과 전에 고정이다.

### G0 — 운영 품질 (첫 20거래일 실행 뒤 한 번)
| 지표 | 통과 | 못 넘으면 |
|---|---|---|
| 스키마 거부(`schemaRejected`) | 0 | 코드 결함 — 고칠 때까지 정지 |
| 격리 회귀 | 20일 내내 초록 | 〃 |
| 논리 인용 통과율(`claimsKept/claimsTotal`, 20일 합) | **≥ 80%** | 지시문 버전을 올리고 G0 를 처음부터(등록 전이므로 허용) |
| 후보당 논리·반증 기록률 | **≥ 85%** | 한도·모델 안정성 점검 |
| 후보 미생성일(낡은 점수 등) | ≤ 2일 | 상류 워크플로 점검 |
| `check.kind` 가 `manual` 이 아닌 무효 조건 비율 | **≥ 50%** | 지시문 수정(코드가 점검할 수 있는 조건을 못 쓰면 반증의 절반이 쓸모없다) |

참고: 공시 해독의 인용 통과는 실측 24/25 · 30/32 · 27/27 ✔(`decode-gemini.py` 주석) — 80% 는 그보다 느슨한 선이다. 근거 묶음이 해독 원문보다 짧고 섞여 있어 낮게 잡았다.
**§3 의 사전등록은 G0 통과 뒤에 한다.** 그 전 기록은 판정 표본에 넣지 않는다(지시문이 아직 움직이므로).

### G1 — 신호 (§3 판정, 12개월+)
§3.3 의 판정이 곧 관문이다. G1 은 **S3 를 계속 돌릴지**만 정한다. G2 와는 독립이다(G2 는 사람의 승인 품질을 본다).

### G2 — 모의 계획
대상: `origin.signalId` 가 있는 종료 계획(모의 계좌).

| 지표 | 통과 |
|---|---|
| 종료 건수 | **≥ 30** (`MIN_SAMPLE` ✔ 그대로) |
| 기간 | 첫 계획부터 **≥ 6개월** |
| 기대값(평균 R) | 부트스트랩 90% 구간 하한 **> 0** |
| −1R 보다 크게 잃은 건(`worseThan1R` ✔) | 종료의 **≤ 10%** |
| 직접 입력 계획(`origin` 없음)과의 비교 | 양쪽 각 **≥ 20**건일 때만 '비교 가능'(`MIN_TAG_SAMPLE` ✔). 그 전엔 나란히 적기만 |

- 30건 전에는 기대값을 화면에 "표본 부족(n/30)"으로만 보인다(기존 규칙 ✔).
- 한계를 같이 적는다: 5분 폴링이라 손절이 늦고 갭은 못 막는다 · 모의 체결은 실제보다 유리하다 · 승인은 사람이 골랐으므로 G2 는 "파이프라인"이 아니라 **"파이프라인 + 이 사용자의 선별"** 의 성적이다.
- 속도: 한 달에 계획 3~5건이면 30건에 **6~10개월**.

### G3 — 실매매
범위 밖. G2 통과는 실매매의 필요조건일 뿐이고, 켜는 것은 사용자다(패스키·킬 스위치). Claude 는 실계좌를 켜지 않는다. 그때 24시간 서버가 필요해지면 비용 규칙(절대 규칙 9)대로 "유료, 월 얼마"부터.

## 5. 회귀 기준 (구현이 통과해야 할 것 — ROADMAP 완료 기준의 원본)

| 회귀 | 단언 |
|---|---|
| 봉투 검증 | 필수 필드 누락·UTC 시각·미래 `asOf`·모르는 `type`·선언 안 된 payload 키·`thesis`/`rebuttal` 의 `contextOnly != true` → 전부 거부 |
| 멱등 | 같은 `eventId` 두 번 쓰기 → 두 번째 거부, 로그 1줄, 진단 `duplicatesRejected 1` |
| **늦게 온 기록** | sortKey 가 로그 마지막보다 **작은** 새 기록 → 쓰인다(커서 멱등이었다면 사라졌을 경우 — ARCHITECTURE §3) |
| sortKey | `occurredAt` 과 불일치 → 거부 · 공시 sortKey 와 섞어 정렬하면 같은 날 공시가 앞 |
| 후보 규칙 | 고정 입력 → 고정 20종목(동률 정렬 포함) · `finalScore: null` 은 제외(0 취급 아님) · 낡은 `dataCutoff` → 후보 0 + 진단 사유 |
| 인용 대조 | 묶음에 없는 인용 → 탈락 · claim 숫자가 인용에 없음 → 탈락 · 통과 0건 → 기록 없음 |
| 무효 조건 | 목록 밖 `kind` → `manual` 로 강등 · 각 `kind` 의 닿음/안 닿음 경계 · 60거래일 뒤 미점검 |
| 사후 평가 | 진입이 다음 거래일 종가 · 정지·폐지 → `ret: null`·`status` · 같은 종목 연속 후보는 첫 날만 사건 |
| **격리** | 점수·선별 소스에 주석 로그 경로·타입 문자열 없음(AGENT_SPEC §5 겹 3) |
| 판정 잠금 | 조건 미달 `--judge` → 거부, 건수만 출력 |
| 실패 주입 | `PIPELINE_FAIL_INJECTION=gate-test` → 로그에 아무것도 안 쓰고 실패(한 방향 훅 — 통과는 못 만든다) |
| 승인(P7) | 웹만 `plans.json`·`approvals.jsonl` 에 쓴다 · `origin` 없는 기존 계획이 그대로 읽힌다 · `broker.place` 호출이 새 코드에 없다(grep 단언) |

전부 네트워크 없이 돈다(`--selftest`·고정 입력). 기존 회귀(`scripts/test-*`)는 변경 위험과 무관하게 매번 전부 돌린다.
