## 0. 한 장 요약

1. **LLM 은 결정 경로에 없다.** 후보는 스코어링 코드가 고르고, 주문은 위험 관문 코드가 내고, 승인은 사람이 한다. LLM(논리·반증)은 후보에 **주석**만 단다. 주석은 후보를 빼지도 더하지도 순서를 바꾸지도 못한다.
2. **이벤트 모델은 A안(별도 추가 전용 로그)** 이다. 기존 `reduce`(공시 위험 상태)는 한 줄도 건드리지 않는다. 새 로그의 멱등은 커서(`lastSortKey`)가 아니라 **`eventId` 중복 거부**로 한다 — 이유는 §3.
3. **지시서의 "5개 팀"을 "코드 3단 + LLM 1단(2역할) + 사람 관문 1"로 바꾼다.** 반증 에이전트는 토론 상대가 아니라 **"코드가 점검할 수 있는 무효 조건"을 쓰는 역할**이다 — 그래야 매도 점검으로 이어지고 가치를 잴 수 있다.
4. **상시 서버가 필요 없다.** 후보는 장 마감 뒤 하루 한 번 나오고 계획은 다음 장 09:05 부터 유효하므로, 승인 알림은 **다음 날 09:00 KST 전에만** 오면 된다(허용 지연 약 12시간). GitHub Actions + 이 PC 로 충분하다. 비용 0.
5. 공개 저장소에는 **종목에 대한 기록**(후보·논리·반증·사후 수익)만, **내 계좌에 대한 기록**(승인·계획·체결)은 PC 상태 폴더에만 둔다.

## 1. 구성 — 지시서 5개 팀과의 차이

| 지시서 | 이 설계 | 실행 주체 | 달라진 이유 |
|---|---|---|---|
| 1 데이터·이벤트 수집 | **S1 수집** — 그대로. 새 수집기 없음 | 코드(기존 Actions) | 이미 있다. 커뮤니티 수집은 범위 밖(§7 #8) |
| 2 스코어링 엔진 | **S2 후보 선별** — 기존 점수 산출물에 후보 규칙 한 겹 | 코드 | 엔진은 그대로. "후보"라는 계약만 새로 생긴다 |
| 3 논리·반증 에이전트 | **S3 주석** — 논리(thesis)·반증(rebuttal) 2역할, 1회 왕복, 토론 없음 | LLM(무료 Gemini) + 코드 검증 | 다회 토론은 한도를 쓰고 같은 모델끼리 수렴한다. 반증은 "무효 조건"으로 출력 |
| 4 리스크·실행 엔진 | **S4 관문** — 사람 승인(웹) → 기존 `plan_trader` → 기존 위험 검사. 주문 경로 불변 | 사람 + 코드(기존) | 승인 단계를 새 주문 표면 없이 넣는다 |
| 5 사후 평가 루프 | **S5 평가** — 후보·주석·무효 조건별 사후 수익, 계획 R 배수 귀속 | 코드 | 근거 단위 귀속이 비어 있었다 |

**왜 "에이전트 5팀"이 아닌가**: 현황조사 §2 대로 2·4·5번의 대부분은 이미 순수 함수 코드다. 여기에 LLM 을 끼우면 회귀로 핀하던 것이 핀할 수 없는 것으로 바뀐다. LLM 이 값을 더할 수 있는 자리는 "긴 공시 원문을 읽고 사람이 볼 맥락을 추리는 것" 하나이고, 그 선례(`scripts/decode-gemini.py` ✔ — 인용을 코드가 원문과 대조)가 이미 돌고 있다. 그 패턴을 넓히는 것이 이 설계다.

### 2.1 단계별 계약 요약 (자세한 스키마는 AGENT_SPEC)

| 단계 | 읽는 것 | 쓰는 것 | 못 하는 것 |
|---|---|---|---|
| S2 | `latest-v2.json`(finalScore·tradeAllowed·tradingState·confidence ✔) · `data/state/*` | `CANDIDATE_SELECTED` | 주석 로그를 읽는 것(격리 회귀로 강제). `rank-h5.json` 을 선별에 쓰는 것 — 그 파일 스스로 "점수·등급·추천·매매에 연결하지 않는다"고 적혀 있다 ✔ |

## 3. 이벤트 모델 확장 — A안 채택

현황조사 §3 의 선택지: A 별도 로그 / B 두 번째 reducer / C 기존 `reduce` 일반화.

**결정: A. 파생 상태는 저장하지 않고 읽을 때 접는다(fold).** B 의 "저장되는 두 번째 상태"는 만들지 않는다.

| 근거 | 내용 |
|---|---|
| 기존 회귀 보호 | `lib/stateReducer.js` ✔ · DC-1.3 분류기 · 골든셋 292종목 · `test-state-infrastructure.js` 가 전혀 안 바뀐다. C 는 🔴 경계 |
| **커서 멱등이 여기선 조용히 틀린다** | `reduce` 는 `event.sortKey <= prevState.lastSortKey` 면 무시한다(REDUCE-006 ✔). 공시는 한 소스가 시간순으로 넣으니 옳다. 그러나 이 로그는 **여러 단계가 서로 다른 시각에** 쓴다 — 수동 배치(Claude 세션)가 어제 후보에 대한 논리를 오늘 넣으면 sortKey 가 커서보다 작아 **오류 없이 버려진다**. "없는 행은 이유를 말하지 않는다"(교훈 75). 그래서 멱등 키를 `eventId` 로 바꾼다 |
| 파생은 계산한다 | 후보의 현재 수명(주석 있음·무효 닿음·평가 끝)은 로그에서 매번 접어 낸다. 저장된 상태가 없으니 로그와 어긋날 상태도 없다(교훈 75) |
| 계약 모양은 맞춘다 | `eventId`·`ticker`·`type`·`occurredAt`(KST ISO)·`sortKey`·`source`·`payload` 는 `EV-1.0`(✔ `lib/eventBuilders/dart.js`)과 같은 이름·뜻이다. 두 로그를 sortKey 로 합쳐 한 줄 타임라인으로 볼 수 있다 |

### 3.1 규약

```

          로그에 이미 있는 eventId 는 쓰기를 거부한다(조용히 무시하지 않고 진단에 "중복 n건"을 남긴다).
sortKey   {YYYYMMDD}T{HHMMSS}:{단계 두 자리}:{종목}:{순번 두 자리}      예) 20261116T204512:30:005930:00

          고정 폭이라 문자열 비교 = 시간순. 같은 날짜에서 공시 키(`20261116:2026…`)가 항상 먼저 온다
          (':' 0x3A < 'T' 0x54) — 공시 occurredAt 이 그날 00:00 인 것과 일치한다.

쓰는 쪽   GitHub Actions 하나(CLAUDE.md "정본을 쓰는 주체는 하나다"). 수동 배치는 inbox 파일을 PR 로 넣고
          Actions 가 검증·인용 대조 뒤 로그에 옮긴다(AGENT_SPEC §6).
실패      스키마·인용 검증에 실패한 기록은 로그에 쓰지 않는다. 진단 파일에만 남긴다(manifest 계약과 같은 원칙).
```

## 4. 승인 흐름 (S4)

현재: 사용자가 웹에서 계획을 직접 입력하는 것이 곧 승인이다(`autotrader/*.py` 에 승인 코드 0건 ✔).
바뀌는 것: **입력 폼의 출발점이 하나 더 생긴다** — "오늘 후보"에서 고르면 종목 카드가 진입·손절·목표를 채우고(이미 있는 동작 ✔ `_plan_form`·`stockcard`), 옆에 논리·반증·무효 조건이 보인다. 저장 버튼이 승인, 거절 버튼이 거절이다.

- **초안은 저장하지 않는다.** 후보 목록과 채워진 값은 화면을 열 때 계산한다. 새 파일도 새 쓰는 쪽도 없다 → `plans.py` 의 "웹만 plans.json 에 쓴다" ✔ 가 그대로다.
- 저장된 계획에는 `origin: {signalId, thesisEventId, rebuttalEventId}` 가 붙는다. 직접 입력한 계획은 `origin` 이 없다 — 이 차이가 VALIDATION 의 비교 축이다.
- **텔레그램에는 승인 버튼을 두지 않는다.** 봇 토큰으로 계획을 만들 수 있게 되면 주문으로 이어지는 새 표면이 생긴다. 텔레그램은 "후보 N건, 웹에서 보라"까지.
- 주문 경로(`plan_trader.step` ✔ · `engine` · `risk.check_intent` ✔)는 **한 줄도 바뀌지 않는다.** 모의 전용, 국내만, 허용 종목 안만 — 기존 그대로.
- 논리 훼손 → 매도: 반증이 쓴 무효 조건을 S5 가 매일 점검해 닿으면 **알림만** 보낸다. 팔지는 사용자가 웹의 "지금 청산"(`closeReq` ✔)으로 정한다. 자동 청산을 붙이는 것은 검증된 청산 규칙을 바꾸는 일이라 별도 🔴.

## 5. 실행 기반 — 현황조사 §7 #3 확정

| 일 | 어디서 | 언제 | 늦으면 |
|---|---|---|---|
| S1 수집 | 기존 Actions | 기존 일정(점수 16:40·공시 18:10·해독 20:00·순위 20:25 KST ✔) | 기존과 같음 |
| S2·S3·S5 | Actions `pipeline.yml`(신규) | 평일 20:40 KST, 해독 뒤 | 몇 시간 늦어도 무해 — 다음 장 전이면 된다 |
| 알림 | 기존 텔레그램 경로 | 위 실행 끝 | 〃 |
| S4 승인·모의 주문 | 이 PC(웹 + `plan_trader`) | 사용자가 볼 때 · 장중 5분 점검 | PC 가 꺼져 있으면 그날 진입 없음(계획은 `validUntil` 까지 유효 ✔) |

**허용 지연**: 후보 생성(20:40) → 다음 장 첫 점검(09:05) = 약 12시간. Actions cron 지연(실측 수 분~수 시간)은 이 안이다. 그래서 **24시간 서버는 이 파이프라인의 요건이 아니다.** 실매매 직전에 다시 본다는 기존 결정(CLAUDE.md 상태 블록)과 같다.
? `plan_trader` 프로필이 지금 PC 에서 실제로 도는지(작업 스케줄러에는 web·snapshot 두 모드만 보인다 ✔ `scripts/run-autotrader-pc.ps1`) — ROADMAP P7 착수 전 확인.

## 9. 이 설계가 약속하지 않는 것
