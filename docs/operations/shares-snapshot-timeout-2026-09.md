# shares-snapshot 30분 타임아웃 — 실패율이 아니라 벽이었다 (2026-09-11)

`2a92269`(같은 날 앞선 기록)이 원인을 **"실패율이 23% → 34% 로 오른다"**로
적었다. 네 실행을 전수로 다시 재니 그게 아니다. 이 문서가 정본이다.

## 1. 관측 — 성공 카운터가 얼어붙는다

```
                 진행 곡선 (50종목마다)                최종      패스  결과
09-08  50/100 무결점 → 112 에서 정지                  112/353   1     5.2분 success
09-09  150 까지 무결점 → 166 에서 정지                166/353   2    30.3분 cancelled
09-10  200 까지 무결점 → 214 에서 정지                214/353   2    16.1분 success
09-11  200 까지 무결점 → 233 에서 정지                233/353   2    30.4분 cancelled
```

실패가 산발하지 않는다. **어느 지점까지 실패 0 이고, 그 뒤로는 100% 실패다.**
KRX 가 세션/IP 를 한도에서 끊는 모양이지 호출이 간헐적으로 실패하는 모양이
아니다. 그리고 벽은 **뒤로 밀리고 있다**(112 → 166 → 214 → 233) — 악화가
아니라 개선 방향이다. 앞 기록의 "실패율이 오른다"는 같은 데이터를 거꾸로 읽은
것이다(분모가 고정 353 인데 벽 뒤의 전량 실패를 비율로 읽었다).

에러는 전건 `get_shorting_balance_by_date: Expecting value: line 13 column 1` —
JSON 이 아닌 응답(차단 페이지)이다.

## 2. 2차 패스는 0을 건진다

완주한 실행이 하나뿐이고, 그 하나가 답을 준다.

```
09-10  패스 2: 시도 139 · 성공 0 · 실패 139     ← 유일하게 완주한 패스 2
```

신설(2026-09-09) 근거는 "막힌 뒤 천천히 회복한다"(353→167→272→273, 09-06)
였다. 그 곡선은 **별개 실행 5회**다 — 매번 프로세스도 KRX 로그인도 새것이었다.
같은 세션 안에서 600초 쉬고 미는 것은 다른 일이고, 실측이 0을 준다.

교훈61 그대로 — 패스 기록을 남긴 것이 값을 했다. `failCount` 만 봤으면
재시도가 0을 건졌는지 전부 건졌는지 구분이 안 됐다.

## 3. 잘린 두 실행은 느린 게 아니라 매달렸다

```
09-09  패스2 11:51:24 → 12:16:51 (25분)   로그 0줄
09-11  패스2 06:31:22 → 06:47:23 (16분)   로그 0줄
09-10  패스2 11:59:09 → 12:00:19 (70초)   에러 139줄     ← 정상적으로 빨리 실패
```

진행표시는 50종목마다 찍는다. 25분 동안 한 줄도 안 나왔다 = **50개도 못 돌았다.**
빠른 실패(차단 페이지)와 달리 KRX 가 아예 응답을 끊었고, pykrx 는 timeout 없이
requests 를 부르므로 **한 호출이 영영 매달린다.**

## 4. 진짜 손해는 타임아웃이 아니라 버려지는 데이터다

```
Build snapshot                      cancelled
Consumer check (sector-strength)    skipped
Commit snapshot                     skipped    ← 패스1 이 건진 233종목까지 통째로 버려진다
```

0을 건지려고 그날 데이터를 전부 잃는 거래다. 그리고 conclusion 이 `failure` 가
아니라 `cancelled` 라 아무도 모른다.

## 5. 고친 것

```
MAX_PASSES  2 → 1          측정값이 0/139 이다. 재개는 `--passes 2` 한 줄
install_http_timeout()     timeout 없이 나가는 requests 호출에 기본 30초
notify-failure             cancelled 도 실패로 센다 + shares-snapshot 을 감시에 추가
```

★ **`socket.setdefaulttimeout` 은 듣지 않는다.** 처음에 그걸로 짰다가 실측에서
틀렸다 — urllib3 2.x 는 전역 소켓값을 안 보고 자기 기본값을 쓴다(전역 3초를
걸어도 60초를 기다렸다). `HTTPAdapter.send` 에 넣어야 걸린다. selftest 가
응답 없는 소켓에 붙어 실제로 끊기는지 재므로, 옛 방식으로 되돌리면 붉어진다.

**타임아웃(`timeout-minutes: 30`)은 안 올렸다.** 임계를 옮기는 것은 경고를
끄는 일이다 — 기대 실행시간이 5분대로 돌아왔으므로 30은 이제 백스톱이다.

## 6. 벽의 정체 — 세션이 아니라 **출처(IP) 단위 차단**이다 (2026-09-11 실측)

§5 를 고친 날 같은 자리를 마저 팠다. 프로브: `scripts/probe-krx-wall.py` ·
워크플로 `probe-krx-wall.yml`(수동 전용). 실행 2회(34597324204 · 34597871676).

### 6.1 막힌 응답의 정체 — 200 OK 인데 차단 페이지다

여태 아무도 이걸 본 적이 없었다. 로그에는 `JSONDecodeError` 만 남았기 때문이다.

```
status        200                                    ← 429 도 500 도 아니다
content-type  text/html;charset=UTF-8
length        2570
url           https://data.krx.co.kr/comm/error/blockError_01.jsp
title         에러페이지 - 한국거래소 | Data Marketplace
```

**`blockError_01.jsp`** — KRX 가 이름으로 말하고 있다. 세션 만료도 유량 초과 응답도
아니고 **차단**이다. 그리고 HTTP 는 200 이라 상태코드만 보는 코드는 전부 통과시킨다.

> 교훈81 그대로다 — *성공 코드는 '내 질문에 답했다'를 뜻하지 않는다.*
> 여기서는 200 + `text/html` 이 그 자리다.

### 6.2 세션 단위 기각 — 막히면 **로그인조차 못 한다**

가르는 관측이 이것이다. 막힌 뒤 `KRXSession.refresh()` 를 부르면:

```
login_krx() -> POST https://data.krx.co.kr/contents/MDC/COMS/client/MDCCOMS001D1.cmd
            -> 같은 blockError_01.jsp
            -> resp.json() 에서 JSONDecodeError
```

로그인 URL 은 데이터 URL 과 **다른 주소**다. 세션이 무효화된 거라면 로그인은 되어야
한다. 안 된다는 것은 **호출자 자체가 막혔다**는 뜻이다. 60초 쉬고 다시 해도 같다
(09-10 의 같은 세션 600초 대기도 0을 건졌다, §2).

### 6.3 계정 단위도 기각 — 5분 뒤 다른 실행이 124건을 성공시켰다

```
1회차  12:06~12:11   벽 219번째 · 로그인 후 190초 · 이후 재로그인 불가
2회차  12:14~12:17   egress IP 172.208.126.97
                     벽 125번째 · 로그인 후 95초   ← 앞 124건은 **정상 성공**
```

같은 `KRX_ID` 다. 계정 단위 차단이었다면 2회차는 **첫 호출부터** 막혔어야 한다.
124건이 성공했다 = 계정은 안 막혀 있었다.

★ 정직하게: 1회차는 IP 기록 스텝을 넣기 **전**이라 두 실행의 IP 가 실제로 달랐다는
직접 증거는 없다(러너마다 다른 것이 Actions 의 정상 동작이라는 전제에 기댄다).
그러나 **계정 기각은 IP 와 무관하게 성립한다** — 위 논증에 IP 가 안 들어간다.
확정하려면 지금은 IP 스텝이 있으니 두 번 연속 돌려 두 IP 를 같이 찍으면 된다.

### 6.4 그래서 2차 패스의 원래 근거가 confounded 였다

신설 근거는 "막힌 뒤 천천히 회복한다"(353→167→272→273, 2026-09-06, 30분에 5회)
였다. 그 5회는 **별개 Actions 실행**이다 — 즉 매번 러너가 바뀐다. 회복한 게 아니라
**새 출처가 새 예산을 받은 것**이다. 같은 출처 안에서는 §2 대로 0을 건진다.

그 위에 얹혀 있던 추론도 같이 무너진다:

> (옛 주석) "호출 간격이 좁아서 막히는 모양이 아니다 — 한도에 부딪힌 뒤 더 천천히
> 미는 것은 같은 벽이다"

이 문장의 근거가 위의 confounded 곡선이었다. **속도를 늦추는 쪽은 지금 미검증
후보로 되살아난다.** 관측된 벽은 시간과 같이 움직인다:

```
벽 위치   107 · 112 · 124 · 166 · 214 · 219 · 233     (SLEEP_SECONDS=0.2, 약 1.3~2 req/s)
로그인 후  56 ~ 190초
```

즉 **1~3분 안에 100~230건**이면 걸린다. 호출 수 고정도 시각 고정도 아니라서
"단위시간당 요청"에 가깝지만 아직 못 박지 못했다.

### 6.5 ★ 고친 것 — 늦추기도 샤딩도 아니고 **출발점 회전**이었다

늦추기 실험을 설계하다가 먼저 물었다 — **벽 때문에 실제로 잃는 게 뭔가.**
재니 "77%만 받는다"가 아니었다.

```
스냅샷 보유 = 유니버스 인덱스 0~272 · 없음 = 273~352     예외 0건
```

매 실행이 같은 순서로 처음부터 돌았기 때문에 **뒤쪽 80종목은 영영 KRX 값을 못
받는다.** `carry_forward` 도 못 구한다 - 한 번도 받은 적이 없어 이월할 값이 없다.
그래서 그 80개는 늘 A3c 폴백이고, A3c 는 KRX 와 꽤 다르다(271종목 대조):

```
완전 일치 61.6%  ·  >1% 차이 26.2%  ·  >5% 7.7%  ·  >20% 2.2%
최대 400%(010120) · 391%(183300)     <- 액면분할로 보인다
```

시총 = 가격 × 상장주식수라 `capTop`·`capCov`·CAP_RS 가 그만큼 틀어진다.
소비자에 A8 기반 가드가 있지만(`PRICE_BASIS_MISMATCH`) **A8 은 cron 이 없고
실측 23일 낡았다** - 오늘 UNVERIFIED 는 4건뿐이었다. 그물이 샌다.

고치는 길이 셋이었고 **셋째를 골랐다.**

| | 비용 | 판정 |
|---|---|---|
| 늦추기 | 미검증(유량인지 총량인지 미확정) · 이겨도 6~12분 직렬 | 안 한다 |
| 샤딩 | A4 8-way · A8 16-way 의 **검증된** 패턴이나 matrix→artifact→finalize 배관 필요 | 지금은 과하다 |
| **출발점 회전** | 한 줄. 4일이면 353종목 한 바퀴(carry 14일 안) | **채택** |

```python
ROTATE_STRIDE = 100          # 관측 최소 벽(107)보다 작아야 연속된 날의 창이 겹친다
off = (day.toordinal() * stride) % len(tickers)
```

날짜의 함수라 재현 가능하다(같은 날 두 번 돌리면 같은 목록 - 난수를 안 쓴 이유).
회귀가 **관측 최소 벽 107 에서도 4일 안에 전 종목이 덮이는지**를 재므로
`ROTATE_STRIDE` 를 벽보다 크게 올리면 붉어진다(150 으로 올려 확인: 미커버 43개).

★ 회전으로 충분한 이유는 **'당일 전종목'이 필요 없어서**다. 하루 안에 353개가
다 필요해지면 그때 A8 처럼 matrix 샤딩으로 올린다 - 그 전에는 배관을 안 늘린다.

### 6.5.1 남은 것과 다음 실험

```
모르는 것   유량 기준인가 총량 기준인가 (벽이 107~233 로 흔들린다)
            쿨다운 길이 (60초·600초 동일출처는 실패 확인. 그 위는 안 쟀다)
            늦추면 안 걸리는가 — **가장 값싸고 아직 안 한 실험**
```

다음 실험은 `SLEEP_SECONDS` 를 0.2 → 0.6~1.0 으로 올려 353종목을 완주하는지 보는
것이다. **단 §6.5 로 급한 이유가 사라졌다** - 커버리지 구멍이 닫혔으므로 이건
'당일 전종목'이 필요해질 때의 선택지이고, 그때도 샤딩이 먼저다(검증돼 있다). 완주하면 벽은 유량이고 해법은 "천천히"다(실행시간은 6~12분이 되지만 지금
4.8분에 273종목이니 남는 장사다). 안 되면 총량이고, 그때는 출처를 나누는 문제
(VM 수집 이관)가 된다.

**급하지 않다.** 실패분은 `carry_forward`(≤14일)와 A3c 폴백이 받고, §5 로 잡이
안 터지므로 매일 273/353 은 들어온다.

### 6.6 프로브 자체에서 나온 결함 셋 (재사용 시 주의)

1. **pykrx 는 `JSONDecodeError` 를 스스로 잡아 찍고 빈 df 를 준다.** 막힘이 예외로
   안 오고 '빈 응답'으로 온다 — 1회차에서 진단 덤프가 한 번도 안 돌았다.
2. 조기중단 조건을 `fail>=25 and ok==0` 으로 썼는데 `ok` 가 누적이라 영영 안 걸렸다.
   연속 실패(streak)로 세야 한다.
3. 재로그인 예외가 프로세스를 죽였다. **그건 측정값이지 크래시가 아니다** — 잡아서
   로그인 엔드포인트의 막힌 본문까지 찍게 고쳤다.

셋 다 "통과가 정보를 주는지 먼저 묻는다"(교훈61·72)에 걸린 자리다. 1회차는
`failure` 로 끝났지만 **그 실패 자체가 §6.2 의 답**이었다.
