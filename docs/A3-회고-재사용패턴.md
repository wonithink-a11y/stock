# A3 회고 — 재사용 패턴

**"무엇을 배웠는가"가 아니라 "무엇을 재사용하는가"다.** 교훈은 CLAUDE.md에 이미
78개가 있다. 여기 담는 것은 다음 수집기(분봉·A3b·A4·뉴스·해외)가 **집어 쓸 수 있는
형태**이며, 그래서 `Source`와 `Verification`이 필수 필드다.

`Verification`을 못 적는 항목은 아직 패턴이 아니라 관행이다. 목록에 남기되 그렇게
표시한다 — 다음 수집기가 그것을 복제할 때 회귀부터 만들어야 한다는 뜻이다.

작성 2026-08-08 (A3 종료 직후) · 대상 태그 `a3-complete`

---

## 1. Resume 호환 판정

```
Pattern        무엇이 같으면 어제 것을 이어받아도 되는가를 명시 목록으로 고정한다
Applicability  여러 날에 걸치는 모든 수집기
Source         config/policies/fundamentals.v1.json  collectionContract.fields
               → 해시가 상태와 manifest 양쪽에 남는다
Verification   scripts/test-fundamentals-a3.py — resume 무결성 회귀
주의           정책 version 문자열로 판정하지 않는다. 임계 하나만 고쳐도 version이
               올라가고 그 순간 며칠치 수집이 조용히 버려진다.
               기준은 하나다 — "이 값이 달랐다면 어제 다른 레코드가 나왔는가?"
               A3 실측: 그 경로가 발동했다면 1,381법인·16,050호출이 사라졌다
```

임계·quota·retryAttempts·output은 이 목록에 **넣지 않는다.** 판정이거나 같은 결과에
이르는 경로의 차이일 뿐 무엇이 수집되는지를 바꾸지 않는다. FN-1.4가 임계만 바꾸므로
A3 재수집이 필요 없는 근거도 이것이다.

## 2. manifest = 인수 조건 통과 증명

```
Pattern        manifest는 "파일이 있다"가 아니라 "인수 조건을 통과했다"를 뜻한다
Applicability  산출물을 내는 모든 단계
Source         lib/backfillManifest.js · docs/BF-1.1-백필계약.md
Verification   *_FAIL_INJECTION 훅 — 인수 조건을 강제 실패시켜 산출이 안 써지는지 본다
주의           실패 시 산출물을 쓰고 exit(1)하지 않는다. 쓰면 하류가 깨진 데이터로
               정상 통과한다. 워크플로의 manifest·commit 스텝은 if: success()
```

`*_FAIL_INJECTION`은 **실패만 만들 수 있고 통과는 만들 수 없다.** 한 방향 훅이라
남겨둬도 나쁜 데이터를 밀어 넣는 통로가 되지 않는다. 새 단계에도 같은 형태로 붙인다.

A3에서 이 패턴이 실제로 일했다 — finalize #1이 게이트에서 죽었을 때 산출물·manifest가
쓰이지 않아 데이터가 손상되지 않았다.

## 3. 상태 검사를 범위별로 나눈다 (T · S · M)

```
Pattern        T 전이(두 상태) · S 상태(하나) · M 병합(전 샤드)
               무리마다 잴 수 있는 자리가 다르므로 사는 자리도 다르다
Applicability  샤딩된 모든 수집기
Source         scripts/build-fundamentals-a3.py  state_invariant_violations 등
Verification   scripts/test-fundamentals-a3.py — 네 전이가 서로 독립으로 발동
주의           병합에서만 잴 수 있는 것을 샤드 쪽에 두면 각 샤드는 늘 정상으로 보인다.
               전이 검사는 실행된 것만 본다 — 예산 소진으로 즉시 끝난 샤드는 보지
               않으므로 실행 여부와 무관한 성질은 읽는 쪽에서 다시 잰다
```

가능하면 **쓰는 시점에 강제한다**(`save_progress`). 읽는 시점의 발견보다 안전하다.

**통과가 정보를 주는지 먼저 묻는다.** `conservationOk`는 `remaining`을
`assigned-done-hard`로 만든 뒤 그 등식을 다시 봤다 — 구성상 참이라 영원히 빈
배열이었고, 그래서 지웠다. 그런 필드는 주석을 달지 말고 지운다. 남아 있으면 true가
건강으로 읽힌다.

## 4. 원시 사실은 수집 자리에서, 파생은 계산

```
Pattern        응답을 본 수집기만 아는 사실을 그 자리에서 남긴다. 비율·패턴은 저장 안 함
Applicability  모든 수집기
Source         recordGaps (법인×연도 공백 사유) · reportsFound · recordRejected
Verification   scripts/test-analyze-a3.py — 분석기가 원시에서 파생을 재계산
주의           '조회하지 않음'과 '조회했더니 없음'을 구분한다. 경계를 지우면
               커버리지가 영원히 거짓말을 한다
```

분모가 산출물에 남지 않는 손실이 있다. `periodEnd`를 못 읽은 보고서는 레코드가
되지 않으므로 산출물의 `periodEndMissing`은 언제나 0이다 — 확보 보고서의 절반을
잃어도 인수 조건은 전건 통과한다. 그래서 **상태에 누적 카운터**를 두고 finalize가
비율을 낸다. A3 실측 `periodEndParsedRate 1.0` · `reportsFound 24,750 == 레코드 24,750`.

## 5. 실패 원인을 세는 자리에서 가른다

```
Pattern        transport / http / parse / dart(업무오류)로 라벨을 붙여 센다
Applicability  외부 API를 부르는 모든 수집기
Source         hardErrorsByCause · callFailuresByCause
Verification   scripts/test-fundamentals-a3.py — 원인 계층 분해
주의           개수는 원인을 지목하지 못한다. 사후에 문자열을 파싱해 가르지 말고
               원인을 아는 자리에서 라벨을 붙인다.
               두 분해는 분모가 다르다 — 시도 단위와 법인-연도 단위를 한 표에 넣으면
               재시도 횟수가 실패율이 된다
```

**모르는 실패의 기본값은 '재시도 가능'이다.** '수집 불가'로 두면 새 오류 코드가 나올
때마다 공백이 조용히 넓어진다. 모르는 것은 '아직 모른다'이지 '못 한다'가 아니다.

## 6. 규칙과 예외를 다른 필드로 가른다

```
Pattern        policyHash = 어떤 규칙으로 만들었나 · approvalHash = 어떤 예외를 인정했나
Applicability  사람의 승인이 개입하는 모든 단계
Source         config/backfill/declared-gaps-a3.json · REG-1.5 approvals 네임스페이스
Verification   REQUIRED_APPROVALS가 선언 누락을 거부한다
주의           승인 목록을 정책 파일에 두면 corp 하나 승인할 때마다 그 정책을 읽는
               모든 단계의 manifest가 흔들린다.
               **승인은 수집 동작을 바꾸지 않는다.** 바꾼다면 그것은 승인이 아니라 규칙이다
```

A3는 `declaredGapsCount 0`으로 끝나 이 채널이 실제로 쓰이지는 않았다. 그래도
계약은 살아 있고, 다음 수집기에서 `nonRetryable`이 나오면 그때 쓰인다.

## 7. PIT는 게이트를 두 겹으로

```
Pattern        인수 조건(FAIL) + 합성 픽스처 회귀. 회귀는 수집 전에 돌린다
Applicability  시점 정합성이 있는 모든 데이터
Source         availableFrom > periodEnd 계약 · fnlttSinglAcnt의 rcept 기준
Verification   scripts/test-fundamentals-a3.py 213건 — 워크플로 게이트로도 돈다
주의           PIT가 뒤집혀도 점수·등급은 정상으로 보이고 백테스트만 좋아진다.
               조용히 무너지는 축은 한 겹으로 막지 않는다
```

**소스를 고를 때 '값이 있는가'만 보지 말고 '계약을 잴 필드가 있는가'를 함께 본다.**
처음 고른 `fnlttSinglAcntAll`에는 `thstrm_dt`가 없어(실측 0/240) 회계기간말을 못
읽었다 — 그대로 갔으면 3일 수집 후 0레코드였다.

## 8. 아티팩트 회수 — 이름과 선택 규칙

```
Pattern        아티팩트 이름에 시도 번호를 넣고, 병합에서 '더 나아간 것'을 고른다
Applicability  샤딩 + 재실행이 있는 모든 수집기
Source         a3-shard-<N>-a<attempt> · scripts/pick-shard-artifacts.py
Verification   scripts/test-pick-artifacts.py 29건
주의           overwrite: true를 쓰지 않는다. 재실행은 일 한도를 앞 시도가 태웠으면
               덜 진행하고 끝날 수 있어 더 나은 상태를 지운다.
               순위는 (corpsDone 수, recordGaps 법인 수) — 진행이 1순위이고
               동점이면 사실이 많은 쪽이 이긴다
```

병합 범위는 **'자기 것뿐'로 고정한다.** 샤드 아티팩트가 `_shards/` 전체를 올리면
남의 전날 상태로 오늘치를 덮을 수 있다. 첫 실행이 무사했던 것은 그때 그 디렉터리가
비어 있었기 때문이다 — 우연한 안전은 설계가 아니다.

## 9. 관측이 내구성을 막지 않게

```
Pattern        사람이 읽는 스텝은 continue-on-error. 출력은 errors='replace'
Applicability  모든 워크플로
Source         PYTHONUNBUFFERED · GITHUB_STEP_SUMMARY · --summary
Verification   (없음) — 관행이다. 다음 수집기가 복제할 때 회귀를 만들어야 한다
주의           요약 스텝이 죽어 다음 커밋 스텝이 스킵돼 7샤드의 하루치가 날아갔다.
               반대편도 있다 — push가 5번 다 실패해도 초록불이었다.
               실패가 다음을 막는 것과 실패가 성공으로 보이는 것은 같은 축의 양끝이다
```

**초록불은 완료가 아니다.** 예산 소진은 설계상 `exit 0`이라(매일 빨간불이면 진짜
실패와 구분이 안 된다) 잡이 초록인데 담당분이 안 끝난 상태가 정상적으로 있다.
완료는 체크마크가 아니라 `완료 샤드 N/8`이 말한다.

## 10. 실행 출처 (run ID) — A3가 못 한 것

```
Pattern        manifest에 execution.runId · runAttempt · workflow를 남긴다
Applicability  Actions에서 도는 모든 수집기
Source         (A3에는 없다) → docs/MN-1.0-분봉Raw저장계약.md §5가 계약으로 넣었다
Verification   (없음) — 다음 수집기가 만들어야 한다
주의           **성공 경로에 남긴다.** A3는 run_identity()를 hardSkipped 항목에만
               펼쳐서(build-fundamentals-a3.py:992) 하드 실패 0인 정상 수집에서
               run ID가 하나도 저장되지 않았고, finalize가 _shards/를 지운 뒤에는
               복원 경로가 없었다. 날짜로는 로그를 못 찾는다
```

A3에서는 종료 시점에 **손으로 기록**해 메웠다(`docs/A3-완료기록.md`). 이 저장소에서
유일하게 복구 불가능한 메타데이터였다.
