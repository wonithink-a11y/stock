# A2a 증분화 — 결정브리프 (2026-09-11)

이 항목은 2026-09-09 부터 네 문서에 "A2a 증분화(🔴) — 하면 단기 슬리브가 진짜
일별이 된다"는 한 줄로만 이월돼 왔다. 이번에 계약·워크플로·라이브 상태를 읽고

## 0. 권고

> **A2a 계약은 건드리지 않는다.** 대신 `refresh-selections` 를 A2a 에서 떼어
> **일별로** 돌리되, 두 제약을 같이 건다 — ① 중간 일봉을 저장소에 커밋하지
> 않는다(Actions 잡 안에서만 쓴다) ② 라이브용으로는 **오늘치 선택만** 담은
> 작은 파일을 커밋하고, 10년치 `selection.json` 은 지금처럼 월 1회 연구
> 산출물로 남긴다.

한 줄 이유: **"A2a 증분화"는 문제의 이름이 틀렸다.** 실제로 막혀 있는 것은
10년 일봉을 매일 다시 만드는 일이 아니라 **단기 슬리브의 선택 목록이 매일
갱신되지 않는 것**이고, 후자는 A2a 를 안 건드리고 풀 수 있다.

## 1. 실제로 무엇이 막혀 있나 (실측 2026-09-11)

`foreign_flow5d_v1` 은 **보유 5세션 · 사실상 매 거래일 리밸런싱** 슬리브다.

```
selection.json  holdSessions 5 · rebalanceDays 2,598 (2016-01-29 ~ 2026-09-03)
                                                      ↑ 마지막 리밸런싱일
라이브 포지션    30종목 전부 entry_date 2026-09-10 · sessions_held 2 · max_holding 5
```

즉 **9/15 경 전량 시간청산되고, 다음 선택 목록은 2026-10-01 까지 없다** —
5일 슬리브가 약 11거래일 현금으로 선다. 사고가 아니라 배선의 결과다:

```
backfill-price-a2a   cron '0 10 1-5 * *'   월 1회
        ↓ workflow_run
refresh-selections   트리거가 이것 하나뿐  → selection 도 월 1회
```

## 2. A2a 가 월 1회인 이유 — 버그가 아니라 정의의 결과다

```
data/backfill/price/a2a/   15개 연도 파일 · 117MB · 거래일당 48KB(gzip)
.git                       이미 1.6GB
```

A2a 는 **매 실행이 전 연도 파일을 다시 쓴다.** "현재 상장분"만 담는 정의라
상장폐지분이 과거에서도 빠지고, `adjusted: true`(수정주가) 라 분할·병합이
나면 **과거 전 구간이 소급 재산정**된다. 실측으로 2026-09-03 실행이 2014년
파일까지 바꿨다(4,794,388 → 4,180,193 bytes).

```
월 1회   117MB × 12   ≈ 연 1.4GB   ← 현재
일별     117MB × 250  ≈ 연 29GB    ← 붙일 수 없다
```

## 3. 그래서 A2a 를 증분화하면 무엇이 깨지나 — 세 가지

1. **생존편향이 되돌아온다.** 증분 추가는 "현재 상장분"을 "그때그때 상장분"
   으로 바꾼다. A1a/A1b 를 따로 둔 이유가 바로 그 구분이고, `REQUIRED_UPSTREAM`
   이 A5→A1b 인용을 강제하는 이유도 같다.
2. **수정주가 기준이 날짜마다 섞인다.** 분할 뒤 append 하면 과거 구간은 옛
   기준, 새 구간은 새 기준이다. 값이 그럴듯하게 남아 **조용히 틀린다.**
3. **manifest 의 뜻이 바뀐다.** 지금은 "샤드 수를 바꿔도 산출물 바이트가
   불변"이라 해시가 재현성을 보증한다. 증분이 되면 해시는 "여태 쌓인 결과"가
   되고, 같은 정책으로 돌린 두 실행이 갈린다.

셋 다 검증 강도 표의 **"조용히 틀림 × 되돌릴 수 없음"** 칸이다 — 실행은
되돌리면 그만이지만, 그 위에서 내린 백테스트 결론은 되돌려도 남는다.

## 4. 권고안이 실제로 건드리는 것

```
안 건드린다   config/policies/price.v1.json · A2a 워크플로 · 연도 파일 ·
              manifest 계약 · 10년치 selection.json · 모든 findings 재현 경로
바꾼다        refresh-selections 의 트리거(workflow_run → 일별 cron + 기존 chain 유지)
새로 만든다   라이브용 "오늘치 선택" 파일 하나 (슬리브당)
```

두 제약이 비용을 없앤다:

- **중간 일봉을 커밋하지 않는다.** selection 이 읽는 것은
  `A2a bars(turnover20) + A4 raw(foreign_net/total_amount)` 이고 필요한 창은
  **최근 20여 거래일**이지 10년이 아니다. Actions 잡 안에서 받아 쓰고 버린다
  (KRX 는 무료·한도 없음 — A4 증분이 이미 같은 방식으로 15분에 돈다).
- **오늘치만 커밋한다.** 현재 `foreign_flow5d_v1/selection.json` 은 **6.0MB** 다
  — 10년치 리밸런싱 이력을 다 담기 때문이다. 그런데 라이브 경로는
  `rule.selected_symbols(as_of)` 하나만 쓴다(`paperEngine.scan_rebalance_signals`).
  백테스트가 이력을 쓰고 **라이브는 안 쓴다.**

## 5. 비용과 되돌리기

```
Actions    성공 실행 실측 16.5분(2026-09-09) → 일별이면 월 약 370분.
           저장소가 PUBLIC 이라 분 단위 과금이 없다(CLAUDE.md 공개범위 결정).
저장소      오늘치 파일만 커밋 → 일 수십 KB 수준. 연도 파일은 그대로 월 1회.
되돌리기    트리거를 원래대로 되돌리고 새 파일을 지운다. A2a·selection.json·
           manifest 를 손댄 적이 없으므로 **연구 산출물에 흔적이 남지 않는다.**
```

되돌리기가 싼 것이 이 안을 고른 이유다. A2a 자체를 증분화하면 되돌려도
그 사이 만든 산출물의 출처가 애매해진다.

## 6. 정직하게 — 이 안의 한계

- **`turnover20` 이 창 경계에서 흔들릴 수 있다.** 매일 최근 20여 거래일만
  받아 계산하므로, 그 창 안에서 분할이 나면 월간 A2a 로 계산한 값과 다를 수
  있다. GO 하면 **첫 단계가 이것의 실측**이다(§7).
- **단기 슬리브 하나를 위한 배선이다.** 지금 일별 갱신이 필요한 라이브 슬리브는
  `foreign_flow5d_v1` 뿐이다(나머지는 hold 21~120). 슬리브가 하나뿐인데 파이프를
  하나 더 놓는 것이 맞는지는 사용자 판단이다.
- **백테스트와 라이브의 선택이 갈릴 수 있다.** 라이브는 일별 창으로, 연구는
  월간 전량으로 계산한다. 같아야 한다면 그 동치를 재는 회귀가 먼저다(§7).

## 7. GO 하면 첫 단계 (구현 전에 재는 것)

숫자 하나로 안이 서거나 무너진다.

```
최근 20거래일 창으로 계산한 selection 과, 월간 A2a 전량으로 계산한
2026-09-03 selection 이 같은가 — 종목 단위로 대조한다.
```

같으면 진행한다. 다르면 **그 차이의 원인을 밝히기 전에는 배선하지 않는다** —
다른 채로 배선하면 라이브가 연구와 조용히 갈린다.
