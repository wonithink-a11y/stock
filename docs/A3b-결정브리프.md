# A3b 결정 브리프 — 사람이 정할 것

**이 문서는 계약 설계가 아니다.** 세 안의 비용과 효과만 나란히 놓는다. 설계를 먼저
하면 결정이 그쪽으로 기운다 — 만든 것은 버리기 어렵다.

작성 2026-08-07 (A3 collect #3 이전) · 수치 출처는 코드와 실측이며 §4에 재현 명령이 있다
개정 2026-08-10 — 안 A로 결정됐다(§6). 두 커버리지 척도를 갈라 적고 범위를 한정했다

---

## 0. 한 줄

**`alotMatter` 하나만 수집하면 `availableWeight`가 0.4475 → 0.68로 임계 0.6을 넘는다.
발행주식총수는 필요 없다.**

**그리고 그것이 A3b가 하는 일의 전부다.** A3b는 폐지 종목의 재무를 복구하지 않는다 —
같은 사업보고서의 다른 절이라 A3가 보고서를 못 찾은 법인은 A3b도 못 찾는다(§5).
A3b의 목표는 **현재 상장 종목을 '유보'에서 꺼내는 것**이다.

## 1. 지금 막혀 있는 것

```
availableWeight = 0.4475  <  criteria.minimumDataCoverage = 0.6
→ 운영 정책이 전 종목을 '유보'로 만든다
```

임계를 낮춰 통과시키는 길은 없다. 커버리지 미달을 점수로 덮지 않는 것이 절대 규칙 1이다.

카테고리별로 살아 있는 비율은 `fundamental 0.85 · valuation 0 · technical 1 ·
supplyDemand 0`이다. **valuation이 통째로 0인 것**이 결정적이며, 그 넷 중 셋이
EPS 하나에 걸려 있다.

### ★ 1.1 커버리지가 두 개다 — 같은 숫자로 쓰지 않는다

`minimumDataCoverage = 0.6` 하나가 **서로 다른 두 척도**의 임계로 쓰이고 있다.
지금은 둘 다 0.68 근처라 같아 보이지만 산출식이 다르다.

```
① availableWeight        lib/a5/featureRegistry.js:89        A5 운영 게이트
   Σ_카테고리 [ categoryWeight × (가용 지표 weight 합 / 전체 지표 weight 합) ]
   카테고리 가중치와 지표 가중치를 이중으로 반영한다. 전 종목 공통 상한이다

② V1 dataCoverage         lib/scoringEngine.js:349            종목별 '유보' 판정
   non-null 지표 개수 / 전체 지표 개수 (19)
   가중치를 전혀 안 본다. 개수만 센다. 종목마다 다르다
```

`fundamental 0.85`가 개수(6/7 = 0.857)가 아닌 이유가 여기 있다 —
`shareholderReturn`의 지표 가중치가 정확히 `0.15`다.

**두 값이 0.68 근처로 붙는 것은 우연이다.** 카테고리별로는 갈린다.

```
valuation   ① 가중 기준 0.6   (perRelative 0.3 + peg 0.3, pbr·marginOfSafety 각 0.2 미가용)
            ② 개수 기준 0.5   (2 / 4)
```

fundamental이 양쪽 다 1.0이 되면서 총합이 붙었을 뿐이고, 가용성이 카테고리별로
불균등해지면 갈라진다. **한쪽 수치로 다른 쪽을 대신 말하지 않는다.**

## 2. 세 안

### 안 A — A3b 신설 (`alotMatter` 수집)

DART `alotMatter.json`(배당에 관한 사항)에서 **주당순이익 · 주당현금배당금** 두 값을
가져온다. A3가 쓰는 `fnlttSinglAcnt.json`(주요계정)에는 이 둘이 없다 — 스펙의 누락이
아니라 엔드포인트의 부재다(교훈77).

**여는 것**

| 지표 | 카테고리 | 필요한 것 |
|---|---|---|
| `shareholderReturn` | fundamental | 주당현금배당금 이력 |
| `perRelative` | valuation | EPS + 업종 횡단면(sicCode는 A3에 있다) |
| `peg` | valuation | PER ← EPS |

**열지 못하는 것** — `pbr`은 발행주식총수를 요구하고 `alotMatter`는 그것을 주지 않는다.
`marginOfSafety`는 소스 자체가 미정이다.

```
0.4475  →  0.68        alotMatter만 (valuation 0 → 0.6)
```

**비용**

```
조회 격자   (법인 × 사업연도) — A3와 같은 모양
            A3 실측: 보고서 확보 24,200 + 공백 6,471 = 30,671회
            A3b도 같은 격자이므로 같은 자릿수를 본다
일 예산     A3 몫 16,000 (전체 20,000 − 안전여유 4,000)
소요        A3 실측 4일(08-05~08-08, 3,801법인). A3b도 3~4일
```

A3가 이미 (법인, 사업연도, 접수번호) 격자를 산출물에 갖고 있으므로 A3b는 **탐색 없이
그 격자만 조회**할 수 있다. 그러면 공백 6,471회가 줄어 A3보다 짧아질 여지가 있다 —
다만 이것은 설계 선택이지 지금 확정할 것이 아니다.

### 안 B — 축소 채점 (연구용)

`valuation`을 빼고 `fundamental + technical`만으로 돌린다.

```
availableWeight 0.4475 유지 → 운영 정책상 전 종목 '유보'
```

백테스트·연구에는 쓸 수 있으나 **운영 산출은 나오지 않는다.** A5 프레임워크는
결측 전파를 정상 경로로 다루므로 코드 변경 없이 지금도 가능하다. 비용 0, 효과 0.

### 안 C — criteria 임계 완화

`minimumDataCoverage`를 0.4475 이하로 내린다.

**절대 규칙 1과 정면으로 충돌한다.** 커버리지 60% 미만이면 '유보'라는 규칙은
"정직한 점수"의 핵심이고, valuation이 0인 상태의 점수는 가치평가를 하지 않은 점수다.
비용은 0이지만 이 안을 고르면 프로젝트의 전제가 바뀐다.

## 3. 비교표

| | 안 A (alotMatter) | 안 B (축소 채점) | 안 C (임계 완화) |
|---|---|---|---|
| ① availableWeight (운영 게이트) | **0.68** ✅ | 0.4475 ❌ | 0.4475 (임계를 내림) |
| ② V1 지표 커버리지 (종목별 유보) | **13/19 = 0.6842** ✅ | 10/19 = 0.5263 ❌ | 0.5263 (임계를 내림) |
| 예상 호출 | ~30,700 (격자 재사용 시 감소) | 0 | 0 |
| 예상 소요 | 3~4일 | 즉시 | 즉시 |
| 새 수집 코드 | 필요 (A3 골격 재사용 가능) | 불필요 | 불필요 |
| 운영 산출 | 나온다 | 안 나온다 | 나온다(품질 미달) |
| 절대 규칙 1 | 지킨다 | 지킨다 | **어긴다** |

참고로 그 다음 단계까지 갔을 때의 상한이다.

```
0.68   A3b(alotMatter)
0.74   + 발행주식총수 → pbr
0.94   + A4 수급 (계약 미정)
```

발행주식총수는 **0.06밖에 더 열지 않는다.** A3b와 묶어서 결정할 사안이 아니며,
0.68에서 이미 임계를 넘으므로 별도 단계로 미룰 수 있다.

## 4. 재현

```bash
node -e "
const {FEATURES, availableWeight}=require('./lib/a5/featureRegistry.js');
const c=require('./config/criteria/KR-2.2.json');
console.log('현재', availableWeight(c).total);
['shareholderReturn','perRelative','peg'].forEach(k=>FEATURES[k].available=true);
console.log('A3b(alotMatter)', availableWeight(c).total);
"
```

`.byCategory`를 함께 찍으면 §1.1의 `categoryWeight × availableFraction` 유도가 그대로 나온다.
**②는 이 명령으로 나오지 않는다** — 다른 함수(`scoringEngine.scoreStock`)의 다른 산출식이다.

**`weightUnlockedBy(criteria, 'A3b')`를 그대로 쓰면 안 된다.** 그 함수는
`stage === 'A3b'`인 피처를 전부 켜는데 거기에 `pbr`이 들어 있다. `pbr`의 blocker는
EPS가 아니라 발행주식총수이므로 0.2925는 과대 추정이다. 레지스트리의 `stage` 필드가
A3b의 범위를 미리 가정하고 있는 셈인데, **그 범위가 바로 정할 것**이었다.

**고쳤다 (2026-08-10).** `pbr`의 `stage`를 `A3b` → `A3c`(발행주식총수)로 갈랐고, 같은
커밋에서 `docs/A5-1.0-입출력계약.md` §5의 `0.74`도 `0.68`로 고쳤다. 이제
`weightUnlockedBy(criteria, 'A3b')`가 **0.2325**를 내며 `0.4475 + 0.2325 = 0.68`로
맞는다 — 이 절의 경고는 해소됐고, 위 재현 명령을 쓰지 않고 그 함수를 그대로 써도 된다.

## 5. A3b가 하지 않는 것 — 폐지 종목 재무 (2026-08-10 확인)

**A3b의 성공/실패 판정에 폐지 종목을 넣지 않는다.** 넣으면 예정된 결과를 실패로 읽는다.

A3 실측이 두 그룹을 갈라 놓았다.

```
현재 상장   2,563 / 2,578   99.42%   A3 재무 있음  ← A3b가 EPS·배당을 얹을 대상
폐지          440 / 1,223   35.98%   A3 재무 있음
                    783            A3 재무 없음
```

그 783을 A3b가 복구할 수 없다고 보는 근거는 **요청 격자가 같다**는 것이다.

```
A3   fnlttSinglAcntAll.json   corp_code · bsns_year · reprt_code
A3b  alotMatter.json          corp_code · bsns_year · reprt_code
```

같은 사업보고서의 다른 절이므로 보고서가 없으면 둘 다 빈 응답이다. 다만 확인 강도가
갈리므로 갈라 적는다.

```
199건   11개년 전부 013("조회된 데이터가 없습니다")  → 창 안에서 보고서가 없었다. 확인됨
599건   recordGaps 항목 자체가 없다                  → 조회 여부가 기록에 없다. 미확인
```

**599건은 별도 DART 정찰로 풀지 않는다.** A3b를 돌리면 그 599 법인을 실제로 조회하게
되고 그 응답이 A3b 자신의 진단에 남는다 — 정찰이 A3b 착수 판단을 바꾸지 못하므로
먼저 할 이유가 없다.

### ★ 그 공백은 A3b 설계 요건이다

599건이 생긴 원인은 [build-fundamentals-a3.py:967](../scripts/build-fundamentals-a3.py:967)의
`if gaps: … else: pop`이다. 같은 파일 주석이 의도를 이미 적어 뒀다 — "빈 dict를 두면
'스캔했으나 사유 없음'과 '스캔 안 함'이 같은 모양이 된다". 지금 그 둘이 실제로 구분되지
않는다.

```
A3b 요건   스캔한 (corp_code, year, reprt_code)는 결과가 없어도 반드시 남긴다
           '조회하지 않음'과 '조회했더니 없음'의 경계를 함께 남긴다 (교훈75)
```

A3를 다시 돌려 이 공백을 메우지 않는다 — 4일이 들고, A3b가 어차피 같은 격자를 조회한다.

## 6. 결정 (2026-08-10 확정)

```
■ 안 A 채택 — alotMatter(EPS · 주당현금배당금) 수집
■ 목표는 현재 상장 종목의 운영 채점 확보다. 폐지 종목 재무 복원은 범위 밖(§5)
■ 발행주식총수는 A3b에 넣지 않는다 — 0.06밖에 안 열리고 0.68로 이미 임계를 넘는다
  (별도 단계 A3c로 갈랐다. featureRegistry의 pbr.stage도 그렇게 고쳤다)
■ A3 격자를 재사용한다 + A3 데이터가 없는 798법인은 조기 종료로 스캔한다
  약 26,400 호출 · 2일. 계약은 docs/A3b-1.0-배당EPS계약.md §3
```

**계약이 확정됐다** — `docs/A3b-1.0-배당EPS계약.md`(2026-08-10). 정찰 32호출이 GO였고
`availableFrom`(rcept_no)·`periodEnd`(stlm_dt)·계약 1의 방향(`>`)이 전부 실측으로
확정됐다. 이 브리프의 몫은 여기서 끝나고, 이후 판단은 계약 문서가 갖는다.

함께 미뤄 둔 것들이다. A3b와 독립이므로 A3b 착수를 막지 않는다.

```
□ 백테스트 표본 편입 조건 — score ≠ eligible 을 먼저 정의한다.
   V1/V2 엔진 선택은 그 다음이다. 지금은 backtester.js:202 가 `score !== null` 만 보고,
   V1 의 '유보'도 IC 계산에는 그대로 들어간다(등급별 집계에서는 빠진다)
□ A5 결측 정책 — 폐지 종목의 재무 결측을 어떻게 다룰 것인가. A2b 실측 후
```

계약 설계(입력·출력·상태·resume·quota·diagnostics·merge)를 이제 시작한다. A3 collect와
완전히 독립이므로 수집을 방해하지 않는다. 설계 시 `docs/A5-1.0-입출력계약.md` §5의
`+0.2925 → 0.74`를 **0.68로 함께 정정한다** — 그 값은 `pbr`까지 켠 과대 추정이다(§4).
