## 0. 이 문서가 아닌 것

- 지표 계약이 아니다. RSI·VWAP·ATR은 여기 없다(`minute.derived`의 몫).
- 시그널 계약이 아니다.
- 정책 파일이 아니다. `config/policies/minute.v1.json`은 T0 이후에 만든다.

**Raw는 원시 사실만 담는다.** 파생은 저장하지 않고 계산한다(교훈75).

## 1. 저장 계층 — Raw는 저장소 밖, manifest는 저장소 안

```
minute.raw     parquet          저장소 밖. 네트워크로 닿는 객체 저장소
                 ↓ sha256
manifest       JSON             저장소 안. 이것이 유일한 커밋 대상
                 ↓
minute.derived 계산             저장하지 않는다
```

**약관과 무관하게 이 구조로 간다.** 허용되면 잃은 것이 없고 금지되면 지켜진다 —
한쪽이 다른 쪽보다 나쁜 경우가 없다. 미국·선물 등으로 확장해도 같은 구조가 선다.

### 1.1 결정 두 개 — Execution Environment · Storage Provider

**확정 2026-08-09.** 앞의 것이 뒤의 것의 후보 집합을 정했고, 둘 다 정해졌다.

```
Execution Environment = 상시 VM (Oracle Cloud Always Free)
Storage Provider      = VM 블록 볼륨(주) + OCI Object Storage(오프사이트 사본)
```

### 확인한 한도 (docs.oracle.com, 2026-08-09 조회)

**널리 인용되는 "A1 4 OCPU / 24GB"는 현재 문서와 다르다.**

```
Compute   VM.Standard.A1.Flex   월 1,500 OCPU시간 + 9,000 GB시간
                                Always Free 테넌시 기준 2 OCPU · 12GB
          VM.Standard.E2.1.Micro  2대 · 각 1/8 OCPU · 1GB
Block     200 GB (부트 볼륨 포함) · 백업 5개
Object    20 GB · API 요청 월 50,000
Network   아웃바운드 월 10 TB
```

2 OCPU를 24시간 돌리면 월 1,440 OCPU시간으로 1,500 안에 들어간다. 메모리도
12GB × 720시간 = 8,640으로 9,000 아래다. **상시 구동이 한도 안에서 성립한다.**

### ★ 유휴 인스턴스 회수 — 이 워크로드의 실제 위험

```
7일 동안 아래가 모두 참이면 Oracle이 인스턴스를 회수할 수 있다
  CPU 95퍼센타일 20% 미만
  네트워크 20% 미만
  메모리 20% 미만 (A1 shape에만 적용)
```

**우리 워크로드가 정확히 여기 걸린다.** Broad 증분은 하루 약 1시간이고 대부분
네트워크 대기다. CPU 점유는 한 자릿수에 머문다.

이것이 위험한 이유는 비용이 아니라 **실패 방식**이다. 회수되면 수집이 조용히
멈추고, 멈춘 사이의 분봉은 246영업일 뒤 영영 사라진다. 알림이 없으면 며칠 뒤에야
안다 — 조용히 틀리는 축이다(교훈49).

대응은 셋이고 성격이 다르다.

```
PAYG 업그레이드   Always Free 한도 안이면 요금 0. 회수 대상에서 벗어난다
                 카드 등록이 필요하다. 사람의 결정이다
부하 만들기       CPU를 인위적으로 태운다. 권하지 않는다 —
                 A1은 1,500 OCPU시간 상한이 있어 여유가 없고, 무엇보다
                 감시를 속이는 방식은 다음 사람이 이유를 모른다
살아있음 감시     회수 자체는 못 막지만 '멈춘 것을 늦게 아는' 부분은 막는다.
                 어느 대응을 고르든 이건 한다
```

`out of host capacity`로 A1 생성이 실패하는 일이 잦다. 가용성 도메인을 바꾸거나
시간을 두고 재시도한다 — 공식 문서가 안내하는 정상 동작이다.

### Storage — 규모가 결정을 쉽게 만들었다

§6.2 커버리지 실측으로 행 수를 추정했다(구간별 캔들 수 중앙값 × 종목 수).

```
Broad 일일   2,559종목 → 588,584행/일 · 호출 9,187회/일
연간(246일)  약 1.38억 행 → parquet 1.52 GB (실측)
Core 백필    182종목 × 246일 ≈ 1,640만 행 → 약 0.18 GB
```

가정이 아니라 실측이다. 하루치 562,974행을 zstd로 써서 6.16MB, **행당 10.95B**였다
(snappy는 14.98B). 합성 데이터라 실제 가격은 자기상관이 있어 이보다 작아질 여지가
있다. 압축은 zstd로 고정한다.

**200GB 블록 볼륨이면 수십 년치다.** 저장 용량은 제약이 아니다.

용량은 제약이 아니지만 **메모리는 제약이다.** Broad 하루 562,974행을 다 모으면
피크 RSS 388.7MB로, 1GB Micro VM에서 기존 모니터와 공존하지 못한다.

```
전량 누적                388.7 MB
+ 배치 쓰기              371.4 MB   ← 거의 그대로다
+ 수집 중 행 버리기       374.6 MB   ← 여전히 그대로다
+ 청크 제출              144.8 MB   ← 여기서 내려갔다
```

앞의 둘이 듣지 않은 이유는 `ThreadPoolExecutor.map`이 전량을 즉시 제출하고
future가 결과를 쥐고 있기 때문이다. **줄여야 하는 것은 '들고 있는 행'이 아니라
'인플라이트 작업'이었다.** 배치로 쓰는 것과 배치로 부르는 것은 다른 일이다.
회귀가 이 성질을 못 박는다 — 수집 중간에 이미 조각이 쓰였는지를 본다.

```
주 저장    VM 블록 볼륨. 로컬이라 쓰기·재압축·재파티션이 자유롭다
사본      OCI Object Storage 20GB. 연 2GB면 여러 해가 들어간다
          일자 파티션으로 올린다 - 종목 파티션이면 월 50,000 요청을 넘긴다
manifest  Git (저장소 안). Raw는 저장소 밖이라는 §1 원칙 그대로다
```

블록 볼륨은 백업이 아니다. VM이 사라지면 같이 사라지므로 사본을 별도로 둔다.

의존성: `pyarrow` 또는 `fastparquet`이 현재 환경에 **없다.** Collector 착수 전에
설치하고, ARM(A1) 이미지에서 휠이 있는지 먼저 확인한다.

### 왜 이렇게 정했는가 (기록)

이전 판이 "저장소는 러너에서 네트워크로 닿아야 한다"를 확정으로 적은 것은
잘못이었다. 그것은 '수집기가 GitHub Actions에서 돈다면'이라는 전제 위의 결론이었다.
전제를 명시하지 않은 조건부 결론은 확정처럼 읽힌다. **전제가 상시 VM으로
정해진 지금, 그 결론은 뒤집혔다 — 주 저장이 로컬 블록 볼륨이다.**

| Execution | Raw 후보 | 키(앱키·시크릿) 위치 | 비고 |
|---|---|---|---|
| GitHub Actions | 네트워크 저장소만 | 저장소 시크릿 | 저장소가 public이라 분 단위 한도는 없다. 그러나 증권사 키가 GitHub에 들어간다 |
| 상시 VM | **로컬 디스크 · NAS(VPN) · 객체 저장소 전부** | VM 환경변수 | 키가 GitHub 밖. 장시간 실행·큐·로컬 캐시가 자유롭다 |
| Self-hosted Runner | 그 머신이 닿는 곳 | 러너 머신 | VM과 유사하나 GitHub에 러너를 등록해야 한다 |
| Local Cron | 그 PC가 닿는 곳 | 로컬 | **무인 운영이 깨진다** — PC를 매일 켜야 한다 |

`SETUP.md`가 "증권사 API 키를 GitHub에 두는 것은 권장하지 않는다"를 이미 적어뒀고,
같은 문서가 "KIS + 상시 구동 머신(오라클 프리티어 등)"을 다음 단계로 지목했다.

상시 VM을 고르면 이 프로젝트가 A3에서 만든 것들(resume·샤딩·일 예산·재시도)이
그대로 산다. Actions의 실행 시간·아티팩트 제약 안에서 그것을 다시 접는 것보다
장시간 프로세스에 얹는 편이 원래 모양에 가깝다.

결정을 굳힌 실측 근거 넷이다.

```
EGW00201(유량초과)이 동시 4~6에서 나온다        §6.2 실측
  → concurrency 2~4 · backoff · resume이 상시 필요하다
Broad 당일 증분이 매일 약 9,200호출 · 약 1시간   §6.2 실측
  → 매일 도는 장시간 작업이며 Actions 분을 계속 태운다
Core 백필이 182종목 x 246일 x 5호출 ≈ 224,000회  §6.3
  → 한 번에 끝나지 않으므로 중단·재개가 전제다
증권사 실계좌 앱키가 GitHub 시크릿에 들어가지 않는다
```

## 2. Raw 스키마

열은 **리터럴 목록으로 고정한다.** '몇 개'로 적으면 나중에 하나를 빼도 여전히 참으로
읽힌다(교훈59).

```
ticker      [0-9A-Z]{6}   normalizeTicker 단일 창구. 문자 제거 금지
ts          KST 분 시각    YYYY-MM-DDTHH:MM+09:00. UTC 저장 금지
open  high  low  close     정수(원)
volume                     그 1분의 거래량. 누적 아님 — 누적이면 여기서 차분해 넣는다
```

`open/high/low`가 이 계약의 존재 이유다. naver 경로는 종가만 주고 그것으로 만든
캔들 폭은 실측 7~10% 과소였다(§부록). **OHLC가 없는 소스로 이 스키마를 채우지 않는다.**

### 2.1 결손은 사유와 함께 남긴다

없는 행은 이유를 말하지 않는다(교훈75). 정상 부재와 손실을 뒤에서 가를 수 없으므로
**응답을 본 수집기가 그 자리에서** 남긴다.

```
gapReason   HALT        거래정지
            PRE_LIST    상장 전
            DELISTED    상장폐지 후
            HOLIDAY     휴장
            EMPTY       조회했으나 응답이 비었다
            NOT_QUERIED 조회하지 않았다      ← EMPTY와 반드시 구분한다
```

마지막 두 줄의 경계를 지운 채로 저장하면 커버리지가 영원히 거짓말을 한다.

## 3. 파티션과 포맷

```
minute/date=YYYY-MM-DD/part-*.parquet
```

**날짜 파티션이다.** 쓰기가 날짜 단위(하루치 append)이고 백테스트가 기간으로 자르기
때문이다. 종목 파티션은 매일 파일 2,800개를 만들고 기간 조회마다 그것을 전부 연다.

조회는 DuckDB로 파일을 직접 읽는다 — 서버가 필요 없다.

```sql
SELECT * FROM 'minute/date=2026-08-*/*.parquet' WHERE ticker = '005930';
```

### 3.1 크기 — 제약이 아니다

```
Core 182     182 × 381분 × 246일 = 1,706만 행/년   parquet 후 약 0.19GB/년
Broad 2,559  §6.2 커버리지 반영   = 1.38억 행/년    parquet 후 약 1.52GB/년 (실측)
```

위는 §6.2 실측(구간별 캔들 수 중앙값)을 반영한 값이다. 얇은 종목은 하루 381분이
아니라 162분만 채우므로, 전종목에 381을 곱한 이전 추정(2.66억 행)은 과대였다.

Broad 5년치도 압축 후 약 8GB다. **git이 못 버텨서 밖에 두는 것이 아니다** —
약관과 조회 성능 때문이다. 용량을 이유로 들면 나중에 "작으니 넣어도 되지 않나"가
된다.

## 4. provenance — 파일에 붙인다

parquet 파일 메타데이터와 manifest 양쪽에 남긴다.

```
source        KIS
endpoint      inquire_time_dailychartprice
market        KRX
adjusted      true | false
requestedAt   KST
schemaVersion MN-1.0
```

`adjusted`가 특히 중요하다. **수정주가면 과거 분봉이 나중에 바뀐다** — 액면분할이
일어나면 어제 받은 2024년 분봉과 오늘 받은 같은 날 분봉의 값이 다르다. 이것은
오류가 아니라 소스의 성질이고, `adjusted`와 `requestedAt`이 없으면 사후에
"데이터가 깨졌다"로 오독된다(A2a에서 `adjusted:true`가 조용히 naver 경로로 가던
것을 뒤늦게 발견한 교훈52와 같은 자리다).

따라서 **같은 (ticker, date)의 재수집은 덮어쓰기가 아니라 새 `requestedAt`의
버전이다.** 어느 쪽을 쓸지는 읽는 쪽이 정한다.

## 5. manifest 계약

`data/backfill/minute/manifest/*.json` — **이것만 커밋한다.**

```
ticker · date · rows · sha256 · source · endpoint · adjusted
requestedAt · createdAt · schemaVersion · gapReasons
execution.runId · execution.runAttempt · execution.workflow
```

`execution` 세 필드는 **A3에서 잃은 것을 처음부터 막는다.** A3는 `run_identity()`가
`hardSkipped` 항목에만 펼쳐져(`build-fundamentals-a3.py:992`) 하드 실패가 0인
정상 수집에서는 run id가 어디에도 남지 않았고, finalize가 `_shards/`를 지운 뒤에는
복원 경로가 없었다. 날짜(`runDates`)만으로는 로그를 찾지 못한다 — 하루에 여러 번
dispatch하고 재실행도 하기 때문이다.

**성공 경로에 남겨야 한다.** 실패 경로에만 남기면 "잘 돌아간 실행"의 출처가
사라지는데, 나중에 되짚어야 하는 것은 대개 그쪽이다. `runAttempt`를 함께 두는
이유는 Re-run이 run id를 유지하고 attempt만 올리기 때문이다(교훈78).

manifest는 "파일이 존재한다"가 아니라 **"이 산출물이 인수 조건을 통과했다"**를
뜻한다(교훈43). 그러므로:

- 인수 조건 실패 시 parquet를 **쓰지 않는다.** 쓰고 나서 `exit(1)`하지 않는다.
- 워크플로의 manifest·commit 스텝은 `if: success()`다.
- Raw가 저장소 밖에 있으므로 `REQUIRED_UPSTREAM` 표에 **'외부 저장소 참조'를 명시적
  타입으로 추가한다.** 안 넣으면 "파일이 없으니 검증을 건너뛴다"는 조용한 경로가 생긴다.

검증은 데이터를 내려받지 않고도 된다 — manifest의 `sha256`과 `rows`를 DuckDB가
읽은 결과와 대조하면 된다.

**pyarrow의 parquet 쓰기는 같은 입력에 같은 바이트를 낸다**(실측, zstd).
따라서 `sha256`은 '이 파일이 안 바뀌었다'뿐 아니라 **'같은 입력에서 다시 만들면
같은 파일이 나온다'**까지 증명한다. 재빌드 검증을 행 단위 대조 없이 해시로 할 수
있다는 뜻이다. 비결정적이었다면 §5의 검증은 해시로는 성립하지 않았다.

`scripts/probe-minute-kis.py`가 잰다. 다시 재려면 그 스크립트를 돌린다.

```

                     경계는 매일 하루씩 민다. 백필은 이 창 안에서만 가능하다
■ 2  페이지 크기      120건/호출 (문서값과 일치)
■ 3  페이지네이션      시각 커서 — FID_INPUT_HOUR_1을 응답의 최소 시각으로 갱신한다
                     경계 캔들 1건이 겹친다. 수집기가 중복을 걸러야 한다
                     하루(381캔들)를 다 받는 데 5호출
■ 4  Rate limit      동시 16회까지 거부 없음 (실효 2.2회/초). 상한은 못 쟀다
■ 5  수정주가        수정주가 축이며 A2a와 같은 축이다
                     348080 / 2025-10-02 — 수정 8327 · 원주 953 · 분봉 8327 · A2a 8327
■ 6  타임존·기준시각   KST · 캔들은 시작시각 기준 (09:00 캔들이 존재)
                     하루 09:00~15:30 · 381캔들 · 장전 시간외 없음
■ 7  거래량 의미      cntg_vol은 그 1분의 거래량이다 (누적 아님)
                     하루 합 27,392,691 vs A2a 27,825,493 = 0.9844
                     차이는 시간외 거래로 보인다. 분봉 합은 정규장만이다
■ 8  휴장일 응답      빈 응답이 아니다. rt_cd=0으로 **직전 영업일 데이터를 준다**
                     2026-08-02 요청 → 20260731 응답. 아래 ★를 볼 것
■ 9  모의계좌         미측정 — 모의 앱키가 없다. 실전 키로는 잴 수 없다
■ 10 오류 코드        잘못된 시장코드만 rt_cd=2 (OPSQ2001). 나머지는 전부 rt_cd=0
                     없는 종목(999999)은 오류가 아니라 rows=0
■ 11 거래정지·액면분할  미측정 — '과거 값이 바뀌는가'는 단발 호출로 잴 수 없다. T1이다
```

### ★ 이 API는 잘못된 질문에 오류로 답하지 않는다

날짜가 파싱되지 않거나 범위를 벗어나면 **오류 없이 최근 영업일 데이터를 돌려준다.**

```
요청 20260802 (휴장)   → rt_cd 0 · 120건 · 응답일자 20260731
요청 20990101 (미래)   → rt_cd 0 · 120건 · 응답일자 20260807
요청 "notadate"        → rt_cd 0 · 120건 · 응답일자 20260807
요청 "2026-08-03"      → rt_cd 0 · 120건 · 응답일자 20260807
```

정찰 1차가 여기 걸렸다. 하이픈 날짜를 보내고 전 구간 "데이터 있음"을 받아
**보존 기간을 3년으로 읽었다.** 실제는 246영업일이다.

따라서 수집기의 성공 조건은 `rt_cd == 0`이 아니라
**`요청 일자 ∈ 응답의 stck_bsop_date 집합`**이다. 이것을 게이트로 걸지 않으면
없는 날짜를 최근 데이터로 채우고도 정상 종료한다 — 조용히 틀리는 축이다(교훈49).

6번과 7번이 특히 조용한 축이라 위에 실측을 붙였다. 타임존이 틀리면 캔들이
통째로 밀리는데 값 자체는 정상으로 보이고, 거래량이 누적인데 개별로 읽으면
모든 지표가 조용히 틀린다. naver 경로는 실측에서 누적이었고 **KIS는 구간이다** —
소스가 다르면 다시 재야 한다는 것이 확인됐다.

**약관은 이 목록에 없다.** 스크립트가 잴 수 없는 것을 체크리스트에 섞으면 "정찰을
돌렸으니 확인됐다"로 읽힌다(교훈50). 별도 트랙이며 §7이다.

## 6.2 분봉 유니버스 선정 입력 (2026-08-09 실측)

**측정이지 정책이 아니다.** Core/Broad 규모는 사람이 정한다.
`scripts/probe-minute-coverage.py` · 140종목 × 2일자 · 호출 1,250회.
분석은 `scripts/analyze-minute-coverage.py`가 계산한다 — 파생값은 저장하지 않는다.

거래대금은 A2a 일봉의 최근 60거래일 중앙값이다(종가×거래량).

```
구간          표본 실패  커버리지                최장결측(분)      일평균
                        중앙값   p10    최소   중앙  p90  최대   호출
500억이상       40   0   1.000  0.997  0.992    0    1    2     5
200~500억      38   2   1.000  0.995  0.971    0    1    2     5
100~200억      40   0   1.000  0.992  0.924    0    1    2     5
50~100억       40   0   0.993  0.971  0.832    1    2    4     5
20~50억        40   0   0.962  0.887  0.801    2    3    5     5
5~20억         40   0   0.844  0.556  0.367    4   12   18     4
5억미만         38   2   0.424  0.173  0.144   20   50   62     3
```

**절벽은 20억 근처다.** 5~20억에서 p10이 0.556으로 무너지고 최장결측 p90이
12분이 된다. 100억 이상은 60~76%가 결측 0이고 최장결측이 2분을 넘지 않는다.

세션별로는 결측이 **마감이 아니라 중반에 몰린다.**

```
구간          개장30분   중반   마감30분   균일도
500억이상       1.000  1.000    1.000    0.000
50~100억       1.000  0.994    1.000    0.006
20~50억        1.000  0.956    1.000    0.044
5~20억         0.967  0.836    0.929    0.130
5억미만         0.650  0.395    0.548    0.255
```

거래가 개장·마감에 몰리기 때문이다. **opening range·마감 전략은 얇은 종목에서도
어느 정도 성립하지만 VWAP·이동평균처럼 중반을 쓰는 지표가 먼저 깨진다.**
하한을 지표군별로 다르게 둘 여지가 여기에 있다.

일자 안정성(2026-08-03 vs 2026-07-01) 차이는 100억 이상 0.003 이하,
20~50억 0.009다. **5~20억은 0.064, 5억미만은 0.097로 흔들려 두 날짜로는
그 구간 정책을 정할 수 없다.** 다행히 하한 후보는 그 위에 있다.

측정된 분모: 두 일자 모두 381캔들로 T0 실측과 일치한다.
세션 분모에서 15:20~15:29를 뺀다 — 종가 단일가 구간이라 캔들이 제도상 없다.
결측 격자에서도 뺀다. 넣으면 모든 종목이 최장결측 10분의 바닥값을 갖는다.

## 6.3 분봉 유니버스 정책 (확정 2026-08-09)

### 원칙 — 수집 대상과 분석 대상을 분리한다

**유니버스 선정 결과를 Raw 수집의 필터로 쓰지 않는다.** 이것이 §6.2 정찰의
가장 중요한 설계 결과다. 둘을 묶으면 오늘 Core가 아닌 종목의 오늘치가 영영
사라지고, 그 종목이 나중에 Core가 되어도 이력을 만들 수 없다.

```
Universe (분석 대상)          Raw Collector (수집 대상)
  Core / Extended / Conditional      Broad = 전체
        ↑ 매 분기 재계산                 ↑ 선정과 무관하게 매일
```

`받았다`와 `쓸 수 있다`는 다른 필드다. Raw에 있다는 사실이 신호 생성 자격을
뜻하지 않는다.

### 계층

거래대금은 A2a 일봉 최근 60거래일 중앙값이다. 종목 수는 2026-08-09 기준이며
분기마다 달라진다 — **수를 계약에 박지 않는다. 기준만 박는다.**

| 계층 | 대상 | 용도 | 246일 백필 | 매일 수집 |
|---|---|---|---|---|
| Core | 200억 이상 (약 182) | 주력 단기 전략·백테스트 기본 | O | O |
| Extended | 50~200억 (약 208) | 전략의 일반화 검증 | 필요 시 | O |
| Conditional | 20~50억 (약 233) | 특정 종목 분석 | 요청 시 | O |
| Broad | 전체 (약 2,559) | 미래 이력 확보 | X | **O** |
| Signal-excluded | 5억 미만 (약 1,672) | Raw 보존만 | X | O |

**Core 200억은 이 프로젝트의 주력 전략 검증용 규모이지 '분봉 사용 가능 하한'이
아니다.** 그 구간은 커버리지가 이미 포화라 품질이 규모를 정한 것이 아니다.

### 품질 tier — 계층과 별개다

계층은 무엇을 언제 모을지를 정하고, 품질 tier는 모은 것으로 무엇을 할 수 있는지를
정한다. **50억을 하드 필터로 박지 않는다.** 경고와 함께 쓰는 것과 못 쓰는 것은 다르다.

```
50억 이상     일반적인 분봉 지표 사용 가능       p10 0.971 · 최장결측 최대 4분
20~50억       조건부 — 품질 경고와 함께 사용     p10 0.887 · 최대 5분 · 총결측 14분
5~20억        지표별 제한 — 중반 의존 지표 불가  p10 0.556 · p90 12분
5억 미만       일반 신호 생성에 부적합            p10 0.173 · 중앙 20분
```

§6.2에서 결측이 **중반에 몰린다**는 것이 확인됐으므로, 같은 종목이라도
opening range·마감 전략은 성립하고 VWAP·이동평균은 깨질 수 있다.
품질 판정은 종목 단위가 아니라 **(종목, 지표군)** 단위로 한다.

### 백필 순서 — 한 번에 돌리지 않는다

```
Step A  Core 10종목 × 246일     Collector 검증. T1 이전에는 여기까지만 간다
Step B  Core 182종목 × 246일    T1 결과 반영 후
Step C  Extended                품질 검증 후
Step D  Conditional             요청 시 On-demand
```

**T1 결과가 나오기 전에 대규모 246일 백필을 시작하지 않는다.** 재현성·수정주가
사후 변경·거래량 정정이 아직 미측정이고(§6.1), 그 답에 따라 재수집이 필요해지면
Step B를 통째로 다시 돌게 된다.

Broad 당일 증분은 이 순서와 **독립이며 지금 시작한다.** 오늘 받지 않은 하루는
246영업일 뒤 복구되지 않는다 — 이것만은 T1을 기다릴 이유가 없다.

### Collector의 P0 조건

```
success := rt_cd == "0" AND 요청일자 ∈ 응답의 stck_bsop_date 집합
```

`rt_cd == "0"`만 보고 성공 처리하면 안 된다. 이 API는 파싱 불가·범위 밖 일자에
오류 대신 최근 영업일을 정상 응답으로 준다(§6 ★). 휴장·거래정지도 같은 경로다.

## 6.1 T1 — 수집 신뢰성 정찰 (7일)

T0는 **API가 무엇을 주는가**를 한 번에 잰다. T1은 **같은 것을 반복해도 같은가**를
잰다. 이건 한 번의 호출로 알 수 없고 며칠이 필요하다.

소수 종목(5~10개)만 매일 재수집해 대조한다. 수집이 아니라 정찰이므로 산출물은
데이터가 아니라 패턴이다.

```
□ 누락        빠진 분이 있는가 · 매일 같은 자리인가 (장 시작·마감 경계가 흔하다)
□ 재현성      같은 (ticker, date)를 다시 받으면 값이 같은가
□ 수정주가    과거 값이 바뀌는가 · 바뀌면 언제 무엇 때문인가
□ 거래량      재조회 시 달라지는가 (정정 체결이 반영될 수 있다)
□ 빈 응답     간헐적으로 비는가 · 재시도로 채워지는가
```

**재현성이 이 정찰의 핵심이다.** §4가 "재수집은 덮어쓰기가 아니라 새 `requestedAt`의
버전"이라고 정했는데, T1은 그 버전이 **얼마나 자주 실제로 갈리는지**를 잰다. 거의
안 갈리면 버전 보관 비용을 줄일 수 있고, 자주 갈리면 그 이유를 먼저 알아야 한다.

### 표본은 의도적으로 고른다

무작위 5종목은 갈리는 축을 못 밟는다. 응답 형태가 달라지는 축을 일부러 넣는다.

```
대형주 · 소형주        거래량 규모
거래정지 이력 종목      §2.1의 gapReason이 실제로 나오는가
신규상장 · 폐지예정     경계 구간의 응답
보존 한계 근처의 날짜   T0가 잰 보존 기간의 마지막 며칠
액면분할 이력 종목      ★ 아래 참조
```

**액면분할은 7일 안에 일어나지 않으면 관측되지 않는다.** 표본에 분할 이력이 없으면
"수정주가 변경 없음"은 *확인*이 아니라 *미관측*이다. 보존 기간 안에 분할이 있었던
종목을 반드시 포함하고, 그런 종목이 없으면 이 항목은 **미확인으로 남긴다** —
잴 수 없는 것을 통과로 적지 않는다(교훈50·57).

### T1 동안 놀지 않는다

7일은 기다리는 시간이 아니다. Collector 중 **T1 결과에 의존하지 않는 부분**은
그동안 만든다.

```
병행 가능   parquet 쓰기 · 스키마 검증 · manifest 생성 · provenance 기록
T1 대기     재수집 정책 · 중복 판정 · 버전 보관 기간 · 결손 재시도 규칙
```

## 7. 약관 — 질문 두 개, 답이 다를 수 있다

```
Q1  API 시세를 개인 분석 목적으로 장기 보관해도 되는가?
Q2  시세 또는 그 파생값을 공개 GitHub Pages·웹 대시보드에 표시해도 되는가?
```

**Q1이 먼저다.** 아니라면 §1의 외부 저장소 구조까지 다시 봐야 한다. Q2는 그다음이며
`static/index.html`과 `docs/data/*.json`(현재 GitHub Pages로 공개 서빙 중)이
대상이다.

2차 요약에서 "시세정보는 본인 자산 투자 목적의 개인 고객만, 제3자 제공 불가, 법인은
KOSCOM 등과 별도 시세이용계약"이라는 내용을 봤으나 **원문을 확인하지 못했다**
(포털이 JS 렌더링이라 본문이 잡히지 않는다). 이 문서는 그 요약을 근거로 삼지 않는다 —
사람이 약관 원문을 읽거나 KIS에 문의해 답한다.

## 8. 하지 않는 것

- naver로 분봉을 모으지 않는다. OHLC가 없고 7거래일이면 사라진다.
- naver를 제거하지도 않는다. `intraday-check.js`는 무인증·무제한으로 이미 돌고 있고,
  KIS로 옮기면 알림 경로가 토큰 만료·429에 묶인다(교훈63).
- 두 증권사를 붙이지 않는다. 인증·토큰·rate limit·휴장·오류 분류 계약이 두 벌이 된다.
- Raw에 파생을 넣지 않는다.
- 완료 상태를 저장하지 않는다. 사실만 축적하고 완료는 계산한다(교훈54).

```
         ② Broad 당일 증분 시작 — T1과 독립이며 미루면 손실이 누적된다
T1 결과 반영 → retry·version·correction 정책 확정
Core 182종목 백필 (Step B) → Extended → On-demand
Feature Engine → Signal Engine → Execution Arbiter → Backtest
```

**Broad 당일 증분만 이 사슬 밖에 있다.** 나머지는 앞 단계가 틀리면 다시 하면
되지만, 오늘 받지 않은 분봉은 다시 할 수 없다.

약관 확인(§7)은 이 사슬과 병렬이며 어느 단계도 막지 않는다. 단 **Q1(장기 보관)의
답이 '불가'면 §1 전체를 다시 본다.**
