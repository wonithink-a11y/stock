# A5-1.0 — 채점 단계 입출력 계약

```
Status   프레임워크 구현 완료 · 운영 투입 대기 (availableWeight 0.4475 < 0.6)
작성     2026-08-06, A3 collect #3 이전
근거     config/criteria/KR-2.2.json (동결) · lib/scoringEngine.js (운영 구현)
         .github/workflows/fetch-fundamentals-kr.js (운영 수집기)
```

이 문서는 두 가지를 한다 — A5가 무엇을 먹고 무엇을 내는지 고정하고, **지금 백필이
그것을 공급할 수 있는지 판정한다.** 후자를 A5 착수 전에 하는 것이 요점이다. 앞
단계가 닫힌 뒤에 읽으면 고칠 자리가 재수집밖에 남지 않는다(교훈76).

## 0. 결론 — **운영 투입**이 막혀 있다. 구현은 지금 가능하다

두 가지를 섞지 않는다. 초판이 이것을 섞어 "A5 착수 불가"로 적었고, 그것은 과했다.

```
A5 구현      지금 가능하다. A3b와 무관한 층이 대부분이다 —
             PIT selector · feature registry · resolver · provenance ·
             confidence 입력 · 결측 전파 · 테스트
A5 운영 투입  막혀 있다. 계산 가능 가중치가 minimumDataCoverage에 못 미친다
```

**결측은 이 엔진에서 정상 경로다.** `missingAxis.v1.json`이 `renormalize`이고,
결측 축은 `components`에 null로 남고 점수 계산에서만 빠진다. 그 사실은
`confidence.coverage`로 표현되며 `PARTIAL_CALCULATION` 플래그 코드까지 이미 있다.
그러므로 축이 비어 있다는 것이 코드를 못 쓴다는 뜻이 아니다 — **점수를 운영에
내보내지 않는다는 뜻이다.**

이 구분을 잃으면 "점수가 안 나오니 개발도 못 한다"가 되어, 결측을 정상 경로로
다루도록 설계된 엔진과 정면으로 어긋난다.

### 계산 가능한 가중치가 임계에 못 미친다

`KR-2.2`의 카테고리 가중치와, 백필(A1a·A1b·A2a·A2b·A3)이 실제로 공급할 수 있는 것.

| 카테고리 | 가중치 | 공급 가능 | 막는 것 |
|---|---|---|---|
| fundamental | 0.35 | **6/7 지표** | `shareholderReturn` — 배당 이력이 없다 |
| valuation | 0.30 | **0/4 지표** | EPS·주식수가 없다 |
| technical | 0.15 | 전부 | — (A2a·A2b 가격) |
| supplyDemand | 0.20 | 없음 | A4 계약 미정 |

`fundamental`의 `shareholderReturn` 가중치가 0.15이므로 그 카테고리는 0.85만 산다.

```
계산 가능 가중치 = 0.35 × 0.85 + 0.15 = 0.4475
criteria.minimumDataCoverage = 0.6
```

**0.4475 < 0.6이므로 운영 정책이 전 종목을 '유보'로 만든다.** 임계를 낮춰
통과시키는 길은 없다 — 커버리지 미달을 점수로 덮지 않는 것이 절대 규칙 1이다.

이 수치는 문서의 주장이 아니라 **코드가 답한다.** `lib/a5/featureRegistry.js`의
`availableWeight(criteria)`가 criteria의 가중치와 피처별 `available` 플래그에서
계산하며, 회귀가 그 값이 임계 미만임을 단언한다. A3b가 들어오면 플래그 몇 개가
true로 바뀌고 수치가 따라 움직인다 — 사람이 문서를 고쳐 맞추지 않는다.

**이것이 A5 인터페이스를 지금 설계한 성과다.** A3 finalize를 마치고 A5에 착수한
뒤에 발견했다면, 그때는 이미 수집이 끝나 되돌릴 수 없었다.

## 1. 무엇이 없는가 — 실측

### 1.1 EPS·배당은 다른 엔드포인트에 있다

운영 수집기는 DART 엔드포인트를 **둘** 쓴다. A3는 그중 하나만 쓴다.

```
fnlttSinglAcnt.json   주요계정      A3가 쓴다.  13~14행 (재무상태표·손익계산서 계정)
alotMatter.json       배당에 관한 사항  A3가 안 쓴다.  주당순이익 · 주당현금배당금
```

`fetch-fundamentals-kr.js:136` `fetchDividend()`가 `alotMatter`에서 두 값을 꺼낸다.

```js
epsRow = bySe(n => n.includes('(연결)주당순이익')) || bySe(n => n.includes('주당순이익'))
divRow = ... '주당현금배당금' && stock_knd '보통주'
```

**주요계정에는 주당순이익이 없다.** 정찰 실측에서 응답 행 수가 13~14인데, 그것은
유동자산·비유동자산·자산총계·유동부채·비유동부채·부채총계·자본금·이익잉여금·
자본총계·매출액·영업이익·법인세차감전순이익·당기순이익의 집합이다.

따라서 A3의 `accounts.spec` 일곱 개는 **있는 것을 다 가져온 것이 맞고**, 빠진 것은
스펙의 누락이 아니라 **엔드포인트의 부재**다.

### 1.2 주식 수가 파이프라인 어디에도 없다

```
A1a  ticker · name · market · corp · listedAt · sector · fiscalMonth
A2a  ticker · date · open · high · low · close · volume
A3   corp · ticker · fiscalYear · availableFrom · rceptNo · fsDiv · periodEnd ·
     currency · sicCode · (계정 7) · accountSource
```

상장주식수도 시가총액도 없다. 그래서 `PBR = price / BPS`를 계산할 수 없다
(`BPS = equity / shares`).

`PER`은 주식 수 없이도 된다 — `price / EPS`이고 EPS를 `alotMatter`가 직접 준다.
**즉 EPS 확보와 주식 수 확보는 서로 다른 문제이며 여는 지표도 다르다.**

### 1.3 지표별 공급 가능 여부 (전수)

| 지표 | 카테고리 | 가중 | 필요한 것 | 지금 |
|---|---|---|---|---|
| `roe` | fundamental | 0.20 | netIncome / equity | ✅ A3 |
| `roeConsistency` | fundamental | — | roeHistory5y | ✅ A3 (11년 PIT 레코드에서 유도) |

| `shareholderReturn` | fundamental | 0.15 | 주당현금배당금 이력 | ❌ `alotMatter` |
| `perRelative` | valuation | 0.30 | price / EPS ÷ 업종평균 | ❌ EPS + 횡단면 집계 |

그러나 그 값은 `peg` 계산에 쓰이고 `peg`는 `per`을 요구하므로 혼자서는 카테고리를
살리지 못한다.

## 2. 선택지

### 안 A — A3b 신설 (권고)

`alotMatter`(EPS·배당)와 `stockTotqySttus`(발행주식총수)를 **별도 단계**로 모은다.

```
A3   fnlttSinglAcnt    재무 계정        수집 완료 (2026-08-08)
A3b  alotMatter        EPS · 배당        계약 확정 (docs/A3b-1.0-배당EPS계약.md)
A3c  stockTotqySttus   발행주식총수      미착수 — A3b와 분리했다
조인 (corp, fiscalYear, availableFrom)
```

> **2026-08-10 정정.** 이 표는 원래 `stockTotqySttus`를 A3b에 묶었는데 분리했다.
> 발행주식총수는 `availableWeight`를 0.06밖에 더 열지 않고(0.68 → 0.74) A3b만으로 이미
> 임계 0.6을 넘으므로, 두 소스를 한 단계로 묶으면 착수 결정이 불필요하게 커진다.
> `featureRegistry`의 `pbr.stage`도 `A3c`로 갈랐다 — `A3b`로 두면 `weightUnlockedBy`가
> `pbr`까지 켜서 A3b의 효과를 과대 추정한다.

**A3의 수집 계약 해시를 건드리지 않는 것이 이 안의 핵심이다.** `source.endpoint`나
`accounts.spec`에 손대면 `collectionContractHash`가 바뀌고, 그러면 collect #1·#2로
모은 **2,605법인의 resume 상태가 전부 폐기된다**(FN-1.3이 막으려던 바로 그 손실이다).
분할 축을 새 소스로 잡으면 그 손실이 없다 — A2를 유니버스 축으로 나눈 것과 같은
판단이다(교훈46).

```
비용   상한 3,801법인 × 11사업연도 × 2엔드포인트 ≈ 83,600호출 · 약 5~6일
       ↑ 최악의 경우다. 정찰 전에는 이 수를 계획의 근거로 쓰지 않는다
이득   +0.2925 → 0.74   (minimumDataCoverage 0.6 통과)
       레지스트리가 계산한 값이다: weightUnlockedBy(criteria, 'A3b')
```

**0.80이 아니라 0.74다.** `marginOfSafety`(valuation 내 0.20)는 소스가 미정이라
A3b로도 안 열린다. A4까지 오면 0.94다. 초판이 0.80으로 적었던 것을 정정한다 —
이런 수치를 손으로 적으면 이렇게 틀리므로 레지스트리가 계산하게 했다.

호출량은 **정찰 뒤에 정한다.** 위 83,600은 상한이고 실제로는 크게 줄 수 있다.
정찰이 답해야 할 질문 넷이다.

```
1  stockTotqySttus가 연도별 조회를 요구하는가, 최신 스냅샷으로 충분한가
2  발행주식수가 실제로 얼마나 자주 바뀌는가 (무상증자·액면분할 빈도)
3  PIT상 annual snapshot이면 충분한가 — 바뀐 '시점'을 알아야 하는가
4  alotMatter에 A3와 같은 조기 종료 규칙이 그대로 듣는가 (폐지 법인 구간)
```

3번이 가장 무겁다. 주식 수가 '연도 말 기준'으로만 필요하면 연도별 조회로 족하지만,
**바뀐 시점**을 알아야 한다면 다른 엔드포인트가 필요하다 — PBR의 분모가 기중에
바뀌는 것을 놓치면 그 구간의 밸류가 통째로 틀리고, 그 오류는 값이 정상 범위에 있어
눈에 띄지 않는다.

넷 다 계획을 뒤집을 수 있는 질문이다. **뒤집힐 수 없게 설계된 정찰은 돌릴 이유가
없다**(교훈51).

### 안 B — 연구용 A5를 축소 채점으로 돌린다

가능한 카테고리(fundamental 부분 + technical)만으로 채점하고, 재정규화한 가중치와
"이 점수는 어떤 축이 빠진 채 계산됐다"를 결과에 스탬프한다.

```
장점   지금 착수 가능

       백테스트가 검증하는 것이 운영에서 쓰는 그 점수가 아니게 된다 —

```

**권고하지 않는다.** 다만 A3b 수집이 도는 동안 파이프라인을 검증하는 용도로는

### 안 C — criteria 임계를 낮춘다

## 3. 입력 계약 (A3b 확보를 전제로)

A5는 **(ticker, asOf) 하나마다** 아래를 받아 `scoreStock()`에 넣는다.

```
asOf          채점 기준일 (거래일). 이 시점에 알 수 있었던 값만 쓴다
ticker        [0-9A-Z]{6}
corp          [0-9]{8}   재무 조인은 반드시 이 키로 한다
```

### 3.1 재무 — A3 (+ A3b)

**PIT 선택 규칙이 계약의 핵심이다.**

```
그 ticker의 corp에 대해  availableFrom <= asOf 인 레코드 중
                        fiscalYear 최대,
                        같은 fiscalYear면 availableFrom 최대
```

마지막 조건이 정정공시를 다룬다. 같은 `(corp, fiscalYear)`에 서로 다른
`availableFrom`이 여럿 있는 것은 중복이 아니라 사실이고, `asOf` 시점에 알 수 있던
것은 **그 시점 이전의 마지막 정정본**이다.

`roeHistory5y`는 위 규칙으로 고른 레코드의 `fiscalYear`부터 거슬러 5개 사업연도를
각각 같은 규칙으로 고른다 — **연도마다 따로 고른다.** 한 번 고른 레코드의 전기 열을
쓰면 그 값의 `availableFrom`이 뒤바뀐다(교훈47).

### 3.2 가격 — A2a·A2b

```
technical      asOf 이전 거래일의 OHLCV. warm-up은 criteria에서 산출한 일수만큼
               스냅샷일 이전 데이터로 채운다 (BF-1.1 §7 A5 인수 조건 6)
valuation      asOf의 close (PER·PBR의 분자)
```

**A2b가 없으면 생존편향이다.** `REQUIRED_UPSTREAM.A5`가 `A1b`를 요구하고
`verifyUpstream()`이 없으면 throw한다 — 우회하지 않는다.

### 3.3 업종 — `perRelative`만의 특수 사정

`perRelative`는 **업종평균 대비 배율**이라 그 종목만 봐서는 계산되지 않는다.
`asOf` 시점의 **같은 업종 전 종목 PER의 횡단면 집계**가 먼저 있어야 한다.

```
1  asOf에서 전 종목의 PER을 계산한다   (PIT 규칙으로 고른 EPS + asOf의 close)
2  업종별 중앙값을 낸다                (평균이 아니라 중앙값 — 적자 종목의 PER이 튄다)
3  각 종목의 perRelative = PER / 그 업종 중앙값
```

업종 키는 A3 레코드의 `sicCode`다. **주의 — `sicCode`는 PIT가 아니다.** '현재의
업종'이라 전 사업연도에 같은 값이 붙는다. A3가 이미 `sectorNotPointInTime: true`로
그 사실을 진단에 남기고 있고, A5는 이 한계를 **결과에 스탬프해서 물려받는다.**
업종이 바뀐 법인의 과거 `perRelative`는 그 시점의 업종이 아닌 값으로 계산된다.

### 3.4 품질 메타데이터 — 점수와 함께 흐른다

`_quality.json`(QR-1.0)의 값이 채점 입력의 신뢰도를 결정한다. A5는 **자기가 어떤
품질의 데이터로 채점했는지를 결과에 실어야 한다.**

```
fundamentalsQuality   { schema, inputDigest, sampleComplete, coverageRate }
priceQuality          A2a·A2b manifest의 해시
survivorshipSafe      A1b가 upstream에 있는가 (false면 채점 자체가 금지)
```

`sampleComplete: false`인 리포트로 만든 데이터에는 채점하지 않는다 — 부분 수집물에
manifest를 찍지 않는 것과 같은 이유다(교훈43).

## 4. 출력 계약

`lib/scoringEngine.js`의 `score()`가 내는 것을 그대로 쓰되, 백테스트가 필요로 하는
축을 더한다. **점수 계산 로직을 다시 구현하지 않는다** — 운영과 연구가 다른 점수를
내면 백테스트가 검증하는 대상이 운영에서 쓰는 그 점수가 아니게 된다. BF-1.1 §7 A5
인수 조건 4번(임의 5레코드를 현행 `analyze.js` 경로로 재계산해 `finalScore` 완전
일치)이 이것을 강제한다.

```
asOf              채점 기준일
ticker · corp
finalScore        0~100
grade             등급. 커버리지 미달이면 '유보'
categoryScores    { fundamental, valuation, technical, supplyDemand }
coverage          지표별 결측 여부에서 유도한 실제 커버리지
warnings          debtRatioAbove200 등
axisModel         SB-1.0의 모델 id. 어떤 축 집합 위에서 매겨진 점수인가 (§5.1)
                  basis · excludedAxes · matchesOperationalModel 을 함께 싣는다.
                  scoreScope FULL|PARTIAL을 대체한다 — '부분인가'가 아니라 '무슨 모델인가'가
                  답해야 할 질문이고, PARTIAL 하나로는 3축과 2축이 같은 값이 된다
inputProvenance   각 지표가 어느 레코드에서 왔는가
  fundamentals    { fiscalYear, availableFrom, rceptNo, fsDiv }
  price           { date, close }
sectorNotPointInTime  true (3.3의 한계를 물려받는다)
```

`inputProvenance`가 있어야 이상한 점수를 만났을 때 **그 점수를 만든 레코드로 되짚어
갈 수 있다.** 없으면 "2019년 A사 점수가 이상하다"에서 멈추고 원인을 못 판다.

`forward return`은 여기 넣지 않는다. 그것은 A6(분석)의 것이고, 채점 산출물이 미래
수익률을 들고 있으면 채점 단계에서 미래를 본 것처럼 보이는 이력이 남는다.

## 5. 게이트 — 무엇이 무엇을 막는가

**구현 게이트와 운영 게이트를 나눈다.** 섞으면 결측을 정상 경로로 다루는 엔진 설계와
어긋난다.

```
구현 게이트   없다. 아래는 지금 전부 만들 수 있고 실제로 만들었다 —
              featureRegistry · pitSelector · resolver · provenance ·
              confidence 입력 · 결측 전파 · 회귀 45건

운영 게이트   전부 참이라야 점수를 내보낸다
  1  A3 finalize 통과 · _quality.json의 sampleComplete == true
  2  A2b 수집 완료 (생존편향 — REQUIRED_UPSTREAM이 강제한다)
  3  availableWeight(criteria).total >= criteria.minimumDataCoverage (0.6)
  4  ✅ 결정됨 (2026-08-11) — supplyDemand를 뺀 재정규화로 간다. 아래 §5.1
```

3번이 지금 `0.4475`로 막혀 있고, 그것을 푸는 가장 짧은 길이 A3b다(**+0.2325 → 0.68**).

> **2026-08-10 정정.** 이 줄은 `+0.2925 → 0.74`였고 틀렸다. 그 값은
> `weightUnlockedBy(criteria, 'A3b')`가 `pbr`까지 켠 결과인데 `pbr`의 blocker는 EPS가
> 아니라 발행주식총수라 `alotMatter`로는 안 열린다. 맞는 값은 **0.68**이고, 0.74는
> A3c(발행주식총수)까지 갔을 때다. `featureRegistry`의 `pbr.stage`를 `A3c`로 갈라
> 같은 오독이 다시 나오지 않게 했다.
>
> **1번은 이미 통과 상태다** — `_quality.json`의 `meta.sampleComplete`가 `true`이고
> `corpsDone 3801 / corpsTargeted 3801`이다(2026-08-08 finalize).

### 5.1 게이트 4 결정 — 축 모델을 선언하고 섞지 않는다 (2026-08-11)

**결정한 것은 재정규화 여부가 아니다.** 재정규화는 MA-1.0으로 이미 구현돼 있었다.
정한 것은 **재정규화된 점수를 서로 비교해도 되는가**이고, 답은 "같은 축 집합 위에서만"이다.

#### 실측이 뒤집은 전제 — 부분 결측은 미래가 아니라 현재다

초안은 현재를 '전 종목 일괄 결측'으로 보고 부분 결측을 A4 착수 이후의 문제로 적었다.
`docs/data/latest-v2.json`(2026-08-10, 143종목)을 세면 그렇지 않다.

```
KR  fundamental+valuation+technical+supplyDemand   99건   4축
KR  supplyDemand+technical                          1건   2축
US  fundamental+valuation+technical                43건   3축
```

세 basis가 한 파일에 있고 그것을 가르는 신호는 43건 전부에 똑같이 붙은
`MISSING_DATA`·`PARTIAL_CALCULATION`뿐이다. **전 종목에 붙는 경고는 아무도 읽지 않는다.**

그리고 `weightedAverage`는 축의 지표가 전부 null일 때만 축을 null로 만들므로,
**A3b가 끝나는 순간 valuation이 EPS 있는 종목에서만 살아 KR 백필에도 basis가 둘 생긴다.**
A4를 기다릴 것도 없다.

#### 경로마다 모델이 다르다 — 이것을 지우지 않는 것이 결정의 실질

```
운영 KR (매일)          KR_4AXIS   수급을 naver에서 일별로 받는다
운영 US (매일)          US_3AXIS   US-2.2가 supplyDemand 가중치를 0으로 선언 — 결측이 아니라 시장 사실
A5 백필 채점·백테스트    KR_3AXIS   A4 미구현. 과거 수급이 없다
```

**★ `KR_3AXIS`의 백테스트 결과를 `KR_4AXIS`(운영 모델)의 검증으로 표현하거나 승격하지
않는다.** 3축이 잘 맞았다는 것이 4축도 잘 맞는다를 뜻하지 않는다. A4 완료 후
`KR_4AXIS`를 별도로 검증하고 그때 3축↔4축 차이를 비교한다 — 그 비교가 이 분리의 이득이다.
이 문장은 산문으로만 두지 않고 `SB-1.0`의 `KR_3AXIS.promotionRule`에 값으로 있으며,
운영 모델이 아닌 실행은 `runBacktest`의 **판정 요약 첫 줄**이 그 사실을 말한다.

#### 어디서 판정하는가

```
엔진   축을 계산한다. SB-1.0을 읽지 않는다 — 그래서 lib/scoringEngine.js 변경이 없다
정책   config/policies/scoreBasis.v1.json (SB-1.0) 이 모델을 선언한다
소비자 lib/a5/axisBasis.js 로 대조하고 withhold 를 판정한다
```

백테스트 표본 편입에서 '채점 엔진이 모집단을 정하지 않는다'로 가른 것과 같은 가름이다.
`SB-1.0`이 `policies`가 아니라 `analysisPolicies`에 있는 이유도 같다 — `meta.policies`는
'그 점수를 만든 정책 전량'이라는 계약이라, 엔진이 읽지 않는 정책을 넣으면 provenance가
허위가 된다.

```
onMismatch      withhold — 선언 basis와 다른 축 집합으로 채점된 종목은 그 산출물에서 뺀다
                대안 include(스탬프만)를 안 쓴 이유는 위 실측이다. 스탬프는 읽지 않으면 없는 것과
                같지만 withhold는 읽지 않으면 종목이 사라져 무시가 불가능하다
미선언          basis를 재지 않고 population.unmeasuredReasons에 AXIS_MODEL_UNDECLARED로 남긴다.
                기본 모델을 몰래 고르면 그 산출물이 어느 모델인지 모른 채 통과한다(교훈57)
제외 우선순위    NOT_SCORED → BASIS_MISMATCH → INSUFFICIENT_COVERAGE → PIT_INVALID
                basis를 coverage 뒤에 두면 basis 혼재가 전부 커버리지 미달로 세어져 0으로 보인다.
                그리고 둘은 종류가 다르다 — coverage는 연속적 품질이고 basis는 모델 정체다
```

#### 남은 것

`analyze.js`의 일별 산출(`docs/data/latest-v2.json`)은 **이번에 바꾸지 않았다.** 게이트 4는
A5 백필 채점 경로의 결정이고, 매일 도는 운영 대시보드에 withhold를 적용하는 것은 별개의
결정이다. 지금은 그 파일에 KR 4축·US 3축·KR 2축이 계속 섞여 실린다.

### 구현된 층 (2026-08-06)

```
lib/a5/featureRegistry.js   피처 → 소스·가용성. availableWeight()가 3번을 계산한다
lib/a5/pitSelector.js       PIT 3규칙 · 이력 · freshness · 미래참조 방어
lib/a5/resolver.js          레코드 → 지표 · provenance · 결측 전파 · confidence 입력

```

`ValuationFeatureProvider`만 나중에 꽂으면 된다 — 인터페이스를 먼저 닫고 구현을
나중에 넣는 구조다. A3b가 오면 `featureRegistry`의 `available` 플래그가 바뀌고
`availableWeight()`가 따라 움직인다. **사람이 문서의 숫자를 고쳐 맞추지 않는다.**

## 6. 다음 결정

**사람이 정할 것 하나** — A3b를 신설할 것인가.

```
신설    정찰 후 확정. 상한 5~6일. +0.2925 → 0.74 (운영 게이트 3 통과)

```

신설한다면 순서는 **A3 finalize → A3b 정찰 → A3b 수집**이다. A3를 먼저 닫아야
`_shards/`가 지워지고 A3b가 같은 상태 디렉터리를 두고 경합하지 않는다.

### 권고 순서

```
1  collect #3 → finalize        A3를 완전히 종료
2  A3 freeze                    계약·measured 확정. A3b와 별개의 계약이다
3  A5 프레임워크                 ✅ 완료 — A3b를 기다리지 않는다
4  A3b 정찰                     §2의 질문 넷. 호출량이 여기서 정해진다
5  A3b 수집
6  ValuationFeatureProvider 연결  레지스트리 플래그가 따라 바뀐다
7  운영 정책 활성화              availableWeight >= 0.6이 된 뒤
```

**2번의 measured는 A3b를 기다리지 않는다.** `A3/measured`와 `A3b/measured`는 별개의
계약이고, A3b가 추가된다고 A3의 실측이 바뀌지 않는다. 오히려 A3를 먼저 얼려두는 편이
이후 변경 관리가 쉽다 — 무엇이 언제부터 참이었는지가 단계별로 갈린다.
